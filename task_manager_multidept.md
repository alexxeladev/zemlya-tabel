# Задача — Доступ менеджера к нескольким отделам

## Контекст

Сейчас manager жёстко привязан к ОДНОМУ отделу (department_id). В реальности руководитель может вести несколько отделов. Нужно сделать связь «многие-ко-многим», управляемую СО СТОРОНЫ ОТДЕЛА: в настройке отдела указывается список менеджеров имеющих к нему доступ.

Это изменение ядра ролевой модели — делается ОТДЕЛЬНОЙ задачей перед разделом ВАХТА, чтобы не смешивать.

Задача намеренно НЕ указывает имена конкретных функций, переменных, файлов. Разберись в коде сам (модель Employee/department, все места где manager проверяется по одному department_id — их много: табель, расчёт ЗП, сотрудники, дашборд). Действуй по правилу 3 попыток.

Перед началом — бэкап БД:
```bash
mkdir -p ~/backups
docker exec -t $(docker ps -q -f ancestor=postgres:16) pg_dump -U tabel tabel > ~/backups/before_multidept_$(date +%s).sql
```

## Модель

Связь «многие-ко-многим» между менеджерами и отделами:
- Один менеджер может иметь доступ к нескольким отделам
- Один отдел может иметь несколько менеджеров
- Управляется со стороны отдела: в настройке отдела — список «Менеджеры отдела»

### Что делать с текущей привязкой

Сейчас у сотрудника есть department_id (его собственный отдел — где он работает как сотрудник). Это НЕ трогаем — это принадлежность сотрудника к отделу.

Добавляем ОТДЕЛЬНУЮ связь: «какими отделами менеджер управляет» (managed departments). Это разные вещи:
- `department_id` — в каком отделе сотрудник числится (работает)
- `managed_departments` — какими отделами он руководит (для manager)

Менеджер может числиться в отделе А, а руководить отделами А, Б, В.

### Миграция

- Новая таблица связи (manager ↔ department): employee_id + department_id
- При миграции: для существующих manager — перенести их текущий «управляемый отдел» в новую связь (чтобы не потерять доступ). Вероятно сейчас manager управляет своим department_id — добавить эту пару в новую таблицу.
- Применить, alembic current = head

## Логика доступа (везде где manager проверяется по отделу)

Сейчас в коде много мест: «manager видит только свой department_id». Заменить на «manager видит отделы из своего списка managed_departments».

Затронутые места (найди все):
- **Табель** — manager видит сотрудников/периоды всех своих отделов (не одного). Селектор отделов показывает его отделы.
- **Расчёт ЗП** — по всем его отделам.
- **Сотрудники** — видит сотрудников всех своих отделов (просмотр, как сейчас).
- **Дашборд** — данные по всем его отделам.
- **Workflow периодов** — может отправлять на проверку периоды всех своих отделов.
- **Финансы** — видит по всем своим отделам.
- Любые другие проверки «actor.department_id == X» для manager → «X in actor.managed_departments».

Принудительная проверка на бэке: manager не может получить данные отдела которым НЕ управляет (даже подделав запрос).

## Интерфейс

### Настройка отдела

В форме создания/редактирования отдела — секция «Менеджеры отдела»:
- Список сотрудников с ролью manager
- Можно добавить/убрать менеджеров этого отдела (мультивыбор или список с чекбоксами)
- Показывает кто сейчас управляет отделом

Доступ к этой настройке — только admin.

### Табель / Расчёт ЗП для мульт“-отдельного менеджера

- Селектор отделов показывает ВСЕ отделы менеджера + «Все мои отделы»
- По умолчанию — все его отделы (с группировкой, как у admin/accountant по отделам)
- Переключение между своими отделами

## Что НЕ делать

- НЕ трогать принадлежность сотрудника к отделу (department_id остаётся)
- НЕ делать разные уровни доступа (редактор/просмотр) на разные отделы — доступ единый (как сейчас у manager к своему отделу)
- НЕ делать раздел ВАХТА (это следующая задача)
- Не рефакторить сверх задачи

## Acceptance criteria

1. В настройке отдела — секция «Менеджеры отдела», admin назначает.
2. Менеджер с 2+ отделами видит все свои отделы в табеле (селектор + группировка).
3. Менеджер НЕ видит отделы которыми не управляет (проверка на бэке, 403 при попытке).
4. Расчёт ЗП, сотрудники, дашборд, workflow — по всем его отделам.
5. Существующие менеджеры не потеряли доступ после миграции (их отдел перенесён в новую связь).
6. Один отдел может иметь несколько менеджеров.
7. Сотрудник числится в своём отделе (department_id) независимо от того чем управляет.
8. `pytest -v` зелёный, тесты: менеджер с несколькими отделами, изоляция чужих отделов, несколько менеджеров на отдел, миграция существующих.

## Подводные камни

- **department_id vs managed_departments** — НЕ путать. Первое — где сотрудник работает, второе — чем руководит. Разные поля/таблицы.
- **Много мест проверки** — найди ВСЕ где сейчас `manager` завязан на один department_id. Пропустишь — там останется старое поведение или упадёт. Поиск по коду тщательный.
- **Миграция существующих** — обязательно перенести текущие привязки, иначе менеджеры потеряют доступ.
- **Селектор отделов** — для manager теперь список его отделов + «все мои», не один фиксированный.
- **Группировка по отделам** — переиспользуй существующую (у admin/accountant при «все отделы»), для manager ограничить его отделами.
- Миграция — alembic upgrade head + проверка.
