# Задача 3.3 — Улучшения табеля и жизненного цикла сотрудника

## Контекст

Базовый табель и workflow готовы. На реальном использовании всплыли 4 проблемы:

1. Системные пользователи (is_system_admin) видны в табеле — лишнее
2. У каждого сотрудника отрисовываются все компании системы — много шума, надо только основную по умолчанию
3. Нет кнопки «Заполнить по графику» — приходится вводить часы вручную каждый день
4. Кнопка «Уволить сотрудника» работает только в одну сторону — нет возможности вернуть

Эту задачу делаем целиком, изменения связаны логически.

## Что нужно сделать

### Изменение 1 — Системные пользователи скрыты из табеля

#### Бэкенд

`app/services/timesheet.py` → `visible_employees_for_actor`:
- Добавить фильтр `Employee.is_system_admin == False` ко всем веткам (admin/accountant/manager/employee)
- Системный admin **никогда** не попадает в выдачу табеля
- В админке сотрудников он по-прежнему виден (как и был)

Обновить тест: при запросе табеля admin **не видит сам себя** если он is_system_admin. Видит только реальных сотрудников.

### Изменение 2 — Только основная компания по умолчанию

#### Концепция

Текущая логика: для каждого видимого сотрудника отрисовываются строки **на все активные компании системы**. Это много шума.

Новая логика:
- **Для каждого сотрудника** отображаются строки только на те компании, в которых:
  - Это его `default_company_id` (основная), ИЛИ
  - В текущем периоде у него есть ячейка с часами (он работал на эту компанию)
- Если у сотрудника `default_company_id IS NULL` (топ-менеджмент без привязки) — отображаются только компании где есть его часы
- Рядом с ФИО сотрудника (в левой sticky-колонке) — кнопка «+ компания», открывает popover/dropdown со списком компаний которые ещё не отображены для этого сотрудника. Выбор → добавляется новая строка в табеле, можно вводить часы.
- На дополнительной строке (не основной компании) — кнопка `×` справа от названия компании. Доступна **только если в этой строке нет часов** за весь период. При нажатии — строка скрывается.

#### Реализация

Это **состояние UI** (не БД-сущность). Логика рендеринга — на фронте, бэкенд просто возвращает entries как раньше.

В `TimesheetMonthResponse` бэкенд возвращает дополнительное поле `extra_companies_by_employee: dict[int, list[int]]` — для каждого employee_id перечень company_ids в которых у него есть ячейки за этот месяц (помимо default_company_id). Фронт использует это чтобы сразу при загрузке развернуть дополнительные строки.

Структура ответа:
```python
class TimesheetMonthResponse(BaseModel):
    year: int
    month: int
    employees: list[EmployeeRead]
    companies: list[CompanyRead]
    entries: list[TimesheetEntryRead]
    periods: list[TimesheetPeriodRead]
    extra_companies_by_employee: dict[int, list[int]]  # ⬅️ НОВОЕ
```

#### Фронтенд

В `TimesheetPage.tsx`:
- Состояние: `expandedCompanies: Record<EmployeeId, Set<CompanyId>>` — какие дополнительные компании развёрнуты для каждого сотрудника. Хранится в локальном state компонента (не в zustand-store, потеря при перезагрузке нормальна — extras дозагрузятся из ответа сервера через `extra_companies_by_employee`).
- При первой загрузке: для каждого employee добавить в expandedCompanies все компании из `extra_companies_by_employee[employee.id]`
- Для рендеринга строк сотрудника:
  - Первая строка: его `default_company_id` (если NULL — берётся первая из expandedCompanies, иначе пустая строка-плейсхолдер «+ компания»)
  - Остальные строки: компании из expandedCompanies в порядке кодов компании

В sticky-колонке слева под ФИО сотрудника — маленькая кнопка-чип:
```
[ + компания ]
```
- Видна только когда есть необъявленные компании
- Клик открывает dropdown со списком остающихся компаний
- При выборе — добавляется в expandedCompanies, появляется новая строка
- Доступно **только в draft-периоде** (если не draft — кнопка скрыта)

На строках дополнительных компаний (не основной) — кнопка `×` слева от названия компании:
- Видна только если в этой строке за весь период 0 часов
- Клик — компания убирается из expandedCompanies
- Доступно только в draft

При вводе часов в новую (только что добавленную) строку — стандартный flow через `saveCell`. После сохранения первой ячейки запись попадает в entries и компания «приживается» как часть данных периода.

#### Тесты

Добавить тесты на `extra_companies_by_employee`:
- Если сотрудник работал в мае на 2 компании (default A и дополнительно B) — `extra_companies_by_employee[emp_id] == [B.id]`
- Если только на default — `extra_companies_by_employee[emp_id] == []`
- Если NULL default — все компании где есть часы возвращаются

#### Эндпойнты

- `POST /api/timesheet/autofill/preview` — body: `AutofillRequest`. Возвращает `AutofillPreview` без применения.
  - Права: admin / accountant / manager (своего отдела)
  - 422 если все периоды не draft (нельзя автозаполнять закрытые)
  - 422 если календарь на этот год не загружен

- `POST /api/timesheet/autofill/apply` — body: `AutofillRequest`. Считает preview заново и применяет.
  - Те же права
  - Audit log: action='timesheet_autofilled', metadata={'entries_created': N, 'employees_count': M}

#### Тесты

- Preview не меняет БД
- Применение создаёт правильное количество entries (рабочие дни × сотрудники)
- Сокращённые дни — на 1 час меньше
- Праздничные дни — не заполняются
- Существующие ячейки не перезаписываются
- Сотрудник без default_company_id — пропускается
- Сотрудник без графика — пропускается
- Сотрудник с графиком 2/2 — пропускается с причиной
- Manager не может автозаполнить чужой отдел
- Закрытый период — 422

### Изменение 4 — Кнопки «Уволить» / «Принять обратно»

#### Бэкенд

В модели Employee поле `dismissal_date: Mapped[date | None]` уже есть, и `is_active: bool`. Логика:
- Когда сотрудник **активен** — `is_active=True`, `dismissal_date IS NULL`
- Когда **уволен** — `is_active=False`, `dismissal_date IS NOT NULL` (дата увольнения)
- При **возврате обратно** — `is_active=True`, `dismissal_date=NULL` (стирается)

Добавить эндпойнты:

- `POST /api/employees/{id}/dismiss` — body: `{ dismissal_date: date }`. 
  - Admin only
  - Если is_system_admin → 403
  - Если уже неактивен → 422
  - Audit log: action='employee_dismissed', after={dismissal_date}
  
- `POST /api/employees/{id}/rehire`
  - Admin only
  - Если уже активен → 422
  - Сбрасывает is_active=True, dismissal_date=NULL
  - Audit log: action='employee_rehired'

Старый `DELETE /api/employees/{id}` — оставляем (для админа всё ещё может быть нужно удалить кого-то ошибочно созданного, без часов). Но в UI его заменим на dismiss/rehire.

При увольнении сотрудника:
- Его часы остаются в БД (никакого каскада)
- Его учётка (если есть доступ) — становится неактивной (is_active=False делает login невозможным)

#### Фронтенд

В `EmployeesPage.tsx`:

**Фильтр статуса** в шапке: радио-группа или select:
- «Работающие» (по умолчанию) — `is_active=true`
- «Уволенные» — `is_active=false`
- «Все» — без фильтра

**Колонка «Статус»** в таблице:
- Зелёный бейдж «Работает» если is_active
- Серый бейдж «Уволен с {dismissal_date}» если не is_active

**В карточке (форме) сотрудника** — секция «Финансы» переименовать в «Трудовая занятость», содержит:
- Дата приёма (как было)
- Если is_active — кнопка **«Уволить»** красная (открывает модал)
- Если не is_active — кнопка **«Принять обратно»** зелёная (без модала, сразу)

**Модал увольнения:**
- Заголовок «Уволить {Имя сотрудника}?»
- Поле даты увольнения (date picker, по умолчанию сегодня)
- Текст-предупреждение: «Часы сотрудника останутся в системе. Доступ в систему будет заблокирован. Сотрудник перестанет отображаться в табеле в новых периодах.»
- Кнопки «Отмена» / «Уволить» (красная)

**Удалить кнопку «Удалить»** из основного списка (физическое удаление сотрудника опасно — оставить только в backend для редких случаев). Для админа на странице сотрудника-черновика (без часов и истории) можно оставить иконку удаления с дополнительным подтверждением, но это не для регулярного использования.

В табеле — для уволенных:
- Если в `dismissal_date` уже прошедшая дата — сотрудник **не отображается в периодах после** этой даты
- В предыдущих периодах (до увольнения) — отображается как раньше с пометкой «уволен» рядом с ФИО
- Логика на бэке: в `visible_employees_for_actor` для периода `year, month` исключать тех у кого `dismissal_date IS NOT NULL AND dismissal_date < date(year, month, 1)`

Условие: видимы все кто был активен **хотя бы один день в периоде**.

- Rehire → снова появляется в текущем периоде
- Login дисмисснутого → 403
- Dismiss is_system_admin → 403
- Rehire активного → 422
- Audit log записывается с before/after

## Подводные камни

- **Autofill и активные периоды**: если у разных видимых сотрудников периоды в разном статусе (один draft, другой closed) — autofill применяется только к тем у кого draft. В preview показать это.
- **Autofill требует календарь** — если на год нет calendar → 422 «Загрузите производственный календарь {year}»
- **«+ компания» во время не-draft**: кнопка скрыта, expandedCompanies из локального state не очищается (страница может листаться между месяцами с разными статусами, пользователь не должен терять то что развернул в draft).
- **Dismiss с будущей датой**: разрешено (заранее зафиксировать увольнение). До наступления даты сотрудник по-прежнему активен в табеле.
- **Если уволили в середине периода — часы за оставшиеся дни остаются**: их вводил manager до увольнения, никто их не вычищает. Это OK — фактические часы фактически отработаны. Сами часы после даты увольнения вводить нельзя (но это уже задача 3.4+ если понадобится).
