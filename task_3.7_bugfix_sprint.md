## БАГ 1 — Workflow для accountant (бухгалтер) не работает

**Сейчас:** Accountant заходит в табель отдела со статусом «На проверке» → не видит кнопок «Утвердить» и «Вернуть на доработку», или видит но они не срабатывают.

**Должно быть:**

| Состояние периода | Роль | Какие действия доступны |
|---|---|---|
| draft | manager (своего отдела) | Отправить на проверку |
| draft | admin | Отправить на проверку (любого отдела) |
| draft | accountant | Никаких (он не отправляет) |
| draft (department=NULL) | accountant | **Закрыть напрямую** (пропуская проверку) |
| pending_review | accountant | Утвердить · Вернуть на доработку (с обязательной причиной) |
| pending_review | admin | Утвердить · Вернуть (с причиной) |
| pending_review | manager | Никаких (он уже отправил) |
| closed | admin | Переоткрыть (с обязательной причиной) |
| closed | accountant | Никаких (только admin переоткрывает) |

**Где искать причину:**
- Возможно, в схеме периода (Pydantic) флаги `can_*` вычисляются с неправильной логикой
- Или эндпойнты возвращают 403 для accountant
- Или фронт не передаёт правильные флаги в компонент действий
- Или модал «Причина возврата» не вызывается

**Что нужно сделать:**

1. На бэке убедись что для каждой роли в зависимости от статуса возвращаются правильные can_*-флаги
2. На фронте кнопки рендерятся **только по флагам с бэка**, не по локальной проверке роли. Если бэк говорит «можно» — кнопка есть. Если «нельзя» — нет.
3. Возврат в draft и переоткрытие закрытого требуют обязательной причины через модал. Причина пишется в audit log.

**Тесты для добавления:**
- accountant видит can_close=True при pending_review
- accountant видит can_return=True при pending_review
- admin видит can_reopen=True при closed
- accountant видит can_reopen=False при closed (только admin)
- accountant с department=NULL: can_close=True напрямую из draft
- Возврат без причины (пустой reason) → 422
- После возврата статус draft + запись в audit_log с reason

## БАГ 3 — Страница «Задачи» для accountant (новая фича)

**Цель:** Дать accountant inbox-страницу со списком табелей которые ждут его действия. Не нужно лазить по отделам и искать «где что висит».

**Что нужно сделать:**

1. На бэке — новый эндпойнт который возвращает список всех периодов в статусах `pending_review` (требуют утверждения) и `closed` (для контекста, последние N). Только для admin и accountant.

   Для каждого периода в ответе включи:
   - Department id и название (или «Без отдела» для NULL)
   - Год, месяц
   - Статус
   - Кто отправил (full_name) и когда
   - Если закрыт — кто и когда закрыл
   - Сколько часов в периоде (агрегат по всем сотрудникам отдела) — для контекста, чтобы accountant понимал размер табеля

2. На фронте — новая страница (например `/tasks`). В sidebar добавь пункт «Задачи» в группу «Учёт» (сверху). Виден admin и accountant.

3. На странице:
   - Заголовок «Задачи на проверку»
   - Секция «Ждут утверждения» (статус pending_review): карточки/строки. На каждой — отдел, период «Май 2026», отправил «Иванов И.И. 28.05», часов «1240ч». Кнопка «Открыть табель» → переход на страницу табеля с предзаполненным фильтром на этот отдел и месяц.
   - Секция «Недавно закрытые» (последние 10): для контекста, можно свернуть.
   - Если ничего нет — пустое состояние «Все табели в работе или нет задач»

4. На дашборде accountant добавь карточку «На проверке: N» с переходом на эту страницу.

5. Открытие табеля по ссылке должно: переключить год/месяц, выбрать department в селекторе. Если в URL передан year/month/department_id — TimesheetPage должен это распарсить.

## БАГ 4 — Округление часов до целого

**Сейчас:** Можно вводить дробные часы (0.5, 1.5, 8.5). Это создаёт лишний разнобой с пересчётом.

**Должно быть:** Часы только целые. Минимум 0, максимум 24.

**Что нужно сделать:**

1. На бэке: тип `hours` в модели TimesheetEntry — целое число (Integer). В Pydantic-схеме — int, не Decimal.

2. **Создай миграцию Alembic** которая:
   - Сначала округлит существующие значения (UPDATE с ROUND)
   - Потом изменит тип колонки на INTEGER
   - На PostgreSQL: `ALTER TABLE timesheet_entries ALTER COLUMN hours TYPE integer USING ROUND(hours)::integer`
   - В Alembic-миграции через `op.alter_column(..., type_=Integer, postgresql_using='ROUND(hours)::integer')`

3. **Обязательно примени миграцию** через `alembic upgrade head`, проверь `alembic current` совпадает с head.

4. На фронте: в input для часов поменяй `step` на `1` (целые). При вводе 8.5 — браузер не даст ввести (или ввести можно, но валидация Pydantic вернёт 422).

5. В расчёте ЗП — все часы остаются целыми. Деньги (оклад, переработка) остаются Decimal — это копейки.

6. Обнови все тесты где использовались дробные часы — замени на целые.

**Тесты:**
- POST cell с hours=4.5 → 422
- После миграции существующее значение 4.5 в БД стало 5
- Расчёт ЗП работает на целых часах

## БАГ 5 — Сотрудники без отдела отображаются в общем табеле

**Сейчас:** Сотрудник с department_id=NULL виден в общей таблице вместе с обычными сотрудниками.

**Что нужно сделать:**

1. На фронте при `departmentFilter === null` группируй сотрудников по `department_id` (включая null как «Без отдела»).

4. Подзаголовок «Без отдела» — отдельная группа, в самом низу.
5. Если выбран конкретный отдел в фильтре — никаких разделителей, обычная таблица.

## Подводные камни

- **Миграция типа колонки `hours`**: PostgreSQL не позволяет менять тип `numeric` → `integer` напрямую. Используй USING-выражение с ROUND. Проверь что миграция применилась.
- **Тесты с дробными часами** — обнови все, иначе они упадут после смены типа.
- **Декомпиляция фронт-вью**: группировка по отделам — это перестройка структуры рендеринга таблицы. Будь аккуратен, не сломай существующие функции скролла и sticky-колонок.
- **URL-параметры**: TimesheetPage должен корректно парсить `?year=2026&month=5&department_id=3` и применять фильтр. Без этого «Открыть из Задач» не сработает.
