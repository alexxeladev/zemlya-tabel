## Сброс и тестовые данные (dev) — `app.cli`

> ⚠️ Только dev-БД. Перед сбросом сделать бэкап (CLAUDE.md → «Бэкапы БД»). Системный
> администратор (`is_system_admin=True`) НЕ удаляется ни при каких условиях.

```bash
cd backend

# Бэкап перед сбросом
mkdir -p ~/backups
docker exec -t $(docker ps -q -f ancestor=postgres:16) pg_dump -U tabel tabel \
  > ~/backups/before_reset_$(date +%s).sql

# Полная очистка (кроме системного админа). --yes пропускает подтверждение.
# Удаляет с учётом FK: audit log, табель, периоды, премии/KPI, удержания,
# проценты распределения, сотрудников, справочники, календари. Идемпотентна,
# печатает статистику удалённого.
python -m app.cli reset-data           # спросит подтверждение
python -m app.cli reset-data --yes     # без подтверждения

# Тестовые данные: 3 компании (zmo/kft/sec), 3 отдела (ИТО/Бухгалтерия/Охрана
# с головными компаниями),
# графики 5/2, 6/1 (weekday) и 2/2, 3/3 по две смены (cyclic, анкеры под фазы
# 1С на июнь 2026), производственный календарь на текущий год, 14 сотрудников
# с граничными случаями (фикс-ставка выходных, коэф 0, заём, без отдела,
# без графика, сменщик 2/2, СОВМЕСТИТЕЛЬ T-011 с двумя позициями «Инженер
# 60000 zmo» + «Электрик 30000 kft», ПОЧАСОВИК T-012 со ставкой 450 ₽/ч).
# Табель часами НЕ заполняется; единственная отметка — ОТПУСК сменщика T-010
# (2/2, 12 ч) на 14 календарных дней с 9-го числа текущего месяца: на нём сразу
# видно правило task_vacation_shift_fix (платятся только смены цикла × 12 ч).
# Идемпотентна.
python -m app.cli seed-test-data

# Демо-база «как в жизни» (task_demo_data): 6 юрлиц, 20 отделов (3–4 на юрлицо),
# 200 сотрудников и ЗАПОЛНЕННЫЙ табель с 1 января по сегодня (~29 тыс. ячеек,
# ~7 секунд). Для того, чтобы крутить систему живьём и мерить производительность.
python -m app.cli reset-data --yes && python -m app.cli seed-demo-data
python -m app.cli seed-demo-data --employees 50 --from 01.03.2026 --to 31.05.2026
```

### Демо-данные: `seed-demo-data` (task_demo_data)

Не путать с `seed-test-data`: тот заводит 14 сотрудников с ГРАНИЧНЫМИ случаями и **пустой** табель (функциональные проверки), этот — реалистичный объём с заполненным табелем. Генератор — `app/services/demo_data.py`.

- **Рабочие дни и длительность смены берутся только из `services.work_schedule`** (`planned_work_dates` / `shift_hours_for_date`). Не дублировать формулы графиков в генераторе: демо-табель обязан сходиться с расчётом ЗП и нормой.
- **Детерминированность**: `random.Random(SEED)`, `SEED = 20260813`. Повторный прогон на чистой базе даёт те же цифры — их можно сверять между запусками и после правок расчёта. Меняете распределения — цифры поедут, это нормально.
- **Взаимоисключение часы/код** соблюдается как в `upsert_cell`: отсутствия расставляются ПЕРВЫМИ, дни с ними пропускаются при заливке часов.
- Запись **bulk-ом** (`bulk_insert_mappings` / `bulk_save_objects`): 29 тыс. ячеек построчным ORM-insert-ом заняли бы минуты. Из-за этого audit log по демо-данным не пишется — это осознанно, генератор не имитирует действия пользователя.
- Что покрыто: три типа оплаты (~70% оклад / 15% посменно / 15% почасово), weekday и cyclic графики (включая 2/2 и 3/3 в две смены), ~12 совместителей со второй позицией в другом отделе и юрлице, фикс-ставка выходных у ~12%, займы, приём внутри периода и увольнения внутри периода, дни на два юрлица, переработки, выходы вне графика и в праздники, все четыре кода отсутствий, больничные **сверх годового лимита**, премии/KPI/аванс, все уровни каскада распределения (отдел → карточка → месячный override → авто по часам), незаполненные карточки без графика (KPI «не вошли в расчёт ФОТ»).
- **Статусы периодов вперемешку**: прошлые месяцы `closed`, предпоследний частично `pending_review`, текущий `draft` — чтобы работал весь workflow и «Задачи».
- QA-учётки те же, пароль `Test1234!`; `qa.manager@` и `qa.timekeeper@` привязаны к ОДНИМ И ТЕМ ЖЕ двум отделам — на них видно разницу в правах.
- Календарь года тянется с xmlcalendar.ru. **Без сети** команда печатает предупреждение и продолжает: норма weekday-графиков будет неверной, календарь нужно залить вручную.

QA-учётки (пароль у всех `Test1234!`): `qa.admin@` (admin), `qa.accountant@`
(accountant), `qa.manager@` (manager: числится в ИТО, **руководит ИТО и
Бухгалтерией** — проверка мульти-отдела), `qa.manager2@` (manager, отдел
Охрана — проверка изоляции чужого отдела), `qa.timekeeper@` (timekeeper,
**ведёт ИТО** — тот же отдел, что у `qa.manager@`: проверка, что руководитель
и табельщик отдела разные люди с разными правами), `qa.employee@` (employee) —
все на `@example.com`.
