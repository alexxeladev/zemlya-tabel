## Историчность расчёта: версии условий и снимок закрытого периода (task_stage3_historicity)

> **Историчность расчёта.** Условия труда позиции — ставка, оклад, тип оплаты,
> график, коэффициенты, распределение — действуют с даты. Расчёт берёт условия,
> действовавшие в рассчитываемый день, поэтому повышение оклада посреди месяца
> применяется с даты повышения, а не ко всему месяцу. Не версионируются: ФИО,
> табельный номер, доступ, отдел и компания позиции.
>
> **Хранятся они изменениями ПО ПОЛЮ** (ADR-001, раздел ниже): строка = поле ·
> дата · значение, и каждое условие меняется само по себе. Снимок всех полей в
> одной строке (`position_terms`) остался только как след перехода: он заставлял
> бэкенд угадывать, что именно правил человек, и стоил боевого дефекта.
>
> **Снимок закрытого периода.** При закрытии сохраняются суммы, распределение по
> юрлицам и использованные версии условий. Закрытая ведомость и выгрузка
> читаются из снимка и не пересчитываются. Переоткрытие аннулирует снимок,
> повторное закрытие создаёт новый; история снимков не ведётся. Корректировка
> закрытого периода запрещена — только через переоткрытие. Правка премий,
> аванса, займа и переопределений в закрытом периоде отклоняется на бэке.

### Решения заказчика (23.09.2026)

| вопрос | решение |
|---|---|
| корректировка закрытого периода | запрещена, только через переоткрытие |
| глубина историчности | версии условий с датами действия |
| уже закрытые периоды | снимки задним числом по текущим данным (после отчёта) |
| переоткрытие | аннулирует снимок, повторное закрытие — новый |
| дата изменения по умолчанию | **1-е число следующего месяца** |
| распределение по юрлицам на позиции | только с 1-го числа месяца, другие даты не даются |
| вахта | ставки поста/объекта/экипажа и оклад начальника НЕ версионируются (уже в строке месяца); **ставка налога** (с месяца) и **официальная зарплата охранника** (с даты) — версионируются |
| дата версии в закрытом месяце | отклоняется (409) |
| займ после закрытых месяцев | удержания закрытых месяцев — факт из снимка, новые условия раскладываются на открытые |
| «на проверке» | блокирует наравне с «закрыт» — и премии/аванс/займ/проценты/показатель, и дату версии |
| экран вахты и его Excel за закрытый месяц | из снимка: месяц и обе половины |

### Условия труда — изменения по ПОЛЮ (ADR-001, task_terms_per_field)

> **Условие меняется само по себе и со своей даты.** Строка = поле · дата ·
> значение (`position_term_changes`), условия дня — по каждому полю последнее
> изменение с `effective_from <= день`. Поэтому «то же 1.7, но с сентября» —
> обычное изменение, а не особый случай: на сентябрь у поля стоит другое
> значение. Правил распространения нет и не нужно.

**Почему переделано.** Версия была СНИМКОМ всех 14 полей. Из-за этого бэкенд
угадывал, какое поле имел в виду человек, сравнивая присланную форму с каким-то
снимком, а правило «поле действует с D и дальше» изображалось мутацией соседних
снимков. 27.09.2026 это дало боевой дефект на препроде: бухгалтер поменяла
коэффициенты, дата по умолчанию увела правку в следующий месяц, и вернуть её
штатно было нельзя ничем — карточка показывала уже нужное значение, и три
проверки подряд решали, что менять нечего. Цена — 64 отработанных выходных часа
по коэффициенту ×0. Починку «переносом правки» написали и откатили после трёх
ревью (каждое нашло дыру, двигающую деньги); разбор — в истории коммита
`3ae0868`.

- **Модель** `PositionTermChange` (`position_term_changes`, миграция
  `a9b8c7d6e5f4`): `position_id`, `field`, `effective_from`, `value` (JSON),
  автор и время; уникальность `(position_id, field, effective_from)`. Значение
  декодируется ПО ИМЕНИ ПОЛЯ (`TERM_FIELD_TYPES`) — одна форма строки на все
  условия. Деньги и коэффициенты хранятся строкой с двумя знаками, иначе
  `Decimal` ездил бы через float.
- **Базовые значения** заводятся при создании рабочего места: по строке на
  каждое поле с `TERMS_BEGINNING` (в интерфейсе «с начала»). Изменений у них
  нет, поэтому журнал ими не засыпается.
- **Чтение — `services/position_terms`**: `terms_on(position, day)` собирает
  значения полей (`TermsAtDate`), `month_segments` режет месяц по датам
  изменений НУЖНЫХ полей (`PAYROLL_FIELDS`; официальная зарплата общий расчёт не
  режет). Изменение, записанное тем же значением, месяц не режет — отрезки
  склеиваются сравнением значений. Истории нет вовсе (позиция вставлена мимо
  ORM) — читаются поля позиции, как и раньше.
- **График на дату** берётся объектом: `schedule_id` последнего изменения →
  зеркало позиции (обычный случай, запроса нет) → `session.get(Schedule, id)`
  под `no_autoflush` для исторического графика. Запрос идёт не больше раза на
  каждый РАЗНЫЙ график, а не на строку.
- **Поля на `EmployeePosition` — ЗЕРКАЛО ПОСЛЕДНЕГО значения каждого поля**
  (`sync_mirror`), их читают формы, маскирование, импорт и вахта. Правка
  прошлого зеркало не двигает. **Расчёт зеркало не читает.**
- **Два пути записи, и путать их нельзя:**
  - **явный список изменений** — `record_term_changes` / `POST
    /employees/{id}/positions/{pid}/terms`: группа полей + дата, бэкенд ничего
    не диффит и пишет ровно присланное. Им ходит карточка;
  - **через зеркало** — слушатель `before_flush` превращает расхождение зеркала
    с последним значением в изменение с датой `set_effective_from` (не задана —
    1-е число следующего месяца). Им ходят создание рабочего места и **форма
    вахты**. У него ОСТАЁТСЯ прежний дефект: значение, совпадающее с зеркалом,
    изменением не считается, и правку задним числом им не внести. Вахту
    переводит отдельная задача — до тех пор в системе два способа.
- **Общая правка условий не принимает вовсе**: `PATCH /employees/{id}` и
  `PATCH …/positions/{pid}` отвечают **422** с подсказкой «меняются кнопкой
  «Изменить»», если версионируемое поле реально РАСХОДИТСЯ с текущим
  (присутствие поля в запросе правкой не считается — форма шлёт их целиком).
  Проверка стоит ПОСЛЕ запрета вахты: у охранного места причина отказа — вахта.
- **Охранному месту новая точка входа отказывает БЕЗУСЛОВНО**
  (`ensure_position_owned_outside_vahta`), а не по расхождению значений: ставки
  у охранной позиции нет вовсе (её очистила миграция `a2b3c4d5e6f7`), поэтому
  проверка «а изменилось ли» не срабатывала бы ни разу, и через обычную карточку
  правились бы официальная зарплата охранника и налог вахты. Нашло ревью;
  держит `test_vahta_staff.py::TestDirectoryReadOnly::test_terms_endpoint_rejected`.
- **Группы условий — один список на систему** (`TERM_GROUPS` +
  `TERM_GROUP_LABELS`): тип оплаты и ставка · график · оплата вне графика ·
  оплата праздничных · коэффициент переработки · официальное трудоустройство.
  Поля внутри группы связаны и порознь бессмысленны, поэтому группа пишется
  ЦЕЛИКОМ — там же гасятся взаимоисключающие поля (база чужого типа оплаты,
  значение чужого вида оплаты). Второй копии правила нет: фронт получает группы
  с бэка, сверку держит `frontend/src/utils/positionTerms.test.ts`.
- **Карточка**: условия показываются группами ТОЛЬКО ДЛЯ ЧТЕНИЯ, у каждой
  «Изменить» → диалог со значениями и **обязательной датой** (по умолчанию —
  1-е число следующего месяца). У группы с запланированным изменением видно
  «с 01.12.2026 будет ×2» — именно этого не хватало 27.09.2026: карточка
  показывала будущее как настоящее. Подпись рабочего места в списке читается из
  условий НА СЕГОДНЯ, а не из зеркала, иначе на одном экране стояли бы разные
  числа. Свободный ввод остался только при СОЗДАНИИ места: истории у него ещё
  нет, всё «с начала».
- **История** — `GET …/terms`: строка на ПОЛЕ («Коэффициент выходных: ×1.5 с
  начала → ×1.5 с 01.09.2026 → ×2 с 01.10.2026»), правок и удалений в ней нет
  (решение заказчика). Ошибочное изменение не удаляется, а перекрывается новым с
  нужной датой.
- **Журнал изменений** (`reference_changes`): изменение условия пишется
  ПОПОЛЕВО и всегда с датой — «Оклад: 60 000 → 90 000 (с 15.05.2026)»
  (`queue_term_change`). Колонки-зеркала сняты с аудита: запись о зеркале
  дублировала бы изменение, ещё и без даты. Равенство значений записи не
  отменяет — то же значение с другой даты и есть изменение.
- **Дата изменения в месяце не-черновике — `ClosedPeriodError` → 409**; «с
  начала» у существующей позиции — только пока у отдела нет ни одного закрытого
  или проверяемого месяца (иначе это переписывание всей истории).
- **Старая таблица `position_terms` НЕ удалена**: пока переход не закончен, она
  остаётся снимком на случай отката. `downgrade` собирает снимки заново из
  изменений (правки, сделанные уже в новой модели, не теряются), но **пустые
  версии не восстанавливает** — снимок, ничем не отличавшийся от предыдущего, в
  пополевой модели не существует. На деве таких было 4 из 246: следы обхода
  дефекта, когда значение вводили «туда-обратно».
- **Проверено на дев-базе (27.09.2026)**: условия каждой позиции на 33 768
  пробных дат и отрезки всех месяцев 2025–2027 до и после миграции, ведомость
  всех позиций за 9 месяцев с часами (2 736 строк, 191 520 полей) — **0
  расхождений**. Миграция развернула 246 версий 234 позиций в 3 285 строк (3 276
  базовых + 9 настоящих изменений); upgrade → downgrade → upgrade возвращает те
  же условия. Сверка — одноразовые скрипты, в репозиторий не клались.
- **Живая проверка в браузере**: правка «то же ×1.5, но с 01.09.2026» вносится
  штатно, запланированное на октябрь ×2 при этом не двигается; в истории и
  журнале обе строки видны с датами.
- Тесты — `backend/tests/test_terms_per_field.py` (21: правка задним числом тем
  же значением, деньги дефекта — выходные часы ×0 → ×1.5, независимость групп и
  запланированного, отказ общей правки, две группы разными датами в один заход,
  закрытый и проверяемый месяц, взаимоисключающие поля, журнал),
  `backend/tests/test_stage3_historicity.py`, `frontend/src/utils/terms.test.ts`,
  `frontend/src/utils/positionTerms.test.ts`.

### Снимок — `services/period_snapshots.py`

- **Модель** `PeriodSnapshot` (`period_snapshots`, один на период): строки
  `/payroll` (`EmployeePayrollRead`), строки ведомости с распределением
  (`StatementRow`), строки кэша дашборда, `terms_used` (версии по отрезкам
  месяца), `loan_facts` (удержание займа по позиции), `guard_views` (экран
  вахты «0/1/2»). Всё — в том виде, в каком отдают экраны.
- **Создание** — `close_period` ДО смены статуса, в той же транзакции.
  **Аннулирование** — `reopen_period`. Других переходов в `closed` нет
  (кроме bulk-сида демо-данных — у них снимков нет, см. ниже).
- **Чтение — по наличию снимка, а не по статусу**: позиция, лежащая в снимке
  месяца, берётся оттуда во ВСЕХ точках — `build_payroll_summary` (табель,
  `/payroll`), `build_payroll_statement` (ведомость, Excel, заморозка переноса),
  дашборд (`substitute_dashboard_rows`), экран вахты (`guard_snapshot_view`,
  несколько охранных отделов склеиваются `_merge_views`). Живой расчёт для неё
  не делается вовсе — держит тест `test_snapshot_read_is_not_a_recompute`.
  Позиция, ушедшая после закрытия в другой отдел, в месяц дважды не попадёт.
- **Чтение закрытого месяца дешевле пересчёта**: полные строки грузятся только
  у снимков отделов запроса, у прочих — лёгкий `position_ids` (чтобы позиция,
  лежащая в снимке другого отдела, не посчиталась дважды). Первая версия грузила
  JSON всех снимков месяца и на одном отделе была МЕДЛЕННЕЕ живого расчёта
  (ИТО 35 → 39 мс) — нашёл замер. Сейчас, июнь 2026 дева, медиана из 9: вся
  компания 346 → 231 мс, ИТО 36 → 15 мс, охрана (120 мест) 65 → 46 мс, суммы
  совпадают до рубля.
- **Снимок и кэш дашборда.** `PeriodSnapshot` — в `_MONTH_KEYED`: создание и
  аннулирование поднимают версию месяца. При пересчёте кэша строки закрытых
  отделов берутся из снимка. Своего источника для закрытого месяца у кэша нет —
  разойтись им негде. `PositionTerms` и `GuardTaxRate` — в `_REFERENCE`.
- **Экран вахты из снимка — только тем, кто видит деньги**; табельщику — живой
  расчёт (в закрытом месяце меняться нечему, маскирование остаётся одним
  местом). Замок и `can_edit` считаются заново при каждом чтении.

### Запрет правок закрытого периода — `services/closed_periods.py`

- **Слушатель `before_flush`** проверяет каждую запись `EmployeeAdjustment`,
  `LoanDeduction`, `CompanyShareOverride`, `DepartmentQuantity`,
  `EmployeeCompanyShare` (по дате набора): месяц её отдела не-черновик →
  `ClosedPeriodError` → 409 (обработчик в `main.py`). Строка периода — под
  `FOR SHARE`, как у часов. Новый эндпойнт, пишущий те же данные, не забудет.
- **Core-DELETE мимо сессии** проверяется явно `ensure_month_open`: месячные
  проценты (`PUT`/`DELETE /timesheet/distribution`), показатель
  (`set_department_quantities`), набор процентов карточки.
- **Исключение** — `allow_closed_writes(db)`: заморозка раскладов при переносе
  отдела (этап 3 её не трогает).
- Часы, отсутствия, ночные и назначения вахты по-прежнему держит своя воронка.

### Займ

`loan_month_state` получает удержания закрытых месяцев из снимков
(`loan_facts`) как ручные правки: новые условия займа (сумма, срок) ложатся
только на открытые месяцы, остаток = сумма − фактически удержанное.

### Снимки для ранее закрытых периодов

`python -m app.cli backfill-snapshots [--out отчёт.csv]` — ОТЧЁТ: по каждому
закрытому периоду без снимка — мест, людей, начислено, к выплате, разнесено,
остаток, налог вахты, «не посчитано», отрицательные выплаты. В базе ничего не
меняется. `--apply` — запись (необратимо в смысле «закрытые месяцы перестают
следовать за справочниками»), только после подтверждения заказчиком.
`seed-demo-data` закрывает периоды bulk-ом мимо `close_period`, снимков не
делает — после пересева дев-базы прогнать `backfill-snapshots --apply`.
