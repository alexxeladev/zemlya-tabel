## Историчность расчёта: версии условий и снимок закрытого периода (task_stage3_historicity)

> **Историчность расчёта.** Условия труда позиции — ставка, оклад, тип оплаты,
> график, коэффициенты, распределение — хранятся версиями с датами действия.
> Расчёт берёт версию, действовавшую в рассчитываемый день, поэтому повышение
> оклада посреди месяца применяется с даты повышения, а не ко всему месяцу. Не
> версионируются: ФИО, табельный номер, доступ, отдел и компания позиции.
>
> **Снимок закрытого периода.** При закрытии сохраняются суммы, распределение по
> юрлицам и использованные версии условий. Закрытая ведомость и выгрузка
> читаются из снимка и не пересчитываются. Переоткрытие аннулирует снимок,
> повторное закрытие создаёт новый; история снимков не ведётся. Корректировка
> закрытого периода запрещена — только через переоткрытие. Правка премий,
> аванса, займа и переопределений в закрытом периоде отклоняется на бэке.

### Решения заказчика (23.09.2026)

| вопрос | решение |
|---|---|
| корректировка закрытого периода | запрещена, только через переоткрытие |
| глубина историчности | версии условий с датами действия |
| уже закрытые периоды | снимки задним числом по текущим данным (после отчёта) |
| переоткрытие | аннулирует снимок, повторное закрытие — новый |
| дата изменения по умолчанию | **1-е число следующего месяца** |
| распределение по юрлицам на позиции | только с 1-го числа месяца, другие даты не даются |
| вахта | ставки поста/объекта/экипажа и оклад начальника НЕ версионируются (уже в строке месяца); **ставка налога** (с месяца) и **официальная зарплата охранника** (с даты) — версионируются |
| дата версии в закрытом месяце | отклоняется (409) |
| займ после закрытых месяцев | удержания закрытых месяцев — факт из снимка, новые условия раскладываются на открытые |
| «на проверке» | блокирует наравне с «закрыт» — и премии/аванс/займ/проценты/показатель, и дату версии |
| экран вахты и его Excel за закрытый месяц | из снимка: месяц и обе половины |

### Версии условий — `services/position_terms.py`

- **Модель** `PositionTerms` (`position_terms`, миграция `c5d6e7f8a9b0`):
  `position_id`, `effective_from` (ВКЛЮЧИТЕЛЬНО; действует до дня перед
  следующей версией), поля `TERM_FIELDS` — тип оплаты и база, график,
  коэффициенты выходных/праздничных/переработки, `is_official` +
  `official_salary`. Первая версия — с `TERMS_BEGINNING` (1900-01-01, в
  интерфейсе «с начала»): миграция перенесла в неё значения полей позиции.
- **Поля на `EmployeePosition` — ЗЕРКАЛО ПОСЛЕДНЕЙ версии**, их читают формы,
  маскирование, импорт, вахта. **Расчёт зеркало не читает** — только
  `terms_on` / `month_segments`. Держать оба — осознанно: переписывать ~40 мест,
  читающих `position.rate`, значило бы менять код вне задачи.
- **Версии никто не создаёт руками.** Код меняет поля позиции как раньше, а
  слушатель `before_flush` превращает расхождение зеркала с последней версией в
  версию с датой `set_effective_from(position, d)` (API: поле
  `terms_effective_from` в `PATCH /employees/{id}`, `PATCH …/positions/{pid}`,
  `PATCH /vahta/staff/{pid}`); не задана — `default_effective_from()`.
  Новая позиция получает версию «с начала» сама.
- **Поле, изменённое с даты D, действует с D и дальше — до первой более
  поздней версии, где оно задано ИНАЧЕ**: версии с прежним значением получают
  новое (иначе повышение «с 15-го» откатилось бы на версии, заведённой ради
  другого поля), а явно запланированное позже изменение не затирается
  (тест `test_earlier_change_keeps_planned_later_change`: 100 000 с 1.11, потом
  90 000 с 15.10 → ноябрь остаётся 100 000; нашло ревью). Зеркало = последняя
  версия.
- **Дата версии в месяце не-черновике — `ClosedPeriodError` → 409**; «с начала»
  у существующей позиции — только пока у отдела нет ни одного закрытого или
  проверяемого месяца (иначе это переписывание всей истории).
- **Расчёт месяца по отрезкам** (`calculate_position_payroll` →
  `_calculate_segment` × N → `_merge_segments`): каждый отрезок с неизменными
  условиями считается ПРЕЖНЕЙ формулой — его часы, его отсутствия, месячная
  норма его графика; суммы складываются. Ставка, график, тип оплаты и норма в
  строке — последнего отрезка. Лимит больничного расходуется сквозь отрезки,
  ночные начисляются один раз. Месяц с одной версией — один отрезок и тот же
  результат до копейки. Соседние версии, различающиеся только официальной
  зарплатой, общий расчёт не режут (`PAYROLL_FIELDS`).
- **Пример (держит тест `test_mid_month_raise_is_paid_from_its_date`)**: оклад
  60 000 → 90 000 с 15 мая 2026, 5/2, норма 160 ч, отработан весь месяц:
  1–14 мая 72 ч × 60 000/160 + 15–31 мая 88 ч × 90 000/160 = 27 000 + 49 500 =
  **76 500 ₽** (до этапа 3 — 90 000 ₽).
- **Кто ещё читает условия по дате**: Т-13 (категории дней — график на каждый
  день, норма — графика на конец месяца), автозаполнение (плановые дни — график
  своего отрезка), лимит больничного (`DatedSchedule` основной позиции на дату
  каждого Б), коэффициенты в «Коэф.» ведомости — версия на конец месяца, вахта
  (`official_month_payouts` по отрезкам официальной зарплаты). Новое место,
  которому нужна ставка или график для денег, — только через `terms_on` /
  `month_segments`, не через поля позиции.
- **Не версионируются** (решение заказчика или закрыто снимком): ФИО, таб. №,
  доступ, отдел и компания позиции; дефолт процентов отдела; фонд ночных смен;
  определение самого графика; производственный календарь; проценты объекта и
  экипажа вахты; поля займа. Все они по-прежнему двигают ОТКРЫТЫЕ месяцы задним
  числом — закрытые защищает снимок.
- **Распределение позиции** — `employee_company_shares.effective_from` (1-е
  число): набор = строки позиции с одной датой, действует набор с наибольшей
  датой не позже 1-го числа месяца (`load_employee_shares(…, year, month)`).
  «Снять с месяца» при заданном раньше наборе — набор нулевых долей.
  `PUT /employees/{id}/company-shares` переписывает только набор СВОЕЙ даты.
- **Налог вахты** — `GuardTaxRate` (`guard_tax_rates`, с 1-го числа);
  `employer_tax_percent(db, year, month)`. `guard_settings` — зеркало
  последней ставки.
- **История в карточке**: `GET /employees/{id}/positions/{pid}/terms`
  (финансовые роли), кнопка «История условий» в `PositionsEditor`; поле «С
  какой даты действуют новые условия» появляется, только если форма меняет
  условия. Зеркало даты по умолчанию — `frontend/src/utils/terms.ts`.

### Снимок — `services/period_snapshots.py`

- **Модель** `PeriodSnapshot` (`period_snapshots`, один на период): строки
  `/payroll` (`EmployeePayrollRead`), строки ведомости с распределением
  (`StatementRow`), строки кэша дашборда, `terms_used` (версии по отрезкам
  месяца), `loan_facts` (удержание займа по позиции), `guard_views` (экран
  вахты «0/1/2»). Всё — в том виде, в каком отдают экраны.
- **Создание** — `close_period` ДО смены статуса, в той же транзакции.
  **Аннулирование** — `reopen_period`. Других переходов в `closed` нет
  (кроме bulk-сида демо-данных — у них снимков нет, см. ниже).
- **Чтение — по наличию снимка, а не по статусу**: позиция, лежащая в снимке
  месяца, берётся оттуда во ВСЕХ точках — `build_payroll_summary` (табель,
  `/payroll`), `build_payroll_statement` (ведомость, Excel, заморозка переноса),
  дашборд (`substitute_dashboard_rows`), экран вахты (`guard_snapshot_view`,
  несколько охранных отделов склеиваются `_merge_views`). Живой расчёт для неё
  не делается вовсе — держит тест `test_snapshot_read_is_not_a_recompute`.
  Позиция, ушедшая после закрытия в другой отдел, в месяц дважды не попадёт.
- **Чтение закрытого месяца дешевле пересчёта**: полные строки грузятся только
  у снимков отделов запроса, у прочих — лёгкий `position_ids` (чтобы позиция,
  лежащая в снимке другого отдела, не посчиталась дважды). Первая версия грузила
  JSON всех снимков месяца и на одном отделе была МЕДЛЕННЕЕ живого расчёта
  (ИТО 35 → 39 мс) — нашёл замер. Сейчас, июнь 2026 дева, медиана из 9: вся
  компания 346 → 231 мс, ИТО 36 → 15 мс, охрана (120 мест) 65 → 46 мс, суммы
  совпадают до рубля.
- **Снимок и кэш дашборда.** `PeriodSnapshot` — в `_MONTH_KEYED`: создание и
  аннулирование поднимают версию месяца. При пересчёте кэша строки закрытых
  отделов берутся из снимка. Своего источника для закрытого месяца у кэша нет —
  разойтись им негде. `PositionTerms` и `GuardTaxRate` — в `_REFERENCE`.
- **Экран вахты из снимка — только тем, кто видит деньги**; табельщику — живой
  расчёт (в закрытом месяце меняться нечему, маскирование остаётся одним
  местом). Замок и `can_edit` считаются заново при каждом чтении.

### Запрет правок закрытого периода — `services/closed_periods.py`

- **Слушатель `before_flush`** проверяет каждую запись `EmployeeAdjustment`,
  `LoanDeduction`, `CompanyShareOverride`, `DepartmentQuantity`,
  `EmployeeCompanyShare` (по дате набора): месяц её отдела не-черновик →
  `ClosedPeriodError` → 409 (обработчик в `main.py`). Строка периода — под
  `FOR SHARE`, как у часов. Новый эндпойнт, пишущий те же данные, не забудет.
- **Core-DELETE мимо сессии** проверяется явно `ensure_month_open`: месячные
  проценты (`PUT`/`DELETE /timesheet/distribution`), показатель
  (`set_department_quantities`), набор процентов карточки.
- **Исключение** — `allow_closed_writes(db)`: заморозка раскладов при переносе
  отдела (этап 3 её не трогает).
- Часы, отсутствия, ночные и назначения вахты по-прежнему держит своя воронка.

### Займ

`loan_month_state` получает удержания закрытых месяцев из снимков
(`loan_facts`) как ручные правки: новые условия займа (сумма, срок) ложатся
только на открытые месяцы, остаток = сумма − фактически удержанное.

### Снимки для ранее закрытых периодов

`python -m app.cli backfill-snapshots [--out отчёт.csv]` — ОТЧЁТ: по каждому
закрытому периоду без снимка — мест, людей, начислено, к выплате, разнесено,
остаток, налог вахты, «не посчитано», отрицательные выплаты. В базе ничего не
меняется. `--apply` — запись (необратимо в смысле «закрытые месяцы перестают
следовать за справочниками»), только после подтверждения заказчиком.
`seed-demo-data` закрывает периоды bulk-ом мимо `close_period`, снимков не
делает — после пересева дев-базы прогнать `backfill-snapshots --apply`.
