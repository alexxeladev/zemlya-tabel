## Dashboard

- Один комбинированный эндпойнт: `GET /api/dashboard/{year}/{month}` — часы, ФОТ (по отделам и юрлицам), статусы периодов, динамика за 6 месяцев. Видимость шьётся в сервисе по роли actor-а: admin/accountant — вся компания, manager — свой отдел (принудительно), employee — только свои часы (`payroll=None`, `periods=None`).
- **Диапазон месяцев** (task_ux_improvements ч.2): `?to_year=&to_month=` — конец периода включительно, `(year, month)` при этом начало. Параметры задаются только парой (иначе 422), конец раньше начала — 422, длиннее `MAX_RANGE_MONTHS` = **12 месяцев** — 422. Без них ответ прежний: `to_*` совпадают с началом, `months_count=1`.
  - Все показатели — **сумма по месяцам** диапазона (часы, норма, ФОТ, эффект округления). Каждый месяц считается ОТДЕЛЬНО и потом складывается: норма, лимит больничного и статусы периодов — месячные, «растянуть» расчёт на диапазон нельзя.
  - `non_calculable_employees` считает **разные рабочие места**, а не строки расчёта: иначе сотрудник без графика удваивался бы с каждым месяцем.
  - Статусы периодов — строка на **(отдел, месяц)**; свернув диапазон в строку на отдел, потеряли бы, какой именно месяц не закрыт. Просрочка считается от НАЧАЛА диапазона.
  - Динамика диапазона — по его же месяцам (одиночный месяц по-прежнему тянет хвост `TREND_MONTHS` = 6 назад). Уже посчитанные месяцы переиспользуются, второй раз не считаются.
  - **Цена запроса линейна по месяцам**: на демо-базе (200 сотрудников) месяц ≈ 1,7 с, квартал ≈ 4,6 с, год ≈ 18 с. Отсюда потолок в 12 месяцев; фронт длиннее и не даёт выбрать. Если понадобится год «мгновенно» — кэш/матвью помесячных итогов, а не расширение потолка.
- Фронт: переключатель периода в шапке — два `<input type="month">` (начало/конец), стрелки двигают окно ЦЕЛИКОМ сохраняя длину, пресеты «Месяц/Квартал/Год». Выбранный период сохраняется (`tabel.dashboard.period`).
- **Вахта входит в ФОТ дашборда** (task_stage1 п.1.2): позиция с назначением на пост считается модулем вахты — той же веткой `load_guard_rows`, что в `build_payroll_summary`. До правки дашборд терял весь ФОТ охраны (август: 8,69 млн вместо 13,57 млн). **Часы вахты в блок «Часы» НЕ входят** (круглосуточные, задавили бы остальных), в разрезе юрлиц зарплата вахты делится **по процентам места работы** — оба решения заказчика. Подробности и таблица «где считается ФОТ» — `.claude/rules/vahta-integration.md` → «Врезка в дашборд». Добавляя новое место, где складывается ФОТ, — звать `load_guard_rows` или считать через `build_payroll_summary`.
- Сервис `app/services/dashboard.py` агрегирует **поверх** `calculate_employee_payroll` и `visible_employees_for_actor` — формулы ЗП и правила видимости НЕ дублировать. Тест сверяет ФОТ дашборда с `/api/timesheet/{y}/{m}/payroll` — цифры обязаны совпадать.
- «Просрочено» = существующий период прошлых месяцев в статусе ≠ closed **у отдела, где в том месяце есть сотрудники** (см. следующий пункт). Ограничение: lazy-создание периодов — месяц, который никто не открывал, в просрочку не попадёт.
- **Отдел без сотрудников в workflow периодов не участвует ВООБЩЕ** (task_dashboard_empty_depts): ни строкой в списке, ни просрочкой, ни в счётчиках. Раньше список строился из `departments` и `timesheet_periods`, а есть ли в отделе люди, никто не спрашивал — отдел, опустевший после увольнений или деактивации рабочих мест, навсегда висел «Черновик · просрочен», хотя закрывать в нём нечего. Псевдо-отдел **«Без отдела»** проверялся только в строках текущего месяца (и без учёта месяца), поэтому в просрочке вылезал всё равно.
  - Правило — `departments_with_employees(rows, year, month)` в `app/services/positions.py` (там же, где остальные фильтры «сотрудники такого-то отдела»). Совпадает с видимостью табеля (`visible_employees_for_actor`): несистемный сотрудник, активный **или уволенный не раньше начала месяца**. Отличие одно: рабочее место должно быть **активным** — строку в табеле даёт `visible_positions`, и отдел, где все позиции деактивированы, показывать нечем.
  - Занятость СВОЯ У КАЖДОГО МЕСЯЦА (увольнения), поэтому проверяется по месяцам — и для строк диапазона, и для каждого просроченного периода отдельно.
  - Снимок занятости берётся **одним запросом на весь ответ** (`department_employment_rows`), а не запросом на месяц: месяцев в дашборде столько, сколько строк в диапазоне и в просрочке, а от месяца тут зависит только сравнение с датой увольнения.
  - **Периоды пустым отделам и не создаются**: `_build_periods_for_response` заводит их по `department_ids_of` ВИДИМЫХ сотрудников, `upsert_cell` — по отделу позиции. Пустые периоды в базе — наследство: отдел опустел уже после того, как период завели. Тест это фиксирует.
  - «Задачи» (`list_review_tasks`) намеренно НЕ фильтруются: там лежат периоды, которые кто-то осознанно отправил на проверку, и бухгалтеру всё равно надо их закрыть.
- **Блок «Статусы периодов» на дашборде — это ТОЛЬКО счётчики** (task_dashboard_empty_depts). Таблица строк «отдел / период / статус / открыть табель» снята: при двух десятках отделов она разрасталась на пол-экрана красных «просрочен» и к цифрам ничего не добавляла. Списком периодов остаются «Задачи» (там по ним ещё и действуют) и сам табель. Поля `rows` / `overdue_rows` бэк по-прежнему отдаёт — из них считаются счётчики, и по ним же написаны тесты; фронт их не читает.
- KPI **«Всего отделов»** (`PeriodCountsRead.departments`) — сводка по выбранному периоду рядом с «Закрыто / На проверке / В черновике / Просрочено». Считаются **РАЗНЫЕ отделы**: в диапазоне у отдела строка на каждый месяц, но отдел один; для одного месяца это ровно `closed + pending_review + draft`. Видимость обычная: manager и timekeeper — только свои отделы, admin/accountant — все.
- KPI `non_calculable_employees` — сколько сотрудников не вошло в расчёт ФОТ (нет оклада/графика, сменный график); фронт показывает предупреждение.
- KPI **«Эффект округления»** (`PayrollTotalsRead.rounding_effect`, task_payout_rounding) — Σ хвостов округления «К выплате» до 1000 ₽ за период. **Знак любой**: плюс — за период осело в пользу компании, минус — компания доплатила; хвосты разных знаков складываются как числа, а не по модулю, и итог вполне может выйти отрицательным. Подпись и цвет карточки на дашборде идут за знаком — одно «Эффект округления» без направления ни о чём не говорит. Считается `_rounding_effect` через `build_payroll_summary` (премий/удержаний в ФОТ дашборда нет, из `calculate_employee_payroll` «к выплате» не получить) — цифра обязана совпадать с `total_rounding_tail` в `/payroll`, тест это сверяет. Живёт в блоке ФОТ, поэтому видимость та же: admin/accountant — все, manager — свой отдел, employee — `payroll=None`.
- Фронт: `DashboardPage` (recharts: BarChart/PieChart/LineChart, всё в ResponsiveContainer), данные одним запросом через `api/dashboard.ts`. Клик по отделу (строка статусов / столбец часов) → `/timesheet?year=&month=&department_id=`. Динамика при <2 точках — заглушка «Недостаточно данных».

### Кэш помесячных итогов (task_perf п.6.2)

> Дашборд считал ЗП всей компании заново при каждом открытии: на дев-базе
> (300 рабочих мест, 6 месяцев динамики) **4,6 с**, из них SQL 0,6 с — остальное
> чистый Python (`calculate_position_payroll` × 2616). Теперь итоги месяца лежат
> в таблице и пересчитываются только когда данные месяца или справочник
> изменились: открытие **4,6 → 0,27 с** на попадании (та же база, та же
> методика — in-process `TestClient`, медиана из 7).

- **Две таблицы** (миграция `b6c7d8e9f0a1`, модели `models/dashboard_cache.py`):
  `dashboard_month_cache` — одна строка на (год, месяц), JSON-список итогов по
  КАЖДОМУ рабочему месту (часы, норма, суммы по категориям, разрез по юрлицам,
  `is_calculable`, плюс хвост округления «к выплате» и нераспределённый остаток
  из ведомости); `data_versions` — счётчики `month:YYYY-MM` и `reference`.
  Строка кэша действительна, пока совпадают ОБЕ версии, на которых считалась.
- **Кэш хранит ВСЕХ, видимость режется при чтении** (`restore_results`):
  менеджер и табельщик — по отделам позиций (`accessible_department_ids`),
  сотрудник — только свои строки, admin/accountant — всё. Промах у менеджера
  считает всю компанию (область admin через `SimpleNamespace`, а не транзиентный
  `Employee`, чтобы не утёк в сессию) — строка кэша общая. Цифры на попадании
  обязаны совпадать с живым расчётом, это держат тесты сверки с `/payroll`.
- **Что обесценивает кэш — решает ОДНО место: `services/dashboard_cache.py`**,
  слушатели сессии, а не вызовы из обработчиков (иначе первый новый эндпойнт
  забыл бы, и руководство видело бы вчерашние цифры). Модели с датой/месяцем
  (`_MONTH_KEYED`: часы, отсутствия, ночные, премии, займ, override, вахта,
  периоды, показатели) бьют по СВОЕМУ месяцу; справочные (`_REFERENCE`:
  сотрудник, позиция, отдел, юрлицо, график, календарь, доли, справочник вахты)
  — по всем. **Новая модель, влияющая на расчёт, обязана попасть в один из двух
  списков.** Сдвиг даты у записи (старый месяц тоже поехал) — бьёт по справочнику.
- **Версия поднимается ПОСЛЕ коммита, отдельным соединением** (`after_flush`
  только запоминает ключи в `Session.info`, `after_commit` делает UPSERT). Внутри
  транзакции нельзя: UPDATE строки `data_versions` держал бы её до коммита, и два
  табельщика одного месяца в разных отделах встали бы друг за другом — PG-тест
  `test_concurrent_writers_do_not_block_each_other` это поймал. Порядок «данные →
  версия» гарантирует, что старые данные под новой версией в кэш не попадут;
  новые под старой — попадут и будут отброшены следующей проверкой. Откат
  транзакции ключи выбрасывает. Цена — **+1 SQL-запрос на пишущий запрос**.
- **Правки МИМО ORM слушатель не видит**: bulk-сиды, Alembic, SQL руками.
  Поэтому `reset-data` чистит обе таблицы, `seed-demo-data` в конце зовёт
  `drop_cache`, а после ручного SQL по данным месяца надо либо
  `update data_versions set version = version + 1 where key = 'month:YYYY-MM'`,
  либо стереть `dashboard_month_cache`. **На старте приложения кэш стирается**
  (`lifespan`): процесс, убитый между коммитом данных и подъёмом версии
  (рестарт на деплое), иначе оставил бы месяц устаревшим навсегда.
- Запись — UPSERT по (год, месяц), а не select+insert: два дашборда на промахе
  считают месяц оба, второй INSERT упёрся бы в unique. `store_month` коммитит
  сам — дашборд свою транзакцию не открывает.
- **Промах стоит дороже, чем раньше**: к расчёту добавилась ведомость всей
  компании ради двух показателей округления (~+1 с). Правка часов в текущем
  месяце обесценивает только его — прошлые месяцы динамики остаются в кэше.
- Тесты — `backend/tests/test_dashboard_cache.py`.
