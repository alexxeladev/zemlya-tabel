# CLAUDE.md — zemlya-tabel

## Что это за проект

Система учёта рабочего времени для девелоперской группы «Земля МО».
- Несколько юрлиц; зарплата сотрудника распределяется между ними.
- Ролевая модель: Admin, Manager, Accountant, Timekeeper (табельщик), Employee.
- Workflow периода: Draft → Pending Review → Closed.
- После Closed правки только Admin с обязательным комментарием и audit log.

## Структура

Раскладка каталогов выводится из самого репозитория (`ls`, граф graphify). Здесь —
только то, чего по дереву не видно:

- **Отдельной таблицы `users` НЕТ**: auth-поля (email, role, пароль) лежат в `Employee`.
- `models/employees.py` — compat-аксессоры (`emp.rate`, `emp.department_id`, …) читают
  и пишут ОСНОВНУЮ ПОЗИЦИЮ, а не сам `Employee`. Дублирующих колонок нет намеренно.
- `services/org_access.py` — единственный источник правды о доступе к отделам.
- `services/work_schedule.py` — единственный источник правды о рабочих днях и норме.
- `services/payroll.py` — `calculate_position_payroll` чистая функция, в БД не ходит.
- `services/dashboard.py` — агрегация ПОВЕРХ payroll, формулы расчёта НЕ дублирует.
- `services/distribution.py` — единственное место округления распределения.
- `frontend/src/utils/colors.ts` — палитра юрлиц общая для чипов табеля и дашборда.

## Конвенции

### Таблицы
- Имена: snake_case, **множественное число** (`employees`, `departments`, `timesheet_entries`)

### Pydantic-схемы
Три схемы на каждую сущность:
- `XxxBase` — общие поля
- `XxxCreate(XxxBase)` — поля для создания (пароль, foreign keys)
- `XxxRead(XxxBase)` — поля для чтения (id, created_at, вложенные объекты), `from_attributes=True`

### Миграции
- **Только через Alembic**, никогда `Base.metadata.create_all()` в проде.
- `alembic revision --autogenerate -m "короткое описание"` — создать миграцию.
- Коммитить файл миграции вместе с изменениями модели.
- В `alembic/env.py` — `import app.models` чтобы все модели были зарегистрированы в metadata.

### Soft delete
Пользователи (и другие сущности с FK из audit_log) **никогда не удаляются физически** — `is_active=False`.

### Audit log
- Вызывать `log_action(...)` из `app.core.audit` при каждом CRUD и смене статуса.
- `log_action` делает `db.add()` — коммит вызывается снаружи вместе с основным изменением.
- **Это ОПЕРАЦИОННЫЙ журнал** (часы, отсутствия, ночные, периоды, экспорты), снимками `before`/`after`. Изменения СПРАВОЧНИКОВ пишет отдельный, пополевой журнал — см. «Журнал изменений справочных данных».

### Роутеры
- Регистрировать в `app/main.py` через `app.include_router(...)`.
- Префикс `/api/...` (не `/api/v1` — версионирование добавим позже при необходимости).

## Производственный календарь

- **Источник:** xmlcalendar.ru — `https://xmlcalendar.ru/data/ru/{year}/calendar.json`
- **Формула нормы:** `Норма = workdays × hours_per_shift − short_days`
- Все вычисления норм — только через `app.services.calendar`, не дублировать формулу в роутерах.
- В тестах **обязательно мокать** `app.services.calendar.fetch_calendar_from_remote` через `monkeypatch` — никаких реальных сетевых запросов.
- Тип дня в строке `days`: обычное число → выходной/праздник, `N+` → праздничный (тоже нерабочий), `N*` → сокращённый рабочий.

## Вахта: табель охраны на постах (task_vahta)

Отдельный модуль учёта охраны: зоны обслуживания → объекты → посты → люди плюс
выездные экипажи ГБР. **Подробности — `.claude/rules/vahta*.md`** (загружаются всегда).

> **Штат охраны ведётся из вахты** (task_guard_ownership): рабочее место в
> охранном подразделении общий справочник НЕ правит — отказ 403 на бэке во всех
> точках входа (`services/guard_staff.py`, единственный предикат «охранная
> позиция»). Поля человека (ФИО, таб. №, доступ, даты в компании) — справочник,
> как у всех. Добавляя новый эндпойнт правки позиции — спросить этот предикат.
>
> **Должности охраны — справочник `guard_job_titles`**, не константа: от должности
> расчёту нужен только `pay_type` (`per_shift` / `salary`). Ведётся во вкладке
> «Должности» настроек вахты; см. `.claude/rules/vahta.md` → «Справочник должностей».
>
> **Общий ввод на охранную позицию закрыт**: часы, премии/KPI/аванс и заём для неё
> отклоняются на бэке (403, «ведутся в модуле „Вахта“») — один предикат
> `guard_staff.ensure_no_guard_accrual`. Снятие уже введённого разрешено всегда.
> Добавляя эндпойнт, который пишет начисление на позицию, — спросить этот предикат.
>
> Три правила вахты НЕ совпадают с основной системой, и путать их нельзя:
> база распределения по юрлицам включает премию **и налог на официальную часть
> выплаты**; «к выплате» округляется **вверх до 500 ₽ по каждой половине**, а
> начисления и распределение не округляются вовсе; проценты берутся от МЕСТА
> РАБОТЫ, а не от человека (каскад и количественный показатель к вахте не применяются вовсе).

## Правила интерфейса (чтобы не объяснять их каждый раз)

Проверять ПЕРЕД тем, как показывать экран пользователю. Всё ниже — из реальных
замечаний по ходу работы, а не из общих соображений.

- **Пользователь не знает внутренних id.** Поля «введите id сотрудника/отдела/
  компании» не существует. Выбор — по имени: ФИО, название, табельный номер.
  Id можно показывать рядом справочно (`Иванов (T-0042)`), но не требовать.
- **Список длиннее ~20 значений — с поиском**, а не голая выпадашка: 200 имён
  колесом не листают. Меньше 20 — обычный `<select>` нормально.
- **Не показывать сырое техническое значение там, где есть человеческое**:
  вместо `#44` — «ООО «Комфорт» (#44)», вместо `weekend_coefficient` —
  «Коэффициент выходных», вместо `bulk` — «Массовая операция». Словари подписей
  держать на бэке (иначе фронт заводит вторую копию и они разъезжаются).
- **Пусто и «не задано» — разные вещи.** Пустая ячейка читается как «данных
  нет»; если значение сняли — писать словом («не задано», «снято»).
- **Экран, который может вырасти, — постраничный.** Журналы, ленты, истории.
  «Загрузить всё и отфильтровать на клиенте» годится только там, где объём
  ограничен по существу (месяц табеля одного отдела).
- **Фильтр меняется — сбрасывать страницу на первую.** Иначе offset от прошлой
  выдачи показывает пустой экран, и это выглядит как поломка.
- **Проверять экран глазами, а не только ассертами.** Скриншот или живой заход
  до того, как сказать «готово»: ассерт «поле присутствует» не отличает удобное
  поле от бесполезного.

## Работа с графом кода (graphify)

Задачи пишутся без имён функций намеренно (п.2 «Стандарта выполнения задачи»):
точки входа ищутся здесь.

Перед тем как искать по файлам грепом или читать их подряд — **спроси граф**:

```bash
graphify query "<вопрос>"        # обход графа от узлов, похожих на вопрос
graphify path "A" "B"            # кратчайший путь между двумя сущностями
graphify explain "<имя>"         # что это за узел и с чем связан
graphify update .                # переизвлечь изменившийся код (без LLM)
```

**Обязательно через граф, а не грепом:**

- **«найди все места, где …»** — грепом легко пропустить копию правила в другом
  слое. В этом проекте таких копий много и они намеренные: `distribution.py` ↔
  `utils/distribution.ts`, `overtime.ts` ↔ `build_payroll_statement`,
  `utils/departments.ts` ↔ фильтр юрлица бэка. Забыть одну из пары — обычный
  способ уронить сходимость экрана с ведомостью.
- **«что сломается, если поменять X»** — `graphify path` показывает связи, а не
  совпадения по строке.
- **перед правкой общего механизма** (распределение, каскад, расчёт, права) —
  проверить, нет ли второй копии правила на другом экране.

Граф покрывает **только код и документы репозитория**. Историю изменений и «после
какого коммита сломалось» по-прежнему смотреть в git — этого в графе нет.

### Состояние на этой машине

- Пакет `graphifyy` стоит в отдельном окружении `~/.local/share/graphify-venv`,
  CLI — `~/.local/bin/graphify`. В зависимости проекта он НЕ входит: это
  инструмент разработчика, а не часть системы.
- Граф собран по всему репозиторию (код через AST + документы семантикой), лежит в `graphify-out/`.
- **`graphify-out/` в `.gitignore`**: 22 МБ на прогон (`graph.json` 8,6 МБ +
  `graph.html` 6,8 МБ). Граф — производная от кода, каждый пересбор давал бы
  новый многомегабайтный блоб в истории. Поэтому после `git pull` или `merge`
  его надо обновлять локально: `graphify update .`
- **Git-хуки установлены** (`post-commit`, `post-checkout`): после коммита и
  после смены ветки граф пересобирается сам. Пересборка идёт **в фоне** —
  `git commit` не ждёт её; лог в `~/.cache/graphify-rebuild.log`, полный прогон
  по этому репозиторию ~6 с. Во время rebase, merge и cherry-pick хук
  осознанно молчит, чтобы не мешать `--continue`. Отключить разово —
  `GRAPHIFY_SKIP_HOOK=1 git commit …`, снять совсем — `graphify hook uninstall`.
- **Правила проекта лежат в `CLAUDE.md` И в `.claude/rules/*.md`** — после их
  правки граф про них устаревает так же, как про этот файл.
- **Хуки обновляют ТОЛЬКО код.** Правки `CLAUDE.md` и прочих документов в граф
  сами не попадут: семантическая часть требует LLM и запускается только из
  `/graphify . --update`. Поэтому после заметных правок этого файла граф про
  него устаревает — а он в графе самый нагруженный источник.
- **Merge-драйвер для `graph.json` не используется.** `graphify hook install`
  заводит его и создаёт `.gitattributes`, но сливать нечего: `graphify-out/` в
  `.gitignore`. Файл удалён — иначе он уехал бы в репозиторий и у коллег без
  локально прописанного драйвера git ругался бы на каждый merge. Понадобится
  обратное решение (граф в репозитории) — тогда убрать его из `.gitignore` и
  вернуть `.gitattributes` строкой `graphify-out/graph.json merge=graphify`.

## Правила работы

- **При сжатии контекста (`/compact`, автосжатие) сохранять**: формулировку
  текущей задачи и решения заказчика из переписки, список изменённых файлов,
  запущенные проверки с результатом и что ещё НЕ проверено.

- Если задача говорит «не реализовывать X» — не реализовывать X. Если кажется что X всё же нужен — спросить пользователя, не делать тихо.

- **Не наебывать.** Не выдавать сделанным то, что сделано наполовину, и
  проверенным — то, что проверено частично. Если охват проверки уже требования —
  сказать это прямо: «проверил вот это, вот это не проверял».

- **Проверку строить под ТРЕБОВАНИЕ, а не под свою реализацию.** Сначала
  выписать, каких мест касается требование пользователя, и только потом писать
  проверку — по этому списку, а не по своему диффу. Проверка, написанная от
  диффа, подтверждает ровно то, что ты и так сделал, и молча пропускает то, что
  забыл.

  Живой пример, на котором это правило и появилось: на просьбу «при выборе
  компании показывать только отделы этой компании» был отфильтрован список
  СТРОК таблицы, тест прочитал названия отделов из строк таблицы и показал
  «всё сходится». Выпадающий список отделов при этом остался со всеми 20
  отделами — то есть половина видимого требования не была ни сделана, ни
  проверена, а отчёт говорил «готово».

- **Поле, которое некуда применить, — признак неверной модели.** Заведя
  атрибут, сразу спросить: кто его читает и в какой формуле он участвует. Не
  находится ответа — атрибут стоит не на той сущности. Так в вахте должность
  («охранник», «ГБР», «начальник») сначала висела на ПОСТУ: точка на карте не
  бывает охранником, и от неё зависела оплата человека, поэтому поле не
  использовалось нигде и было замечено только заказчиком. То же самое дважды
  показал загрузчик реальных данных: если, чтобы разложить файл заказчика по
  модели, приходится ВЫДУМЫВАТЬ сущность («Выезд ГБР · 1 экипаж»), — модель
  неверна, а не файл кривой.

- **Перед коммитом и деплоем — спрашивать.** Не коммитить, не пушить и не
  катить на препрод по своему решению, даже когда правка выглядит очевидной и
  проверенной. На препроде работают живые пользователи.

## Стандарт выполнения задачи (раньше писалось в каждом промпте)

Действует по умолчанию для любой задачи, особенно из `task_*.md`. Промпт может
отменить пункт явно; молча пропускать нельзя.

1. **Прочитать задачу целиком** (`task_*.md` и таски, на которые она ссылается).
   Работа была прервана — сначала `git status` и `git log`, определить, что уже
   сделано, и не переделывать готовое.
2. **Имён функций в задаче нет намеренно** — места искать через граф
   (`graphify query` / `graphify path`, см. «Работа с графом кода»), а не угадывать.
   Если задача просит «сначала доложи» — доложить найденные точки входа до правок.
3. **Баг, тормоза, «подозрение» — сначала диагностика, НИЧЕГО не меняя.** Числа,
   а не предположения; таблицей (было / стало / из чего разница), ранжировать по
   вкладу. Не чинить по ходу — ждать решения.
4. **Решений за заказчика не принимать.** Неоднозначность или дыра в логике —
   остановиться, описать варианты со своей рекомендацией, спросить. Не делать
   сверх описанного, но и не выполнять молча то, что противоречит коду или
   логике: сказать об этом до работы.
5. **Бэкап БД перед началом** любой задачи, которая пишет в базу или несёт
   миграцию (раздел «Бэкапы БД»).
6. **Миграции**: `alembic upgrade head` + `alembic current` сразу после создания
   (хук напоминает сам).
7. **Суммы.** Задача про отображение, права, целостность или производительность
   НЕ меняет деньги: сверить ведомость и итоги до и после на нескольких месяцах.
   Проверочный пример из задачи (конкретные суммы) — обязательно тестом.
8. **Производительность — ничего не должно стать медленнее.** Оптимизация — замер
   до и после на тех же данных той же методикой (фронт — Long Animation Frames);
   не стало лучше — задача не закрыта.
9. **Проверка** — скилл `check-changes` (подбор тестов по изменённым файлам,
   фронт-тесты и сборка, зеркала бэк↔фронт). UI — глазами в браузере
   (Playwright; стенд обычно поднят — сначала `docker ps`). Задача, задевающая
   больше одного места, — перед отчётом агент `requirement-reviewer` с дословным
   требованием. Полный `pytest` (~30 мин) — в фоне, дождаться до итогового отчёта.
10. **Обновить правила**: раздел в `CLAUDE.md` или в нужном `.claude/rules/*.md` —
    что сделано, почему так, решения заказчика из переписки, где тесты.
11. **Правило 3 попыток** (ниже).
12. **Коммиты — по одному на часть задачи, но каждый только после вопроса**;
    push — тоже после вопроса. **Деплой делает пользователь сам** — не запускать
    `deploy.sh` и не ходить на препрод с изменениями.
13. **Препрод — только чтение и замеры.** Любое изменение там — спросить.
    Логины и пароли из переписки никуда не записывать (ни в файлы, ни в память).
14. **Итоговый отчёт**: что сделано; какие проверки запускались и что вернули;
    что НЕ проверено; что отложено и почему.

## Бэкапы БД

- **Dev — перед задачей, которая пишет в базу, несёт миграцию или массовую
  правку данных** (п.5 стандарта), и всегда перед `reset-data`:

  ```bash
  mkdir -p ~/backups
  F=~/backups/before_<задача>_$(date +%s).sql
  docker exec -t $(docker ps -q -f ancestor=postgres:16) pg_dump -U tabel tabel > "$F" \
    && test -s "$F" && ls -lh "$F"
  ```

  Имя — по задаче (`before_vahta_sites_…`, `before_vedomost_…`): по нему потом
  ищут, какой дамп был «до». Пустой дамп — не бэкап: `test -s` обязателен, путь
  назвать в отчёте. Восстановление:
  `docker exec -i $(docker ps -q -f ancestor=postgres:16) psql -U tabel tabel < "$F"`
  (в чистую базу — сначала пересоздать её).
- **Препрод — бэкап делает `deploy.sh` сам** (`pg_dump | gzip` в
  `~/backups/zemlya-tabel`, хранит 10, при неудаче деплой прерывается;
  восстановление — `docs/DEPLOY.md`). `--no-backup` по своей инициативе не
  использовать. Ручная операция с данными препрода (как сверка табельных номеров)
  — только с разрешения и после дампа `preprod_tabel_before_<что>_<дата>.sql.gz`.
- **В дампах персональные данные** — только локально: не в репозиторий, не в
  `docs/`, не в тесты и не цитировать в ответах. `~/backups` без спроса не чистить.
- Сравнить «было → стало» (например, подозрение, что миграция испортила
  справочники) — поднять дамп во временную базу `*_check` и сравнивать запросами;
  временную базу потом удалить.

## Правило 3 попыток

Если ты столкнулся с проблемой которую не получается решить (тест падает, ошибка установки, синтаксическая ошибка которую исправить не выходит, миграция не применяется и т.п.) — даю тебе 3 попытки.

После 3 неудачных попыток одной и той же задачи:
1. ОСТАНОВИСЬ. Не пробуй дальше.
2. Кратко опиши пользователю что пытался сделать (3 попытки в одну строку каждая).
3. Дай гипотезу почему не получается.
4. Жди указаний от пользователя.

Это правило важнее «довести задачу до конца». Лучше остановиться и спросить, чем сжечь токены на бесполезные попытки.
