# CLAUDE.md — zemlya-tabel

## Что это за проект

Система учёта рабочего времени для девелоперской группы «Земля МО».
- Несколько юрлиц; зарплата сотрудника распределяется между ними.
- Ролевая модель: Admin, Manager, Accountant, Timekeeper (табельщик), Employee.
- Workflow периода: Draft → Pending Review → Closed.
- После Closed правки только Admin с обязательным комментарием и audit log.

## Стек

- **Backend:** Python 3.11+, FastAPI, SQLAlchemy 2.x, Alembic, PostgreSQL (psycopg)
- **Схемы:** Pydantic v2 + pydantic-settings
- **Auth:** JWT Bearer (python-jose), хеширование passlib[bcrypt]
- **Тесты:** pytest + httpx, SQLite in-memory для изоляции
- **Линтер:** ruff
- **Frontend:** React 18 + TypeScript + Vite, Tailwind CSS, Zustand (store), axios, react-router-dom, zod, recharts (графики дашборда)
- **Excel:** openpyxl (экспорт Т-13)

### Демо-данные: `seed-demo-data` (task_demo_data)

Не путать с `seed-test-data`: тот заводит 14 сотрудников с ГРАНИЧНЫМИ случаями и **пустой** табель (функциональные проверки), этот — реалистичный объём с заполненным табелем. Генератор — `app/services/demo_data.py`.

- **Рабочие дни и длительность смены берутся только из `services.work_schedule`** (`planned_work_dates` / `shift_hours_for_date`). Не дублировать формулы графиков в генераторе: демо-табель обязан сходиться с расчётом ЗП и нормой.

## Конвенции

### Таблицы
- Имена: snake_case, **множественное число** (`employees`, `departments`, `timesheet_entries`)

### Pydantic-схемы
Три схемы на каждую сущность:
- `XxxBase` — общие поля
- `XxxCreate(XxxBase)` — поля для создания (пароль, foreign keys)
- `XxxRead(XxxBase)` — поля для чтения (id, created_at, вложенные объекты), `from_attributes=True`

### Миграции
- **Только через Alembic**, никогда `Base.metadata.create_all()` в проде.
- `alembic revision --autogenerate -m "короткое описание"` — создать миграцию.
- Коммитить файл миграции вместе с изменениями модели.
- В `alembic/env.py` — `import app.models` чтобы все модели были зарегистрированы в metadata.

### Soft delete
Пользователи (и другие сущности с FK из audit_log) **никогда не удаляются физически** — `is_active=False`.

### Audit log
- Вызывать `log_action(...)` из `app.core.audit` при каждом CRUD и смене статуса.
- `log_action` делает `db.add()` — коммит вызывается снаружи вместе с основным изменением.

### Роутеры
- Регистрировать в `app/main.py` через `app.include_router(...)`.
- Префикс `/api/...` (не `/api/v1` — версионирование добавим позже при необходимости).

## Производственный календарь

- **Источник:** xmlcalendar.ru — `https://xmlcalendar.ru/data/ru/{year}/calendar.json`
- **Формула нормы:** `Норма = workdays × hours_per_shift − short_days`
- Все вычисления норм — только через `app.services.calendar`, не дублировать формулу в роутерах.
- В тестах **обязательно мокать** `app.services.calendar.fetch_calendar_from_remote` через `monkeypatch` — никаких реальных сетевых запросов.
- Тип дня в строке `days`: обычное число → выходной/праздник, `N+` → праздничный (тоже нерабочий), `N*` → сокращённый рабочий.

## Timesheet

- Одна запись = (employee, **position**, work_date, company, hours) — позиция появилась в task_positions ч.A; `position_id IS NULL` читается как основная
- `hours=0` не существует — при сохранении с hours=0 запись удаляется из БД
- Все мутации только через `upsert_cell` сервиса (audit log там)
- После правки ячейки фронт перечитывает ТОЛЬКО часы, суммы — с задержкой (см. «Производительность табеля»)
- Фильтрация по department_id на бэке принудительная для manager
- Один сотрудник может иметь несколько ячеек в один день на разные компании
- **Ночная смена — отдельная сущность**, а не ячейка часов: в одном дне может быть и дневная работа, и выход в ночь (см. «Ночные смены»)
- Unique constraint: `(employee_id, work_date, company_id)`
- **Системные пользователи (is_system_admin=True) скрыты из табеля** — никогда не попадают в выдачу
- Компании сотрудника в табеле: только default_company по умолчанию + те, где есть часы. Бэк отдаёт `extra_companies_by_employee: dict[int, list[int]]`. UI хранит «expanded companies» в локальном state (не zustand), загружает с сервера при старте.

## Два вида табеля (задача 3.10)

- Тумблер в шапке: **«Классический»** (`TimesheetPage`, одна строка/сотрудник, слоты компаний в ячейке дня) и **«По компаниям»** (`TimesheetCompanyView`, сотрудник = N строк по компаниям). Выбор в zustand `store/timesheetView` + localStorage (task_ux_improvements ч.3 — см. «Сохранение состояния интерфейса»), не сбрасывается ни при смене месяца, ни при перезагрузке. По умолчанию — классический.
- Оба вида используют **одни и те же данные** с бэка (`GET /api/timesheet/{y}/{m}?include_payroll=`), отличается только рендеринг. `TimesheetPage` — владелец данных, передаёт их и колбэки в `TimesheetCompanyView` пропсами.
- Вид «по компаниям»: строка = позиция × компания, **два уровня rowspan** (task_positions ч.B) — ФИО на все строки сотрудника, Должность/Отдел/График слева и Итого Ч/Итого ₽/Δ/Норма справа на строки одной позиции. Колонки компании (дни, Итого Ч компании, Оклад/Сверхур.Ч/Празд.Ч/Сверхур.₽/Празд.₽) — на каждой строке. Финансы видят только admin/accountant/manager.
- Строки сотрудника: родительская (`default_company`, помечена «осн.», удалить нельзя) + где есть часы + добавленные вручную. Кнопка «+» (справа от чипа последней компании) и «×» (убрать доп. строку с 0 часов) — **только в draft** (как и редактирование часов в классике).
- Sticky слева в обоих видах: ФИО/Отдел/График (+ Компания в новом виде) — фикс. ширины + накопленные смещения (`stickyLeft()` в `TimesheetCompanyView`), иначе sticky разъезжается.
- **Фильтры шапки — как на «Расчёт ЗП»** (task_search_and_shiftpay → task_timesheet_filters): поиск **«ФИО или таб.№»**, фильтр **«Все компании»**, фильтр отдела — в этом порядке. Поиск и компания фильтруют уже загруженные данные на фронте (на бэк не ходят), регистронезависимо, поверх фильтра отдела; общие для обоих видов — `TimesheetPage` отдаёт в `TimesheetCompanyView` уже отфильтрованный список. Компания берётся по той же логике, что в ведомости: сотрудник относится к компании, если **есть часы по ней в месяце ИЛИ она у него основная** (`default_company_id`).
- **Фильтруются только строки**: итоги (ИТОГО, по компаниям, суммы по дням) продолжают считаться по всем видимым сотрудникам месяца, иначе фильтр молча менял бы суммы. Что итоги шире выборки — видно по счётчику «найдено N из M · итоги по всем» рядом с кнопкой «Сброс».
- Блок **«ПО КОМПАНИЯМ»** в подвале — сворачиваемый, по умолчанию **свёрнут** (при 8 юрлицах занимал пол-экрана, в основном прочерками). Развёрнутость сохраняется (ключ `tabel.timesheet.companySummary`).
- **Норма — часов И дней** (task_ux_improvements ч.1): в колонке «Норма ч / дн» под часами мелким шрифтом число рабочих дней (смен) месяца, в строке ИТОГО — их сумма. Цифра приходит с бэка (`EmployeePayroll.norm_days`, считается `norm_days_for_schedule`) и уже учитывает вид графика: у weekday это плановые дни производственного календаря, у cyclic — **смены цикла** (2/2 → 16 смен, а не 30 дней). Не считать норму дней на фронте.

## Производительность табеля (task_timesheet_perf, 200 сотрудников)

При 200 сотрудниках и 8 юрлицах табель «все отделы» открывался **13 с** и столько же стоила каждая введённая цифра — фронт перезагружал месяц целиком после каждой ячейки. Профиль показал: SQL — 0,6 с из 13, всё остальное Python. Замеры (200 сотрудников / 6 отделов / ~5850 ячеек, синтетика): открытие отдела **3,15 → 0,07 с**, все отделы **11,57 → 0,41 с**, ведомость «все» — 0,22 с, дашборд 3,43 → 1,72 с.

Четыре причины и что с ними сделано — **не откатывать, не «упрощать» обратно**:

- **`compute_extra_companies_by_employee` был O(сотрудники × ячейки)** — на каждого сотрудника сканировался весь список ячеек месяца (1,2 млн итераций, 78% времени запроса). Теперь один проход в dict. Результат обязан остаться прежним: ключ есть у каждого сотрудника (в т.ч. без часов), основная компания исключена, порядок возрастающий (проверяется в `tests/test_task33_improvements.py`).
- **Лишний `commit` на GET обесценивал загруженные объекты.** `_build_periods_for_response` коммитил всегда, `expire_on_commit=True` сбрасывал уже прочитанные часы и сотрудников, и каждая строка перезагружалась своим SELECT-ом (6455 запросов вместо 43). Теперь `get_or_create_periods` берёт существующие периоды одним запросом и сообщает, создавалось ли что-то; коммит — только если создавалось (обычно первый заход в месяц). Плюс периоды строятся **до** загрузки часов. Созданный период коммитить обязательно — его id уходит клиенту и по нему шлют submit. `expire_on_commit` не трогали: тесты используют свой `TestingSessionLocal` и такую правку не заметили бы.
- **`parse_days_string` разбирал строку дней заново на каждый вызов** — `is_workday`/`is_short_day`/`is_holiday` зовутся на каждый день каждого сотрудника. Теперь `@lru_cache` по самой строке (устареть не может: другой календарь — другая строка), результат **иммутабельный** `frozenset` — не мутировать на месте.
- **Фронт перезагружал месяц с расчётом ЗП после каждой ячейки.** Теперь правка часов/отсутствия перечитывает **только часы** (`include_payroll=false`, ~0,03 с), а суммы пересчитываются через `PAYROLL_REFRESH_DELAY_MS` = 1200 мс после последней правки. Пока суммы устарели — индикатор «суммы пересчитываются…», а «Итого Ч» в строке считается по ячейкам, а не по `payroll.total_hours` (иначе введённая цифра видна в дне, но итог секунду стоит на месте). Ответ без расчёта приходит с `payroll=null` — прежние суммы в state сохраняются, иначе денежные колонки мигали бы пустотой.

**Отдел выбирается явно.** `TimesheetPage` не грузит табель, пока не выбран отдел (`DepartmentGate`); выбор хранится в `store/timesheetView` (`deptChoice: number | 'all' | null`, null — не выбран) и переживает смену месяца. «Все отделы» остались отдельным пунктом — сводные итоги в подвале нужны бухгалтеру, после оптимизаций это 0,4 с. Гейт показывается только тем, у кого есть выбор (`canSelectDept`): employee и руководитель/табельщик одного отдела грузятся сразу. Ссылка `?department_id=N` из «Задач» и дашборда считается выбором. Группа «Без отдела» отдельным пунктом пока не выбирается — эти сотрудники видны через «Все отделы» (у API нет способа запросить NULL-отдел).

Бенчмарки, которыми это мерилось, в репозиторий не клались: скрипты одноразовые (`bench_month.py` / `bench_profile.py` / `bench_dept.py` — синтетика в SQLite in-memory, профиль по этапам и по `cProfile`). Если понадобится мерить снова — важно, что абсолютные числа SQLite ≠ Postgres, а пропорции Python-части переносятся.

### Как откатить

Три независимых коммита, каждый откатывается сам по себе (`git revert <sha>`), порядок не важен — они не пересекаются по файлам:

| коммит | что вернётся | цена отката |
|---|---|---|
| `b0a705b` perf(backend) | старые O(N×E), безусловный commit, разбор календаря без кэша | табель «все отделы» снова 13 с; правильность не страдает |
| `83b8bce` perf(frontend) | перезагрузка месяца с расчётом после каждой ячейки, табель сразу по всем отделам | ввод снова упирается в время ответа; экран выбора отдела исчезнет |
| `10f2196` docs | этот раздел | — |

Внутри бэкендного коммита правки тоже независимы: можно вернуть только `lru_cache` (`app/services/calendar.py`), только условный commit (`_build_periods_for_response` + `get_or_create_periods`) или только один проход (`compute_extra_companies_by_employee`). Фронтовые две части (задержанный пересчёт сумм и `DepartmentGate`) тоже разделимы: гейт — это `deptChoice` в `store/timesheetView` + ранний `return` в `TimesheetPage`, пересчёт — `fetchMonth(withPayroll)` / `afterEdit`.

### Риски, которые были и как закрыты

- **Изменился результат `compute_extra_companies_by_employee`.** Проверено сверкой старой и новой реализации на реальных данных дев-БД (все месяцы с часами — совпадение) плюс 7 проверок в `tests/test_task33_improvements.py`.
- **Фантомный период.** Если бы условный commit не сработал, созданный период откатился бы вместе с транзакцией GET, а его `id` уже ушёл клиенту — кнопка «Отправить на проверку» дала бы 404 «Period not found». Гарантия: `get_or_create_periods` возвращает флаг `created`, и это **единственный** источник решения о коммите. Любая новая запись в этом пути обязана либо выставить флаг, либо коммитить сама.
- **`parse_days_string` вернул `frozenset` вместо `set`.** Сравнение с обычным `set` работает, тесты не правились. Все существующие вызывающие только читают (`in`, `len`, распаковка) — проверено grep-ом по `app/` и `tests/`.
- **Устаревшие суммы после правки часов.** Закрыто индикатором «суммы пересчитываются…» и тем, что «Итого Ч» берётся из ячеек. Excel и ведомость считаются на сервере — там всегда свежие цифры.
- **Пересчёт упал — суммы молча остались старыми.** `fetchMonth` возвращает признак успеха, и пометка снимается только при успехе; при ошибке остаётся индикатор + тост.
- **Чужой отдел в сторе.** `deptChoice` живёт в zustand и переживает смену пользователя в одной вкладке: после логина другого человека выбор мог указывать на недоступный ему отдел (403 и пустой экран). Закрыто сбросом выбора, если его нет в загруженном списке отделов; пустой список (неудавшаяся загрузка справочника) сбросом не считается.

### Риски, которые остались (следующий спринт)

- **Регрессию производительности ничто не ловит.** Перф-тестов в CI нет: вернуть O(N×E), лишний commit или загрузку часов до периодов можно, и все 577 тестов останутся зелёными. Если это повторится — заводить тест на **число SQL-запросов** (счётчик через `event.listen(engine, "before_cursor_execute")`), это дёшево и стабильнее замеров времени.
- **Первый заход в месяц стоит ~1,2 с** (создаются периоды → commit → обесцениваются уже загруженные сотрудники). Дальше 0,07 с. Лечится вычислением списка отделов отдельным лёгким запросом до загрузки сотрудников; не делали — это раз в месяц на отдел.
- **Дашборд остался 1,7 с** и выбор отдела его не касается: он считает ЗП по всем сотрудникам за 6 месяцев динамики. Кандидаты — кэш/матвью помесячных итогов или расчёт динамики по запросу, а не сразу.
- **Ведомость «Расчёт ЗП» грузит всех** (0,22 с на 200 — терпимо), но DOM у неё такой же тяжёлый, как был у табеля. Если начнёт тормозить — тот же приём с выбором отдела.
- **Группа «Без отдела» недоступна отдельным пунктом**: у `GET /timesheet/{y}/{m}` нет способа запросить `department_id IS NULL` (нет фильтра — значит «все»). Такие сотрудники видны только через «Все отделы». Если группа реально используется, добавить в API явное значение (например `department_id=none`) и пункт в гейт.
- ~~**`deptChoice` не переживает перезагрузку страницы**~~ — закрыто в task_ux_improvements ч.3: выбор отдела (как и месяц, вид и фильтры) хранится в localStorage, см. «Сохранение состояния интерфейса».
- **Ссылка со сменой только query-параметра не меняет выбранный отдел**: `?department_id=N` читается один раз при монтировании. Переход «Задачи → Табель» работает (это смена маршрута), а вот клик по другому отделу на дашборде, когда табель уже открыт, отдел не переключит. Поведение было таким и до этих правок, но с сохранением выбора в сторе стало заметнее.
- **Виртуализация и `<select>` юрлиц не трогались.** После выбора отдела строк ~34 и это не нужно. Если появится отдел на 100+ человек — вернётся тяжёлый DOM; тогда виртуализация конфликтует с `rowSpan` ФИО (в виде «по компаниям» — два уровня merge), то есть это переделка вида, а не оптимизация.
- **Фронт-тестов нет вообще**, вся проверка ручная: ввод часов, смена компании в слоте, код отсутствия, выбор отдела, «Все отделы», переход из «Задач».

## Графики работы: weekday и cyclic (task_shift_schedules)

- **Единственный источник правды — `app/services/work_schedule.py`.** Payroll, автозаполнение, Excel-экспорт и превью считают рабочие дни и норму только через него; не дублировать формулы и не сравнивать `schedule_type` напрямую (есть `normalize_schedule_type` / `is_cyclic_schedule`).
- Два вида графика (`Schedule.schedule_type`), legacy-значения `standard`/`shift` мигрированы и всё равно нормализуются на входе:
  - **`weekday`** («по дням недели»: 5/2, 6/1, вс–чт, вт–сб) — рабочие дни в колонке `work_weekdays` (JSONB, 0=Пн … 6=Вс). Пусто → выводятся из имени «N/M» при N+M=7, иначе Пн–Пт.
  - **`cyclic`** («скользящий цикл»: 2/2, 3/3) — `cycle_start_date` (анкер фазы) + `cycle_work_days`/`cycle_off_days`. `offset = (дата − старт).days; index = offset mod (work+off)`, работает для любых дат до и после анкера. **Смена 1 и смена 2 — два отдельных графика с разными анкерами** (сдвиг фазы), а не поле в одном.
- Два РАЗНЫХ понятия «рабочий день», не путать:
  - `is_schedule_work_day` — **оплата**: календарный праздник в рабочий день недели остаётся рабочим днём графика (часы по окладу); выход в свой выходной → «вне графика». Обёртка `is_off_schedule_day`.
  - `is_planned_work_day` / `planned_work_dates` — **план**: норма часов, автозаполнение, превью. Здесь праздник рабочим днём НЕ является.
- Норма месяца — `norm_hours_for_schedule` (дни — `norm_days_for_schedule`):
  - weekday: Σ по плановым дням, смена, у сокращённого дня смена − 1. Для 5/2 совпадает со старой календарной формулой (июнь 2026 → 167). Обычная суббота/воскресенье календаря рабочим дням графика не мешают: у 6/1 суббота рабочая, нерабочий **будний** день календаря (праздник или перенос) исключается у всех.
  - cyclic: смены месяца по циклу × часы смены, производственный календарь НЕ участвует (2/2 по 12 ч, июнь 2026 → 15 × 12 = 180). Сокращённый день смену сменщика не укорачивает.
- Дневная норма (`shift_hours_for_date`) → переработка сменщика считается от 12 ч, а не от 8.
- `schedule_issue(schedule)` — единая причина «посчитать нельзя» (нет графика; сменный без анкера/паттерна). Её отдают и `reason_if_not_calculable` в payroll, и пропуск сотрудника в автозаполнении. **`is_calculable=True` для сменных графиков с анкером**; производственный календарь сменщику не нужен.
- Превью: `POST /api/schedules/preview` (тело — поля формы, не id: график может быть ещё не сохранён) → дни месяца с флагом рабочий/нерабочий, часы, норма. Права как у чтения справочника (employee — 403).
- Проверенные анкеры под фазы из 1С на июнь 2026 (есть в `seed-test-data`): 2/2 смена 1 → `2026-05-31`, 2/2 смена 2 → `2026-06-02`, 3/3 смена 1 → `2026-06-04`, 3/3 смена 2 → `2026-06-07`.

## Ночные смены: фонд отдела, вычисляемая ставка, лимит (task_night_shifts_rework)

Ночная смена — **отдельная подработка**, а не разновидность дневной работы. Единственный источник правды — `app/services/night_shifts.py`; в расчёт она приходит готовыми числами (`night_shifts`, `night_rate`), поэтому `services/payroll.py` остаётся чистой функцией и за фондом в БД не ходит.

- **Природа**: отметка `(позиция, дата)` без часов (`NightShift`, таблица `night_shifts`, unique `(position_id, work_date)`). К графику **не привязана** — выйти в ночь можно в любой день, хоть в свой выходной. Доступна только рабочим местам с флагом `has_night_shifts`.
- **С дневными часами того же дня СОСУЩЕСТВУЕТ, с кодом отсутствия — НЕТ.** Часы и ночная смена — разные работы одного дня; ОТ/ДО/Б/Н — отметка на весь день человека, и выйти в ночь он в этот день не может. Обе стороны закрыты в сервисах, как и взаимоисключение часов и кодов:
  - постановка кода (`set_absence`) удаляет ночные отметки дня **по всем рабочим местам** сотрудника, с audit log и освобождением лимита;
  - `set_night_shift` на день с кодом даёт **422** «В этот день отмечено отсутствие (Б) — снимите код…». Код **не снимается молча** (в отличие от часов): отсутствие отмечено на человеке целиком, а галочка ставится одному рабочему месту — тихо стирать его нельзя. В UI галочка такого дня заблокирована.
- **Ставка ВЫЧИСЛЯЕТСЯ, вручную не задаётся**: `ставка = фонд_отдела / календарные_дни_месяца` (100 000 / 31 = **3225.81**), округление до копеек. Календарные дни, не рабочие — смена к графику не привязана. Фиксирована на месяц: от числа отмеченных смен не зависит. Ручное поле `employee_positions.night_rate` **снято миграцией** `b8c9d0e1f2a3` — два источника цены смены неминуемо разъехались бы. В карточке позиции остался только флаг.
- **Фонд — на отделе** (`Department.night_shift_fund`, Numeric(12,2), server_default **100000**, миграция `a7b8c9d0e1f2`). Правит admin: `PATCH /api/departments/{id}` и форма отдела в «Оргструктуре». Хардкода лимита в коде нет; 0 — законное значение «ночных смен в отделе нет». **Без отдела ночных смен нет вовсе** — фонда взять негде, попытка отметить даёт 422.
- **Лимит числа смен = `фонд / ставка`, то есть тождественно числу календарных дней месяца** — так и считается (`night_shift_limit`), а не делением на округлённую ставку: `100000 / 3225.81 = 30.99…`, и floor молча отнял бы последнюю смену. Отсюда главное свойство: `число_смен × ставка ≤ фонд` (с точностью до копеек округления ставки — 31 × 3225.81 = 100000.11).
- **Лимит СУММАРНЫЙ по отделу**, а не по человеку: в одну ночь могут выйти несколько человек, каждый выход тратит смену фонда. Считается по факту — снятая отметка лимит освобождает, отдельного «потрачено» в БД нет.
- **Блокировка авторитетна на бэке**: `set_night_shift` перед вставкой пересчитывает смены отдела за месяц и при `used + 1 > limit` бросает `NightLimitExceeded` → **409** «Лимит ночных смен отдела исчерпан (осталось N смен из M)». Фронт показывает остаток заранее, но не решает: две вкладки иначе перерасходовали бы фонд.
- **Оплата** — надбавка СВЕРХУ дневного расчёта: `night_amount = число_смен × ставка`, входит в `total_amount`, в «Итого начислено» ведомости и дальше в «К выплате» (округление к выплате — общее, вниз до 100 ₽). Дневной расчёт (оклад, переработка, выходные, отсутствия) ночные не трогают вовсе. Начисляется даже там, где дневной расчёт невозможен (`is_calculable=False`): ночная смена от графика и оклада не зависит. В `breakdown_by_company` не разносится — как и отсутствия, к юрлицу не привязана, её разносит каскад процентов ведомости.
- Эндпоинт: `PUT /api/timesheet/night-shift` (`{employee_id, position_id, work_date, value}`; `value=false` — снять). Права как у ячейки часов **плюс** `_require_timesheet_role`: это факт времени, поэтому отмечает и табельщик, но не сам сотрудник. Период должен быть в draft. `GET /timesheet/{y}/{m}` отдаёт `night_shifts` (отметки) и `night_funds` (фонд/ставка/лимит/использовано/остаток по отделам выдачи).
- **Фонд считается по ВСЕМУ отделу**, а не по видимым актору сотрудникам (`count_by_department`): иначе остаток на экране расходился бы с проверкой при сохранении.
- Расчёт и дашборд берут данные через один `load_night_context(db, employees, year, month)` — дашборд обязан сходиться с `/payroll`, поэтому ночные учитывает и он.

- **UI**: под строкой рабочего места с флагом — строка **«🌙 Ночные»** с галочкой на каждый день (не слот в ячейке: ночная сосуществует с дневными часами). Слева от дней — остаток лимита отдела.
  - **Строка живёт только в днях.** В сводном блоке справа её нет: «Итого ч» и весь денежный (у табельщика — часовой) блок строки рабочего места растянуты на две строки через `rowSpan` (`trailingSpan` в `renderPositionRow`), то есть колонки просто выше. Пустые ячейки на их месте — хоть одной широкой через `colSpan`, хоть по одной на колонку — читались как грязная полоса через всю таблицу; так уже пробовали, не возвращать.
  - Высоту ФИО-ячейки считает **`employeeRowSpans`**: `count` из `withSpans` знает только про позиции и разъехался бы ровно на высоту ночных строк.
  - Числа колонок хвоста — константы `MONEY_COLS` (15) и `HOUR_COLS` (8): по ним считается `totalCols` и заглушка строки ИТОГО, и, разъехавшись, они ломают всю таблицу.
- Колонки: в табеле «**Ночные ₽**» (у табельщика «Ночные см.»), в ведомости «Ночные» (сумма + число смен), в Excel ведомости — **хвостовые** колонки «Ночных смен» / «Надбавка за ночные» (в середину нельзя: в шаблоне финдира зафиксированы буквы колонок). В Т-13 ночных нет — там только часы, а у ночной смены часов нет.
- **Чего пока нет**: строки «Ночные» в виде «по компаниям» (`TimesheetCompanyView`) — отмечают ночные в классическом виде, как и премии/KPI; ночных в Т-13; отдельного фонда для сотрудников без отдела (им ночные недоступны). `seed-demo-data` ставит только флаг `has_night_shifts` — сами смены не отмечает.
- Тесты — `backend/tests/test_night_shifts.py` (30 шт.): ставка и лимит по месяцам, оплата 15 смен × 3225.81 = 48387, сосуществование с дневными часами, суммарный лимит отдела и блокировка 32-й смены, освобождение при снятии, нулевой фонд, сотрудник без отдела и без флага, табельщик (отмечает, денег не видит), закрытый период, взаимоисключение с кодом отсутствия в обе стороны (и что дневные часы ночную по-прежнему не трогают).

## Autofill (автозаполнение по графику)

## Employee lifecycle (жизненный цикл сотрудника)

- Увольнение: `POST /api/employees/{id}/dismiss` (body: `{dismissal_date: date}`) → is_active=False, dismissal_date установлен
- Возврат: `POST /api/employees/{id}/rehire` → is_active=True, dismissal_date=NULL
- Физическое удаление (`DELETE /api/employees/{id}`) оставлено для редких случаев
- Видимость в табеле: исключаются только те у кого `dismissal_date IS NOT NULL AND dismissal_date < date(year, month, 1)`. Таким образом уволенные в середине месяца видны в этом месяце
- Часы и история сохраняются при увольнении (каскада нет)
- is_active=False → login невозможен (auth endpoint возвращает 403)

## Импорт сотрудников из Excel (task_employee_import)

- Два эндпоинта, оба **только admin**: `GET /api/employees/import/template` (шаблон .xlsx) и `POST /api/employees/import` (multipart `file`, флаг `?confirm=`). `confirm=false` — превью со статусами строк, в БД ничего не пишется; `confirm=true` — создать валидные строки. **Подтверждение шлёт тот же файл**: разбор и валидация повторяются перед записью, на сервере нет состояния между шагами и превью не берётся на веру.
- Сервис `app/services/employee_import.py` — шаблон, нормализация, валидация, импорт. Колонки фиксированные (`COLUMNS`) и разбираются **позиционно**: заголовки нужны человеку, парсер на них не опирается. Лист «Сотрудники» (иначе первый), плюс в шаблоне лист «Справочники» с допустимыми компаниями/отделами/графиками.
- Шаблон: 1-я строка — заголовки, 2-я — **пример** (помечен `EXAMPLE_MARKER` = «ПРИМЕР — удалите эту строку» в колонке таб.№), 3-я — подсказки формата, данные ниже. Парсер пропускает пример (по маркеру, а не по номеру строки — его можно и удалить) и пустые строки.
- Нормализация (чистые функции, покрыты тестами): `normalize_schedule_key` (`5\2`, `5 / 2` → `5/2`), `company_keys` (компания ищется по коду, полному имени и без кавычек/правовой формы: `ООО "Комфорт"` → `Комфорт`), `parse_decimal` («50 000» с любым видом пробела, «50 000,50», «2500₽»), `parse_date` (ДД.ММ.ГГГГ, ISO, серийная дата Excel от 30.12.1899), `parse_pay_type`, `parse_weekend_pay_type` (голое число: <10 — коэффициент, ≥10 — фикс. ставка).
- Справочники **не создаются автоматически** — не нашли компанию/отдел/график, значит ошибка строки. Ищем только среди активных, ключи собираются в память один раз (`_load_refs`).
- Валидация даёт список ошибок на строку (`ImportRowRead.errors`, `is_valid`): нет ФИО, нет компании, компания/отдел/график не найдены, нет оклада/ставки за смену, не число, дата не распознана, **дубль таб.№** (и с БД, и внутри файла). Таб.№ занимает только **валидная** строка — ошибочная не импортируется, номер остаётся свободным.
- Импортируются только валидные строки, частичный импорт — норма. Карточка собирается общим `build_employee` (`app/services/employees.py`, вынесен из роутера — им же создаёт обычный CRUD), поэтому оклад/ставка и дефолты коэффициентов обрабатываются одинаково. **Доступы (email/роль/пароль) через импорт не заводятся**, часы/премии/займы тоже. Всё в одной транзакции, audit log на каждого созданного + сводка `employees_imported`.
- Фронт: `pages/admin/EmployeeImportModal.tsx` (кнопка «Импорт из Excel» в шапке раздела «Сотрудники»). Сводка + таблица всех строк, ошибочные красным со списком причин, нераспознанный справочник — зачёркнутым значением из файла. Кнопка подтверждения называет число валидных строк и блокируется, если их нет.

## Оргструктура: головная компания отдела и мульти-отдел менеджера (task_org_structure)

- **Головная компания отдела** (`Department.head_company_id`, nullable) — в какой компании отдел числится в дереве. Это **ярлык для навигации и группировки**, и НИЧЕГО больше: расчёт остаётся мультикомпанийным (часы по юрлицам + проценты распределения), формулы на это поле не смотрят и смотреть не должны. Отдел без головной компании — нормальное состояние, он попадает в ветку «Без головной компании». Миграция проставила её там, где она однозначна (все активные сотрудники отдела на одной основной компании).
- **Менеджер ↔ отделы — many-to-many** (`department_managers`, управляется со стороны отдела). Не путать два поля:
  - `Employee.department_id` — где сотрудник **числится** (работает). Не тронуто этой задачей;
  - `Employee.managed_departments` / `managed_department_ids` — чем менеджер **руководит**. Числиться в отделе и руководить им — независимые вещи: менеджер может руководить отделами, где не числится, и наоборот (числится, но не руководит → доступа нет).
  - Загружается `lazy="selectin"` — права проверяются на каждом запросе, ленивая загрузка дала бы N+1.
- **Единственный источник правды доступа — `app/services/org_access.py`** (`managed_department_ids`, `can_access_department`, `accessible_department_ids`, `is_department_scoped`, `can_see_finances`). Проверок «manager по одному отделу» и сравнений `actor.role == "manager"` в коде больше нет (иначе новая роль вроде табельщика молча попадала бы в ветку admin/accountant); новые места делать только через эти функции. Роутеры переводят отказ в 403 (в `routers/timesheet.py` — общий `_require_dept_access`).
- Правило: `department_id` в запросе не задан → отдаются **все** отделы менеджера; задан свой → сужается до него; задан чужой → **403** (не пустая выдача — молчаливая пустота выглядит как «данных нет»). Группа «Без отдела» (`department_id IS NULL`) менеджеру недоступна никогда.
- Покрыто: табель, расчёт ЗП, ведомость, премии/удержания, автозаполнение, оба Excel-экспорта, сотрудники, дашборд, submit периода. `GET /api/departments` отдаёт менеджеру только его отделы — из этого списка строится селектор.
- Менеджеры и табельщики отдела: `GET/PUT /api/departments/{id}/managers` (PUT — admin). PUT задаёт **полный набор** (пусто — снять всех), в набор принимаются только сотрудники с ролью `manager` или `timekeeper` (иначе 422), audit log `department_managers`. Роль каждого — в `role` ответа.
- Миграция `e2f3a4b5c6d7` перенесла каждому существующему менеджеру его `department_id` в новую связь — доступ не потерян. Фикстуры менеджеров в тестах обязаны задавать `managed_departments` явно, иначе менеджер не управляет ничем.
- **Единый экран «Оргструктура»** (`pages/admin/OrgStructurePage.tsx`, `/admin/org`, только admin) — дерево Компания → Отдел → Сотрудники, заменил вкладки «Компании» и «Отделы» (старые пути редиректят на `/admin/org`). Из дерева: создать компанию, создать отдел внутри компании (головная компания подставляется), сменить головную компанию, назначить менеджеров, перейти в карточку сотрудника (`/admin/employees?employee_id=N`).
  - Данные: `GET /api/org/tree` (`services/org_structure.py`) — всё дерево за несколько запросов, без N+1. CRUD экран не дублирует: пишет через существующие `/api/companies` и `/api/departments`, чтобы права и audit log остались в одном месте.
  - **Сотрудники в узле отдела свёрнуты по умолчанию** и не рендерятся, пока узел не раскрыт (в свёрнутом — `employee_count`): при 100+ сотрудниках иначе взрывается DOM.
  - Отделы без головной компании и сотрудники без отдела отдаются отдельными ветками — иначе они пропали бы из дерева вместе с возможностью их починить.
- Селектор отделов на фронте: admin/accountant — всегда, manager/timekeeper — если отделов **больше одного**, с опцией «Все мои отделы» (табель и «Расчёт ЗП»).

## Перенос отдела в другую компанию (task_move_department)

Подразделение может отделиться в самостоятельное юрлицо. Инструмент — массовое
действие в «Оргструктуре» на узле отдела, **только admin**: выбрать целевую
компанию → предпросмотр → перенести. Меняет **головную компанию отдела** и
**компанию рабочих мест ЭТОГО отдела**, действует **с текущего месяца вперёд**.

- **Переносятся только позиции переносимого отдела.** У совместителя рабочее
  место в другом отделе остаётся на своей компании — берутся `EmployeePosition`
  с `department_id == отдел` и `is_active`. Неактивные не трогаются намеренно:
  строк расчёта они не дают (`visible_positions` смотрит только на
  `active_positions`), то есть смена их компании ни на что не влияет.
- **Уже введённые часы НЕзакрытых месяцев переезжают вместе с отделом.** Компания
  лежит в САМОЙ ячейке (`timesheet_entries.company_id`), поэтому сменить компанию
  позиции мало: заполненный текущий месяц остался бы на прежнем юрлице, и деньги
  за него ушли бы ему же. Переносятся только ячейки, стоявшие на СТАРОЙ головной
  компании отдела: часы на других юрлицах — это осознанная работа на сторону, а не
  «часы отдела». Ячейки с `position_id IS NULL` (заведены до появления позиций,
  читаются как основная позиция) едут вместе с ней. Столкновение — в тот же день на
  то же рабочее место уже есть ячейка целевого юрлица — разрешается СЛОЖЕНИЕМ часов
  (иначе нарушится unique `(employee, position, date, company)`).
- **`managed_departments` сохраняются**: отдел не пересоздаётся, у него меняется
  только `head_company_id`, поэтому руководители и табельщики остаются на месте.
- **Всё одной транзакцией** (`move_department`, коммитит роутер): при сбое не
  остаётся ни половины перенесённых позиций, ни половины заморозки.
- **Обратный перенос НЕ восстанавливает исходную картину, если на целевом юрлице
  уже были часы**: при столкновении часы складываются в одну ячейку, и обратный
  ход отправит на старую компанию всю сумму, включая те часы, что изначально были
  «свои». Перенос туда-обратно безопасен только когда целевая компания часов не
  имела (обычный случай — новое юрлицо). Проверять до отката:
  `select count(*) from timesheet_entries where company_id = <целевая>`.
- Эндпойнты: `GET /api/departments/{id}/move-preview?target_company_id=` (ничего
  не меняет) и `POST /api/departments/{id}/move`. Перенос «в себя» — 422.
- Сервис — `app/services/department_move.py`; UI — `MoveDepartmentModal` в
  `pages/admin/OrgStructurePage.tsx` (кнопка «Перенести» на узле отдела).

### Почему перенос сначала ЗАМОРАЖИВАЕТ закрытые месяцы

**Снапшота расчёта в системе нет.** `timesheet_periods` хранит только статус и
кто/когда закрыл — ни одной денежной колонки; ведомость за любой месяц, включая
`closed`, каждый раз пересчитывается из ТЕКУЩИХ справочных данных. Статус
`closed` блокирует правку ячеек, а не расчёт. Это надо помнить в любой задаче,
меняющей справочные данные задним числом.

Основную часть истории смена компании позиции всё же не задевает: компания
отработанного часа лежит **в самой ячейке** (`timesheet_entries.company_id`), а
`services/payroll.py` компанию позиции не читает вовсе. Но `position.company`
входит в расчёт ещё двумя путями, и оба правят прошлое:

1. **«Нет часов вообще → вся сумма на основную компанию»** — сотрудник, у
   которого в закрытом месяце была только премия (или отпускные, больничные,
   ночные), увёл бы её на новое юрлицо целиком;
2. **остаток округления** в `distribute` достаётся основной компании, а если её
   нет в наборе — компании с наибольшей долей: рубль переезжает между юрлицами.
   На демо-базе это 4 строки из 78 за 6 закрытых месяцев одного отдела.

Поэтому перенос **сначала** фиксирует фактический расклад закрытых месяцев
месячным override-ом (`CompanyShareOverride` — он на вершине каскада), и только
потом меняет компанию. Порядок обязателен: заморозка считает ведомость по ЕЩЁ
СТАРОЙ компании. «Закрытый месяц» отдела = его же период в статусе `closed`.
Позиции, у которых override за этот месяц уже есть, пропускаются — ручной
расклад бухгалтера и так на вершине каскада.

Граница `closed` / не-`closed` — **одна и та же для обеих половин инструмента**:
закрытый месяц не трогаем и замораживаем, незакрытый (`draft`, `pending_review`)
следует за отделом — и по часам, и по расчёту. «Закрыт» значит «бухгалтерия уже
видела эти цифры». Если прошлый месяц остался незакрытым, его часы тоже переедут —
это осознанно, но после переноса такой месяц стоит проверить.

Замораживаются и строки с **нулевым начислением**: сумму там фиксировать нечем,
но привязка к юрлицу всё равно поехала бы (у строки без часов расклад берётся от
основной компании). Для них проценты берутся из самой строки, а не из сумм.

**Проценты заморозки считаются из уже посчитанных СУММ и с шагом `1e-6`**
(`FREEZE_PERCENT_STEP`). Это не педантизм: на 40 000 случайных раскладов шаг
`0.01` расходится с исходными суммами в 38 289 случаях (до 140 ₽), `0.001` — в
30 778 (до 14 ₽), `1e-6` — ни разу. На грубом шаге заморозка **сама** двигала бы
историю, ради которой затевалась. Ради этого миграция `e1f2a3b4c5d6` расширила
`company_share_overrides.percent` до `Numeric(9, 6)` (ручной ввод в ведомости
остаётся двухзначным). Шаг держит тест — «упростив» его обратно, видно регрессию.

### Что перенос НЕ чинит (и предупреждает об этом)

Наборы процентов ссылаются на `company_id` напрямую, поэтому перенос их не
трогает, а в каскаде они стоят **выше** авто-распределения по часам. Если у
рабочих мест (`EmployeeCompanyShare`) или у самого отдела
(`DepartmentCompanyShare`) задан явный %, куда целевая компания не входит, —
зарплата и после переезда пойдёт на прежние юрлица. Предпросмотр это считает
(`stale_share_position_count`, `department_shares_stale`) и показывает красным.
**Молча сбрасывать чужую настройку распределения нельзя** — это управленческое
решение бухгалтерии, а не следствие переезда.

Отсюда же: часы незакрытых месяцев инструмент переносит сам, но если у отдела или
его рабочих мест задан явный % каскада, деньги пойдут по нему, а не по часам.
Отдел с собственным дефолтом продолжит делиться по нему, пока проценты не поправят
руками.

Тесты — `backend/tests/test_move_department.py` (29 шт.): сам перенос, позиции
чужих отделов не тронуты, ответственные сохранены, расклад закрытого месяца
рубль в рубль, премия сотрудника без часов остаётся на старом юрлице, ручной
override не переписывается, отдел без закрытых месяцев не пишет ни строки,
открытый месяц уходит на новую компанию, предпросмотр (охват, ничего не меняет,
обе формы предупреждения) и точность шага заморозки. Отдельный класс на
перепривязку часов: открытый месяц переезжает, закрытый нет, сторонние юрлица не
тронуты, столкновение складывает часы, legacy-ячейка без позиции едет с основной,
подработка в чужом отделе на месте.

## Роль «Табельщик» (task_timekeeper_role)

Иерархия прав: `employee < timekeeper < manager < accountant/admin`. Табельщик **заполняет время** своих отделов и **не видит финансов**; отдельных «уровней табельщиков» нет.

- **Отделы — та же связь `managed_departments`**, что у менеджера (`department_managers`, управляется со стороны отдела). Табельщик и руководитель одного отдела — разные люди с разными правами; числиться в отделе и вести его табель — независимые вещи. Список кандидатов в PUT `/api/departments/{id}/managers` принимает роли `manager` и `timekeeper` (иначе 422), кто есть кто — в `DepartmentManagerRead.role`.
- **Два предиката в `app/services/org_access.py` — единственный источник правды «кто что видит»**:
  - `is_department_scoped(actor)` (`DEPARTMENT_SCOPED_ROLES = manager, timekeeper`) — доступ ограничен своими отделами. Проверок `actor.role == "manager"` в коде больше нет: новая роль иначе молча попадала бы в ветку admin/accountant и увидела бы **всех** сотрудников;
  - `can_see_finances(actor)` (`FINANCE_ROLES = admin, accountant, manager`) — кому отдаются деньги. Плюс `hides_finances(actor)` — кому их надо вычищать из ответа.
- **МОЖЕТ**: часы (`PUT /timesheet/cell`, батч), отсутствия ОТ/ДО/Б/Н (`PUT /timesheet/absence`), автозаполнение по графику, выгрузка **Т-13** (в файле только часы, рублей нет — `_require_timesheet_role`), чтение справочников (отделы — только свои, графики, календарь), дашборд по часам и статусам периодов.
- **НЕ МОЖЕТ**: расчёт ЗП и ведомость (`/payroll`, `/statement`, экспорт ведомости), премии/KPI/аванс, займ и его правки, распределение по юрлицам, проценты в карточке — **403** через `_require_finance_role`. Не отправляет период на проверку (`submit_for_review` — только admin/manager, `can_submit=False` в ответе), не закрывает и не переоткрывает, не видит инбокс «Задачи», не управляет сотрудниками/оргструктурой/доступами (всё это admin-only).
- **ВИДИТ ВСЕ ЧАСЫ.** Табельщик ведёт время, поэтому расчёт для него **считается**, и из него отдаются часы: норма, Δ, переработка, часы вне графика и праздничные, дни отпуска и больничного, остаток годового лимита Б, плановые/фактические дни и смены. Без этого он не увидит, правильно ли заполнил табель. Деньги из того же ответа вычищаются (`mask_payroll_summary`): суммы **обнуляются** (в схеме они обязательные `Decimal`, и `None` не прошёл бы валидацию ответа), ставки и коэффициенты — в `None`. Премии/KPI/удержания (`adjustments`) не отдаются вообще. В UI у него на месте денежного блока — колонки часов (Норма, Δ, Сверхур. ч, Вне граф. ч, Празд. ч, Ночные см., Отпуск дн., Больничный дн.), в виде «по компаниям» — Сверхур./Вне граф./Празд. в часах по каждому юрлицу плюс Δ и Норма.
- **Финансы скрыты на УРОВНЕ API, не в UI.** 403 на расчётных эндпойнтах мало: оклад, ставки, коэффициенты и займ лежат в карточке сотрудника и его позициях, а они приходят вместе с табелем. Поэтому `app/services/finance_masking.py` вычищает денежные поля из уже собранных схем ответа (`GET /timesheet/{y}/{m}`, `GET /employees`, `GET /employees/{id}`, `GET /employees/{id}/positions`) — прямой запрос табельщика тоже вернёт `null`. Список полей **перечислен явно** (`FINANCIAL_POSITION_FIELDS` / `FINANCIAL_EMPLOYEE_FIELDS`): новое денежное поле надо в него добавить, иначе утечёт молча.
- **Ночные смены**: факт выхода табельщик **отмечает** (`PUT /timesheet/night-shift` — это время, а не деньги), видит `has_night_shifts`, число смен (`night_shifts`) и остаток лимита отдела в сменах. Ставка (`night_rate`), фонд отдела (`night_shift_fund` в `GET /departments`) и надбавка (`night_amount`) — нет. Факт да, деньги нет.
- **Дашборд**: часы, отделы и статусы периодов — да; `payroll`, `payroll_by_department`, `payroll_by_company` и `payroll_total` в динамике — `None`/пусто (`include_money = can_see_finances`).
- **Фронт**: в меню только «Дашборд» и «Табель» (`Расчёт ЗП`, `Задачи`, справочники скрыты, роуты закрыты `RoleRoute`); в табеле два разных признака — `canSeeMoney` (денежные колонки) и `canSeeHourStats` (`canSeeMoney || timekeeper`, детализация часов). Расчёт запрашивается по `canSeeHourStats`, поэтому у табельщика колонки часов живые и пересчитываются после правки так же, как суммы у остальных; кнопка «Отправить на проверку» не появляется (`can_submit` с бэка), «Заполнить по графику» и «Excel» доступны. Роль назначается в карточке сотрудника (`ROLE_OPTIONS`), отделы — в «Оргструктуре» → «Ответственные».
- Схема БД не менялась: `employees.role` — `varchar(50)`, старый enum-тип `userrole` снят ещё миграцией `a1b2c3d4e5f6`. **Миграции для этой задачи нет.**
- Тесты — `backend/tests/test_timekeeper.py` (29 шт.): время без денег (включая проверку, что все категории часов на месте, а суммы и ставки — нули/None), «50000» не встречается в сыром ответе табеля, 403 на всех финансовых эндпойнтах, невозможность отправить период, изоляция чужого отдела, назначение роли, и отдельно — что менеджер того же отдела деньги по-прежнему видит.

## Совместительство: позиции сотрудника (task_positions, часть A)

- **Сотрудник имеет 1+ позиций** (`EmployeePosition`, таблица `employee_positions`) — «рабочих мест». Ровно одна помечена `is_primary` (основная), остальные — совместительство.
- **На позиции:** должность (`title`), тип оплаты и его база (`rate` / `shift_rate` / `hour_rate`), график (`schedule_id`), отдел (`department_id`), основная компания (`company_id`), коэффициенты выходных/праздничных/переработки, флаг ночных смен (`has_night_shifts`; ставки на позиции НЕТ — см. «Ночные смены»). **На человеке:** ФИО, таб.номер, доступ (email/роль/пароль), `managed_departments`, займ и премии/KPI/аванс — но **с привязкой к позиции**.
- **Расчёт идёт по КАЖДОЙ позиции отдельно** — своим окладом, графиком, нормой и коэффициентами. `calculate_position_payroll(employee, position, entries, ...)` — основная функция; `calculate_employee_payroll(employee, ...)` осталась тонкой обёрткой над ОСНОВНОЙ позицией (совместимость и одиночный случай).
- **«К выплате» между позициями НЕ суммируется** — платят разные компании. `/payroll`, `/statement` и дашборд отдают **строку на позицию**; `employee_id` в них повторяется, различает строки `position_id`. Общий итог по человеку можно показывать только справочно.
- **Compat-аксессоры**: старый «плоский» API карточки (`emp.rate`, `emp.schedule_id`, `emp.department_id`, `emp.default_company_id`, `emp.weekend_*`, ...) сохранён — это чтение и запись ОСНОВНОЙ позиции (`_position_field` в `models/employees.py`, список полей — `EMPLOYEE_COMPAT_FIELDS` в `models/positions.py`). Дублирующих колонок на `employees` **нет**: два места хранения оклада разъехались бы, и зарплата зависела бы от того, какое прочитали. `Employee.__init__` гарантирует основную позицию даже у сотрудника без единого «позиционного» поля.
- **Отдел — свойство позиции**, поэтому SQL-фильтры «сотрудники такого-то отдела» собраны в `app/services/positions.py` (`in_department` / `in_departments` через `Employee.positions.any(...)`). Прямого `Employee.department_id` в запросах больше нет — новые места делать только через эти функции. `Department.employees` / `Company.employees` / `Schedule.employees` стали **viewonly** через `employee_positions`.
- **Отпускные и больничные платит только ОСНОВНАЯ позиция** (task_positions_fixes п.1). Отсутствие отмечено на человеке — он отсутствует на всех работах, — но оплачивается по основной позиции, её окладу, норме и ГРАФИКУ (`оклад_основной / норма_основной × смены_графика × длина_смены`, см. task_vacation_shift_fix). На совместительстве дни отсутствия начислений не дают: платить отпуск с каждого рабочего места значило бы платить его N раз. Годовой лимит больничного (10 дней) — **на человека**, расходует его основная позиция. В строке доп. позиции остаются справочные `vacation_days` / `sick_days` (человек отсутствовал), а `*_paid_days`, `sick_unpaid_days` и суммы — нули. Гасится в одном месте — `pays_absences` в `calculate_position_payroll`.
- **Видимость**: менеджер (и табельщик) видит только рабочие места в СВОИХ отделах — подработка сотрудника в чужом отделе ему не показывается (`visible_positions`, роли из `DEPARTMENT_SCOPED_ROLES`). Период ищется по отделу ПОЗИЦИИ: подработку в другом отделе закрывает период того отдела.
- Часы/премии/проценты с `position_id IS NULL` — заведены до появления позиций и читаются как **основная позиция**; иначе миграция потеряла бы данные. Не обходить `Employee.position_by_id` и `services.positions.entries_by_position`.

### Три типа оплаты позиции (`pay_type`)

Тип задаёт расчёт базовой суммы и «единицу» надбавок (час у окладной/почасовой, целая смена у посменной); правила остаются общими — переработка по дням, категории дня из `day_category`, коэффициенты из карточки позиции. Отсутствия, премии, удержания и распределение от типа не зависят. Поля баз **взаимоисключающие** — при смене типа чужие гасятся (`_PAY_TYPE_BASE_FIELD` в роутере, `build_employee` в сервисе).

| Тип | База | Переработка | Отпуск/больничный |
|-----|------|-------------|-------------------|
| `salary` (окладная) | `rate × зачётные_часы / норма`, cap на оклад | по дням, `(оклад/норма) × часы × коэф.` | «оклад/норма × смены графика × длина смены» |
| `per_shift` (посменная) | `плановые_смены × shift_rate` | по дням, `max(0, часы_дня − смена) × (ставка_смены/часы_смены) × коэф.` | от условного оклада `ставка × норма смен` |
| `hourly` (почасовая) | `(факт − переработка) × hour_rate` | **по дням** (как окладная): `max(0, часы_дня − смена) × ставка × коэф.` | **не начисляются** |

- **Посменная = база + надбавки** (task_shiftpay_addons, разворот прежнего «у посменной надбавок нет»): база — смены **плановых дней графика** × ставка; смена в свой выходной/праздник — `ставка × коэффициент` карточки; часы сверх дневной нормы смены — переработка по дням от **часовой ставки** `shift_rate / hours_per_shift`. Подробности — ниже в разделе Payroll.
- Отличие почасовой от окладной: у окладника отработка нормы даёт **гарантированный** полный оклад, у почасовика — только фактические часы (отработал меньше нормы → пропорционально меньше).
- **Переработка почасовика — ПО ДНЯМ** (task_positions_fixes п.2), единообразно с окладной: `hourly_overtime_hours` в `app/services/payroll.py`. Помесячный вариант (`факт_месяца − норма_месяца`) откачен — он гасил переработку одного дня недоработкой другого. Дневная норма — длительность смены по графику позиции (`shift_hours_for_date`, у сокращённого дня −1), причём в **любой** день с часами, а не только в плановый: у почасовика нет категории «вне графика», иначе выход в свой выходной целиком стал бы переработкой ×1.5.
- У почасовика **нет** категорий «вне графика» и «праздничные»: каждый час уже оплачен по ставке, сверхнормативные — с коэффициентом. `rate` у него `None`.
- Почасовик в отпуске/болезни: код отсутствия ставится и виден в табеле, но денег не даёт (нет часов — нет оплаты).
- Не задана ставка за час → `is_calculable=False`, причина «Не задана ставка за час».

### Миграция

- Миграция `f1a2b3c4d5e6` создала каждому существующему сотруднику **ровно одну основную позицию** из его данных и привязала к ней часы, премии/KPI/аванс, займ (`employees.loan_position_id`) и проценты распределения. Колонки, уехавшие на позицию, с `employees` сняты. Проверено: downgrade → upgrade возвращает данные один в один, вся тестовая база проходит без правок.
- Уникальность ячейки табеля теперь `(employee_id, position_id, work_date, company_id)`; наборов процентов — с `position_id`.
- Вахта и роль табельщика к позициям отношения не имеют и здесь не делались.

## UI совместительства: позиции в карточке, табеле и ведомости (task_positions ч.B)

Часть A перевела на позиции расчёт, часть B — интерфейс. **Сотрудник с одной позицией везде выглядит ровно как до совместительства: одна строка, те же цифры.** Схема БД не менялась — новых миграций в части B нет.

### Карточка сотрудника: секция «Должности (позиции)»

- `pages/admin/PositionsEditor.tsx` внутри карточки: список рабочих мест (должность, тип оплаты, оклад/ставка, график, отдел, компания, коэффициент выходных, признак «основная»), добавление совместительства, редактирование, удаление, «Сделать основной». Три типа оплаты с соответствующим полем базы — поля взаимоисключающие, бэк гасит чужие при смене типа.
- **В режиме редактирования плоские поля карточки** (Структура / тип оплаты и база / коэффициенты выходных, праздничных, переработки) **скрыты** — это та же основная позиция через compat-аксессоры, и два места ввода одного оклада разъехались бы. При СОЗДАНИИ они остаются: там они заводят основную позицию.
- Эндпоинты (чтение — кто видит карточку, запись — только admin): `GET/POST /api/employees/{id}/positions`, `PATCH/DELETE /api/employees/{id}/positions/{pid}`, `POST /api/employees/{id}/positions/{pid}/make-primary`. `EmployeeRead.positions` отдаёт весь список.
- **Удаление**: основную и последнюю активную удалить нельзя (422). Позиция, на которой уже есть часы, премии или проценты, **не удаляется физически, а деактивируется** (`is_active=False`, ответ `{"result": "deactivated"}`) — иначе история табеля осталась бы без рабочего места. Чистая позиция удаляется (`"deleted"`). CRUD — `app/services/positions.py` (`create_position`, `apply_position_fields`, `set_primary`, `delete_position`, `position_usage`).
- Проценты распределения задаются **позиции**: `GET/PUT /employees/{id}/company-shares?position_id=`; в карточке при нескольких позициях появляется селектор рабочего места.

### Табель: строка на рабочее место

- **Строка табеля = сотрудник × позиция** в обоих видах. ФИО объединяется по строкам сотрудника через `rowSpan`; должность, отдел, график, часы, норма, Δ и весь денежный блок — **свои у каждой позиции**. В классическом виде добавлена колонка «Должность». В виде «по компаниям» уровня merge стало два: ФИО — на все строки человека, Должность/Отдел/График/Итого позиции — на строки компаний этой позиции.
- `GET /api/timesheet/{y}/{m}` отдаёт `positions_by_employee` — **только ВИДИМЫЕ актору** рабочие места (`visible_positions`): в табеле отдела видна только позиция этого отдела, менеджеру — только его отделов. Совместитель «инженер в ИТО + электрик в Комфорте» даёт по одной строке в каждом табеле. Полный список — в карточке.
- **Группировка по отделам идёт по отделу ПОЗИЦИИ, а не человека**, поэтому позиции одного сотрудника попадают в разные группы и под свои периоды. Из-за этого `rowSpan` ФИО считается внутри отрисовываемого списка (`withSpans` в `TimesheetPage.tsx`), а не заранее.
- Часы пишутся на конкретное рабочее место: `position_id` в `PUT /timesheet/cell` и в батче. Компания и длительность смены по умолчанию берутся из позиции. Ключи фронтовых индексов — `posKey(empId, positionId)` (`TimesheetPage.tsx`, там же `positionIdParam` и синтетическая позиция для ответа без `positions_by_employee`).
- **Код отсутствия — на человека целиком** (он отсутствует на всех работах): рисуется и снимается на первой его строке, на остальных день пуст.
- Премия / KPI / аванс адресуются рабочему месту, на котором заработаны (`position_id` в `POST /timesheet/adjustments`), и попадают в «к выплате» именно этой строки. Модал показывает, какому месту начисляет.
- `_check_cell_access` в `routers/timesheet.py` проверяет отдел **позиции**: с `position_id` — её отдел, без — достаточно доступа к любому рабочему месту сотрудника (иначе менеджер не смог бы править того, чья основная позиция в другом отделе).
- Автозаполнение уже в части A идёт по графику каждой позиции — UI ничего не меняет.

### Ведомость и Excel

Три уровня merge: employee-level (№, Таб.№, ФИО, дни отпуска/больничного, Итого Ч сотруд.), position-level (Подразделение, Должность, График, Норма дней/часов, Факт дней, ФАКТ ч/мес), row-level (Компания, дни, Итого Ч компании, Сверхур./Вне граф./Празд. ## Timesheet Periods

- Workflow: `draft → pending_review → closed`; возвраты: `pending_review → draft` (accountant+admin), `closed → draft` (только admin)
- Все возвраты и переоткрытие — обязательный `reason` (≥3 символа), audit log
- Период привязан к `(department_id, year, month)`. NULL department_id — отдельная группа «Без отдела»
- Ячейки (cells) можно редактировать **только в draft**. Admin тоже подчиняется — должен reopen чтобы править
- Период создаётся lazy при первом GET месяца (`get_or_create_period`)
- NULL-department: accountant может закрыть сразу из draft (нет manager-а, pending_review пропускается)
- Partial unique index в PG: один период на (department_id, year, month), NULL обрабатывается отдельным index

## Payroll (расчёт ЗП)

- Считаем **брутто к начислению** — НДФЛ/страховые/премии/авансы — задача 1С
- **Только `Decimal`**, никаких `float`. Округление `ROUND_HALF_EVEN` до целых рублей.
- **Тип оплаты — у ПОЗИЦИИ** (`EmployeePosition.pay_type`, см. раздел «Совместительство»; было `Employee.pay_type`, task_search_and_shiftpay). Третий тип `hourly` описан там же. Тип задаёт базовую сумму и «единицу» надбавок (час / целая смена), правила общие: переработка по дням, категории дня из `day_category`, коэффициенты из карточки. Отсутствия, премии, KPI, удержания и распределение по юрлицам от типа не зависят:
  - **`salary`** (дефолт) — месячный оклад `rate`, база пропорционально отработанному (см. ниже);
  - **`per_shift`** — оклада нет, есть `shift_rate`: **база = смен ПЛАНОВЫХ дней графика × ставка** (`base_shifts` в ответе; `worked_shifts` — все отработанные смены, включая выходные). Не задана ставка → `is_calculable=False`.
  - **Надбавки посменного** (task_shiftpay_addons — разворот прежнего решения «у посменной надбавок нет»; в старых коммитах категории обнулялись):
    - **смена в свой выходной по графику / в праздник** — `ставка_за_смену × коэффициент` из карточки позиции (тот же `weekend_*` / `holiday_*`, что у окладника, дефолт 1.5). Коэффициент применяется к **ЦЕЛОЙ смене**, а не по часам: 4 часа в выходной стоят столько же, сколько 8. Исключение — `fixed_rate`: фикс-ставка задаётся ЗА ЧАС, поэтому у всех типов оплаты считается по часам.
    - **переработка** — ПО ДНЯМ, как у окладной: `max(0, часы_дня − дневная_норма) × часовая_ставка × overtime_coefficient`, суммируется за месяц. Категории дня — общие (`day_category`), поэтому переработка идёт только по плановым дням: часы выходной смены уже оплачены целиком по коэффициенту.
    - **часовая ставка посменного** — `per_shift_hourly_rate(position, schedule)` = `shift_rate / hours_per_shift` **графика позиции** (6/1 → 9 ч, 2/2 → 12 ч; 4000/9 = 444.44), без сокращения предпраздничного дня: это ставка сотрудника, а не свойство даты. Не путать с `EmployeePayroll.hourly_rate` — там условный оклад / норма часов, от него считаются отпускные и больничные.
    - Определение «выходной/праздник по графику» — та же `day_category` для всех типов оплаты, дублирования нет.
  - **Отсутствия посменного** считаются по той же формуле, что у окладника, но от **условного оклада** = `shift_rate × норма_смен_месяца` (`notional_salary`; норма смен — `norm_days_for_schedule`, то есть плановые смены по графику). Считается на лету, отдельным полем НЕ хранится — норма смен разная от месяца к месяцу. В `EmployeePayroll.rate` у посменного лежит именно условный оклад; что это за число, видно по `pay_type`.
  - Поля ответа: `pay_type`, `shift_rate`, `worked_shifts`, `norm_shifts`. Оклад и ставка взаимоисключающие — при смене типа роутер гасит поле чужого типа, иначе расчёт молча возьмёт не то.
- **Переработка ПО ДНЯМ** (task_overtime_daily — финальное решение, откат помесячного варианта 3.11b п.0): для каждого дня `max(0, факт_дня − дневная_норма)`, суммируется за месяц. Часы всех компаний в дне складываются. Дневная норма = `hours_per_shift`, у сокращённого дня `hours_per_shift − 1`, у дня **вне графика и праздничного** 0. Недоработка одного дня НЕ гасит переработку другого. Часы вне графика — отдельная категория, в зачётные часы и в переработку НЕ входят. Хелперы: `daily_norm_hours` / `daily_overtime_hours` в `app/services/payroll.py` (оба принимают `schedule`).
- **База оклада** от зачётных часов рабочих дней графика: `base = rate × min(1, зачётные / norm)`, где зачётные = `Σ min(факт_дня, дневная_норма)` (= часы рабочих дней графика − переработка). Часы вне графика в базу НЕ входят.
- `overtime = overtime_hours × (rate/norm) × коэффициент`, где коэффициент — поле ПОЗИЦИИ `overtime_coefficient` (0/1/1.5, дефолт 1.5).
- **ТРИ непересекающиеся категории часов** — `day_category(schedule, date, calendar_data)` в `work_schedule.py`, единственный источник правды (её же используют Excel-экспорт и ведомость):
  - **`planned`** — день входит в план сотрудника: часы до дневной нормы в оклад, превышение смены — переработка;
  - **`holiday`** — день в план НЕ входит и является нерабочим **праздничным** по календарю: ВСЕ часы дня — праздничные, per-employee `holiday_pay_type / holiday_coefficient / holiday_fixed_rate`, дефолт 1.5 (как у выходных; точная ставка задаётся в карточке сотрудника);
  - **`off_schedule`** — день в план не входит и праздником не является (свой законный выходной): ВСЕ часы — «вне графика», per-employee `weekend_pay_type / weekend_coefficient / weekend_fixed_rate`, дефолт 1.5.
  - **Приоритет праздника выше выходного**: выход 12 июня — это работа в праздник, независимо от того, выходной это по графику или нет.
  - У **сменщика** праздник, попавший НА ЕГО СМЕНУ, остаётся `planned` — норма по циклу (180 ч) эту смену уже содержит, вынести её в праздничные значило бы урезать оклад. Праздник на выходном цикла → праздничные.
  - «Праздник» отличается от обычного выходного эвристикой `is_public_holiday` (`services/calendar.py`): нерабочий **будний** день календаря — праздник или перенос, нерабочая Сб/Вс — обычный выходной. xmlcalendar праздники отдельно не размечает (`+` = перенесённый выходной, а 12 июня стоит обычным числом), поэтому иначе их не отличить.
  - Часы `holiday` и `off_schedule` в зачёт оклада и в переработку НЕ идут: у такого дня дневная норма 0.
- **«Рабочий день по графику»** — `app/services/work_schedule.py`, единственный источник правды (используют payroll, автозаполнение, Excel-экспорт, превью): `is_schedule_work_day(schedule, date, calendar_data) -> bool | None` и обёртка `is_off_schedule_day(...) -> bool`. Виды графиков, план vs оплата и расчёт нормы — в разделе «Графики работы: weekday и cyclic».
- **Имена полей**: `off_schedule_hours / off_schedule_amount` — вне графика, `holiday_hours / holiday_amount` — праздничные. До task_holiday_pay `holiday_*` означало «вне графика» — при чтении старых коммитов и дампов это надо держать в голове. Подписи в UI и Excel: «Вне граф.» и «Праздн.».
- `norm_days` (плановых рабочих дней/смен по графику) и `fact_days` (дней с часами) — справочные, в деньгах не участвуют.
- **Месячная норма часов — по ГРАФИКУ** (task_shift_schedules), `norm_hours_for_schedule`: weekday-график считает её по производственному календарю с учётом своих дней недели, cyclic — по циклу (2/2 июнь 2026 → 180 ч, не 167). `norm_hours_for_period` в `services/calendar.py` остался только для справочных данных календаря (`/api/calendar/...`), в payroll не используется.
- `is_calculable=True` для сменных графиков с анкером цикла. Не считается: нет графика, сменный без `cycle_start_date`/паттерна, weekday без производственного календаря (норма была бы завышена — сменному календарь не нужен), нет оклада, норма 0.
- Распределение по компаниям (`CompanyBreakdown`): base/overtime ₽ — пропорционально всем часам; off_schedule ₽ и holiday ₽ — пропорционально часам СВОЕЙ категории (то есть туда, где реально отработано). Поля per-company: `hours`, `percent`, `overtime_hours`, `off_schedule_hours`, `holiday_hours`, `base_amount`, `overtime_amount`, `off_schedule_amount`, `holiday_amount`, `total`. `off_schedule_hours`/`holiday_hours` — точные, `overtime_hours` — пропорционально часам (метод наибольших остатков, сумма = итог).
- **Сумма частей по компаниям сходится с итогом точно** — распределение через `_distribute_whole_rubles()` (метод наибольших остатков: floor долей + остаток рублей компаниям с наибольшими дробными остатками, тай-брейк по company_id). НЕ округлять доли независимо — даёт расхождение до ±N/2 руб. на категорию.
- Видят только admin / accountant / **manager** (свои отделы, см. раздел «Оргструктура»). На бэке принудительная проверка — игнорировать `?include_payroll=true` от employee.
- **Головная компания отдела на расчёт не влияет вообще.** Компании берутся из часов табеля и процентов распределения; отдел в дереве — только навигация. Не завязывать распределение на `Department.head_company_id`.
- Отдел с флагом «распределение по заявкам» каскад НЕ использует — см. «Распределение по заявкам на подбор».
- Эндпоинт: `GET /api/timesheet/{year}/{month}/payroll`, параметр `?include_payroll=true` у основного GET.
- Сервис: `app/services/payroll.py` — чистая функция `calculate_employee_payroll`, не лезет в БД.
- Фронт: Decimal с бэка приходят как строки; `formatMoney()` / `formatHours()` в `frontend/src/utils/money.ts`.

## Отсутствия: коды ОТ / ДО / Б / Н (task_absences_part1)

- Модель `EmployeeAbsence` (`app/models/employee_absences.py`): `(employee_id, work_date, kind)`, unique на день, `kind ∈ {vacation, unpaid, sick, absent}` → коды **ОТ / ДО / Б / Н** (`ABSENCE_CODES` — единый источник для API, UI и Excel). Отсутствие на **весь день**, к юрлицу НЕ привязано.
- **Взаимоисключение часы/код**: в дне либо часы (возможно по нескольким компаниям), либо один код. Постановка кода удаляет часы дня, ввод часов снимает код — обе стороны в `app/services/absences.py` и `upsert_cell`, удаления пишутся в audit log. Никогда не обходить эти две функции при мутации. **Ночные смены дня код тоже снимает** (и наоборот — на день с кодом ночную не отметить, 422): см. «Ночные смены».
- Эндпоинт `PUT /api/timesheet/absence` (`kind=null` — снять), права как у ячейки часов, период должен быть в **draft**. Коды в `GET /{y}/{m}` → поле `absences` — видны всем ролям (employee видит свои), финансы отсутствий — только admin/accountant/manager.
- **Оплата** (`absence_pay` в `app/services/payroll.py`): `оклад / норма_часов × часы_отсутствия`. ОТ → `vacation_amount`, Б → `sick_amount`. ДО и Н — 0, только отметка.
- **Часы отсутствия = рабочие СМЕНЫ ГРАФИКА в периоде × длина смены** (task_vacation_shift_fix), а не «календарные дни × 8»:
  - какие дни периода оплачиваются, решает `is_payable_absence_day(work_date, calendar_data, schedule)` в `app/services/absences.py` — она зовёт **ту же** `is_planned_work_day` из `work_schedule.py`, что считает норму и автозаполнение. Логика графиков не дублируется;
  - длина смены — `absence_day_hours(schedule)` = `hours_per_shift` **графика позиции** (5/2 → 8, 6/1 → 9, 2/2 и 3/1 → 12). Не хардкодить 8; сокращение предпраздничного дня к отсутствию НЕ применяется — это ставка сотрудника, а не свойство даты;
  - у сменщика **выходные цикла не оплачиваются**: отпуск 14 календарных дней на 2/2 — это 7 смен × 12 ч = 84 ч, а не 14 × 8. Праздники календаря смену цикла не отменяют (у cyclic календарь на план не влияет);
  - **5/2 по 8 ч не изменился**: плановые дни графика для пятидневки — это ровно рабочие дни производственного календаря (включая «рабочую субботу»-перенос), а смена = 8 ч. Проверено на dev-базе: 161 сотруднико-месяц с ОТ/Б на 5/2 — расхождений нет; изменились только cyclic и 6/1 (там смена 9 ч и суббота рабочая);
  - графика нет → старое правило (рабочий день календаря × 8 ч); такая позиция всё равно `is_calculable=False` и денег не даёт.
- **Платит только ОСНОВНАЯ позиция** (task_positions_fixes п.1): у совместителя отпускные/больничные начисляются один раз, с основного рабочего места; лимит больничного — на человека. Подробности — в разделе «Совместительство».
- **Годовой лимит больничного** (часть 2): первые `SICK_LEAVE_LIMIT_DAYS` (настройка, дефолт **10**) оплачиваемых дней Б в календарном году — 100%, дальше 0 (за свой счёт). Считается **хронологически по дате** в `split_sick_dates_by_limit` (`app/services/absences.py`): правка задним числом в ранний месяц съедает лимит раньше, поздние месяцы пересчитываются сами — состояние лимита в БД НЕ хранится. Расходуют лимит только оплачиваемые дни, то есть **рабочие смены графика**: Б на выходном (у сменщика — на выходном цикла) отмечен, но денег не даёт и лимит не жжёт. График для этого берётся у ОСНОВНОЙ позиции — `schedules_by_employee` в `services/absences.py`, его передают `sick_days_used_before_month` и `over_limit_sick_dates` (иначе «израсходовано до месяца» считалось бы по календарю, а текущий месяц — по графику, и лимит поехал бы). Учитываются все отметки года независимо от статуса периода (факт болезни есть). Смена года обнуляет счётчик, приём в середине года лимит не урезает.
- Поля лимита: `sick_limit_days`, `sick_days_used_before` (израсходовано до месяца, считает `sick_days_used_before_month`), `sick_unpaid_days` (сверх лимита в этом месяце), `sick_limit_remaining`. В `GET /{y}/{m}` каждая отметка Б несёт `over_limit` (`over_limit_sick_dates` — по всему году), поэтому ячейка знает про лимит, не считая его сама. UI: «Б*» пунктиром, «N б/о» в колонке, остаток лимита в подсказке и в ведомости.
- Платим только за **рабочие дни по графику сотрудника**: `*_days` — сколько дней отмечено кодом, `*_paid_days` — сколько из них рабочих смен графика (за них деньги). Код на выходном виден в табеле, но не оплачивается — иначе оклад за отработанное + отпускные вылезут за полный оклад.
- **Оклад пропорционален отработанному** и это следует из существующей формулы: `base = rate × зачётные_будние_часы / норма`. В дне отсутствия часов нет → оклад за него не начисляется, он оплачивается отпускными/больничными. Ни задвоения, ни потери: оклад 50000 / норма 167ч / 5 дней ОТ → 38024 (оклад) + 11976 (отпускные) = 50000.
- **Норма не меняется** от отсутствий (это плановые часы месяца). Переработка тоже не затрагивается: дни отсутствия часов не дают, а расчёт по дням идёт по дням с часами.
- `total_amount` = оклад + переработка + часы вне графика + отпускные + больничные + **надбавка за ночные смены** (см. «Ночные смены»: она не зависит от графика и считается отдельно). `breakdown_by_company` остаётся **только по рабочим категориям** — разнесение отпускных по юрлицам делает ведомость (проценты каскада), само отсутствие к юрлицу не привязано.
- Excel Т-13: код в ячейке дня вместо часов (на первой строке сотрудника), колонки «Кол-во дней отпуска/больничного» заполнены, внизу легенда кодов. Сотрудник без часов, но с отсутствиями, в табель попадает.

## Премии, KPI, удержания и «К выплате» (задача 3.11a)

- **НЕ сделано здесь (задача Б):** отдельная ведомость «Расчёт ЗП» и распределение по компаниям в %.
- **Премии / KPI / аванс** — `EmployeeAdjustment` (`app/models/employee_adjustments.py`): `(employee_id, year, month, kind, amount, reason, created_by)`. `kind ∈ {premium, kpi, advance}`. Обоснование (`reason`) обязательно (≥3 симв.), `amount > 0`. Несколько записей за месяц суммируются по типу. Аванс — удержание (вычитается).
- **Займ** — поля в карточке сотрудника: `loan_amount`, `loan_term_months`, `loan_start_date`. Гасится равными долями `доля = round(сумма / срок)` автоматически с месяца начала. Остаток **считается на лету** = `сумма − Σ фактически удержанное` (не хранится отдельным полем, чтобы не рассинхронить).
- **Ручная правка займа за месяц** — `LoanDeduction` (`app/models/loan_deductions.py`): строка существует ТОЛЬКО при override бухгалтером (`actual_amount` + справочный `planned_amount`). Для месяцев без строки удержание = плановая доля, считается на лету.
- Чистая функция `loan_month_state(...)` в `app/services/payout.py` итерирует месяцы от старта: последний месяц добивает остаток (если он меньше доли), override не может превысить остаток (досрочное погашение), недоудержание продлевает срок. Возвращает `None` если займа нет или месяц раньше старта.
- **Формула:** `К выплате = начислено (оклад+переработка+вне графика) + премии + KPI − (доля займа + аванс)`. `compute_payout(...)` — чистая. Все суммы Decimal, ROUND_HALF_EVEN.
- **Округление «К выплате» вниз до 100 ₽** (task_payout_rounding): финальная сумма каждого сотрудника округляется floor-ом до сотни — `floor_to_payout_step` в `app/services/payout.py`, единственное место округления (110407 → 110400, 26826 → 26800). Округляется ТОЛЬКО итог: оклад, премии, удержания и всё промежуточное остаётся точным. Отрицательная сумма (удержали больше начисленного) не округляется — floor утянул бы её дальше в минус, а хвост обязан быть ≥ 0.
  - `net_payout` — округлённая (это и есть выплата, её показывают табель, ведомость и Excel), `net_payout_exact` и `rounding_tail = точное − округлённое` — справочные поля ответа. Хвост никуда не переносится.
  - **Итог — Σ округлённых выплат, а не округление суммы**: `total_net_payout` складывает уже округлённые строки (`total_net_payout_exact` / `total_rounding_tail` — рядом, справочно). Фронт (табель, ведомость) суммирует строки так же.
  - Округление к выплате **не участвует в распределении по юрлицам**: база распределения — Итого начислено (ДО удержаний), см. раздел 3.11b. Не путать с методом наибольших остатков в `services/distribution.py` — это разные округления.
- Эндпоинты (в `routers/timesheet.py`, права admin/accountant/manager своего отдела; employee — 403): `GET /{y}/{m}/adjustments`, `POST /adjustments`, `DELETE /adjustments/{id}`, `POST /loan-override`, `DELETE /loan-override/{emp}/{y}/{m}`. Поля payout и коэффициент отдаются в `EmployeePayrollRead` + суммы в `PayrollSummaryRead`. Adjustments также включены в `GET /{y}/{m}` (только для финансовых ролей).
- **Коэффициент** (п.3) — отображение `weekend_pay_type/coefficient/fixed_rate` в колонке «Коэф.» (`fmtCoeff` во фронте), не редактируется в табеле (только в карточке).
- Фронт: классический `TimesheetPage` — колонки Коэф. / **Премия** / **KPI** (раздельные: у сотрудника может быть и то, и другое) / Удержано / К выплате + `AdjustmentsModal` (добавление с обоснованием, правка займа). Вид «по компаниям» эти колонки пока не показывает.

## Ведомость «Расчёт ЗП» + распределение по юрлицам (задача 3.11b)

- **Единый источник расчёта**: `build_payroll_summary` вынесена в `app/services/payroll_statement.py`; и табель (`/payroll`), и ведомость (`/statement`) считают через неё — формулы НЕ дублируются (роутер делегирует тонкой обёрткой).
- **Округление распределения — ОДНО место: `app/services/distribution.py`** (task_distribution_v2 ч.1). `distribute(total, weights, main_key, step)`: точная доля → округление до шага (ROUND_HALF_EVEN) → весь остаток на **основную компанию** сотрудника (нет её в наборе — на компанию с наибольшей долей). Сумма частей ровно = итог. `split_equally(ids, main_key)` — «Разнести поровну» (100% между отмеченными галочками компаниями, ч.2). Фронт **зеркалит** алгоритм в `frontend/src/utils/distribution.ts` (живой пересчёт при вводе %) — правишь одно, правь второе, иначе экран и Excel разъедутся снова. Excel не считает суммы сам — берёт из того же `build_payroll_statement`.
- **Каскад приоритетов распределения** (ч.3), `resolve_shares` в `payroll_statement.py` — берётся ПЕРВОЕ заданное (кроме отделов «по заявкам»: у них каскада нет вовсе, см. отдельный раздел): `месячный override` (`CompanyShareOverride`) → `карточка сотрудника` (`EmployeeCompanyShare`) → `дефолт отдела` (`DepartmentCompanyShare`, `PUT /api/departments/{id}/company-shares`, admin) → `авто по часам табеля`. Уровень отдаётся в `StatementRow.distribution_source` (`month|employee|department|hours`) и виден в ведомости и в примечании Excel. Дефолт отдела применяется ТОЛЬКО к сотрудникам без своего распределения. Наборы процентов грузит `app/services/company_shares.py` (там же общая валидация ≈100%).
- **Распределение затрат по юрлицам в %** — управленческое. Уровни каскада (гибрид как у займа: строки существуют ТОЛЬКО там, где что-то задано):
  - `CompanyShareOverride (employee_id, company_id, year, month, percent)` — правка в ведомости на конкретный месяц; есть хоть одна строка за месяц → берётся весь набор override;
  - `EmployeeCompanyShare (employee_id, company_id, percent)` — распределение в карточке сотрудника;
  - `DepartmentCompanyShare (department_id, company_id, percent)` — дефолт отдела, наследуют только сотрудники без своего распределения;
  - валидация суммы ≈100% (99–101) — общая для карточки и отдела, `validate_shares` в `app/services/company_shares.py`.
- **Авто-распределение по часам — нижний уровень каскада** (task_distribution_fix): если % не задан НИ на одном уровне (override / карточка / отдел) → «Итого начислено» распределяется пропорционально фактическим часам сотрудника по компаниям из табеля (`_auto_shares_by_hours`, тот же `distribute`). Любой заданный уровень выше перекрывает авто; очистка уровня возвращает к следующему (карточка → отдел → авто). Нет часов и нет % нигде → вся сумма на `default_company`. Флаги `StatementRow`: `distribution_source` (`month|employee|department|hours`) и `is_auto_distributed` = `source == "hours"` (оба — Pydantic-поля ответа, не колонки БД). Excel: авто-строки не помечаются «≠100%», в примечании — подпись уровня каскада. Фронт: авто-строки не префилл, плейсхолдер вычисленного %, пунктир/серый курсив; под кнопками строки — пометка уровня.
- **База распределения = Итого начислено** (оклад+праздн.+переработка+премии+KPI, ДО удержаний). `сумма_компании = Итого_начислено × %`, точная сумма через `distribute_by_percent` (тот же `_distribute_whole_rubles`, нормализует если Σ%≠100).
- **Итого начислено** в ведомости = `base_salary (оклад+вне графика) + переработка + отпускные + больничные + ночные + премия + KPI`; **К выплате** = Итого начислено − удержания (= `net_payout` из табеля).
- Эндпоинты (admin/accountant — все; manager — свой отдел; employee — 403): `GET /timesheet/{y}/{m}/statement`, `PUT /timesheet/distribution`, `DELETE /timesheet/distribution/{emp}/{y}/{m}`, `GET /timesheet/{y}/{m}/statement/export/excel` (файл `vedomost_{y}_{mm}.xlsx`). Дефолт-проценты в карточке: `GET/PUT /employees/{id}/company-shares`.
- Excel: `app/services/payroll_statement_export.py` → `generate_statement_excel(statement) → bytes`. Формат — по эталонному файлу финдира (шапка, состав и порядок колонок, итоги сверху и снизу): см. «Порядок юрлиц, их названия и формат Excel-ведомости».
- **Обоснования премий/KPI/удержаний в выгрузке** (task_ux_improvements ч.1b). Единственное поле с комментарием в системе — `EmployeeAdjustment.reason` (обязательное, у премии, KPI и аванса); у займа своего обоснования НЕТ, помечается только ручная правка удержания (`loan_note`, с плановой долей). Тексты грузит отдельный `load_adjustment_reasons` — суммирующий `load_adjustment_sums` участвует в расчёте и не трогается. В `StatementRow` это **списки** `premium_reasons` / `kpi_reasons` / `advance_reasons` вида «5000 ₽ — за объект А»: за месяц записей может быть несколько, и одна сумма без разбивки цифру не объясняет. В Excel — три **хвостовые** колонки «Обоснование премии/KPI/удержаний» (в середину не вставлять: в шаблоне финдира зафиксированы буквы колонок) плюс те же тексты примечанием к самим суммам. На экране ведомости — подсказка к сумме.
- Фронт: `PayrollPage` — сводная ведомость с редактируемыми процентами по компаниям (живой пересчёт сумм, подсветка Σ%≠100, сброс переопределения), кнопка выгрузки в Excel. Карточка сотрудника: `overtime_coefficient` + `CompanySharesEditor` (проценты по умолчанию).

## Распределение по заявкам на подбор: отдел HR (task_hr_applications)

Отдел с флагом **«распределение по заявкам»** делит зарплату своих сотрудников между юрлицами не каскадом процентов, а **по числу отработанных за месяц заявок на подбор**. Придумано для HR, но привязано к флагу, а не к имени отдела.

- **Признак — `Department.uses_applications_distribution`** (Boolean, server_default **false**, миграция `c9d0e1f2a3b4`), правит admin: `PATCH /api/departments/{id}` и галочка в карточке отдела в «Оргструктуре». Хардкода имени «HR» в коде нет и быть не должно: сегодня это HR, завтра — любой другой отдел, а имя отдела переименуют и правило молча отвалится.
- **Заявки — помесячные**: `DepartmentApplication` (таблица `department_applications`, unique `(department_id, company_id, year, month)`), заявки отдела для каждого юрлица за конкретный месяц. Заводятся заново каждый месяц; строки с нулём **не хранятся** — «компания без заявок» и «0 заявок» одно и то же состояние, два способа его записать неминуемо разъехались бы.
- **Хранятся ДВЕ части — `in_progress` («в работе») и `closed` («закрытые»), как в исходном файле HR**; «Заявок» = их сумма и **считается** (`DepartmentApplication.count` — property, не колонка), а не хранится третьим полем: иначе итог и разбивка живут отдельно и однажды перестанут сходиться. Миграция `d0e1f2a3b4c5` (после `c9d0e1f2a3b4`) заменила прежнюю колонку `count` на две; заведённые до неё заявки стали «в работе».
- **Распределение считается от ОБЩЕГО числа** (в работе + закрытые): обе части равноправны, отдел отработал их все. Как заявки разложены на части, на суммы не влияет — это проверяется тестом.
- **Проценты вычисляются, вручную не задаются**: `процент = заявки компании / сумма заявок` (пример из файла HR: ЗМО 16 из 43 → **37.21%**). Набор **единый на весь отдел**: заявки отработаны отделом, поэтому и рекрутёр, и руководитель HR делятся по одним и тем же процентам, а отличаются только суммами.
- **Заявки ЗАМЕНЯЮТ каскад целиком**, а не встают его очередным уровнем: у отдела с флагом ни месячный override, ни проценты карточки, ни дефолт отдела, ни авто по часам не применяются. Ветка стоит **выше** `resolve_shares` в `build_payroll_statement`, `distribution_source` = **`applications`**.
- **Суммы считаются от ЧИСЛА заявок, а не от округлённого процента**: `distribute(начислено, {компания: заявок}, основная_компания)` — `distribute` сам нормализует веса, поэтому доля = `начислено × заявки / Σзаявок` точно. 320000 × 16/43 = 119069.77 → **119070 ₽** (шаг округления — рубль, как во всём распределении); от 37.21% вышло бы 119072. Округление и «остаток — основной компании» — тот же единственный `app/services/distribution.py`, второй реализации нет.
  - Проценты для показа считаются **тем же** методом наибольшего остатка (`distribute(100, заявки, main_key=None, step=0.01)`), поэтому в сумме ровно 100.00. `main_key=None` здесь обязателен: с основной компанией сотрудника набор перестал бы быть общим на отдел.
- **Заявки за месяц не заведены → обычный каскад + предупреждение** (`StatementRow.distribution_note`, в ведомости «⚠ заявки не заданы», в Excel — текстом в примечании). Молча обнулять распределение отдела нельзя: включённый флаг не должен ломать расчёт месяца, в котором заявки ещё не ввели.
- **Отделы без флага не затронуты вообще** — каскад работает как раньше, `distribution_note` у них пуст.
- Сервис — `app/services/applications.py` (загрузка заявок, проценты, состояние для API); суммы там НЕ распределяются, это остаётся в `distribution.py`.
- Эндпоинты (права как у распределения: admin/accountant, manager — свои отделы; **табельщик и employee — 403**): `GET /api/timesheet/{y}/{m}/applications` (только отделы с флагом; отдел с флагом и без заявок приходит с `is_empty=true` — иначе блок ввода негде показать), `PUT /api/timesheet/applications` (полный набор за месяц; отдел без флага — **422**). Заявки приходят и вместе с табелем: `GET /timesheet/{y}/{m}` → `applications`. От статуса периода не зависят: это правило разнесения затрат, а не факт времени.
- **UI повторяет исходный файл HR** — и заявки, и суммы распределения видны в самом табеле:
  - **Блок «📋 Заявки на подбор»** над таблицей (`components/ApplicationsPanel.tsx`), **сворачиваемый и по умолчанию свёрнутый** (вместе с колонками распределения занимал пол-экрана; развёрнутость хранится в `UI_KEYS.timesheetApplications`, свёрнутый заголовок показывает отдел, число заявок и распределённую сумму). Свёрнутый блок остаётся смонтированным и прячется **классом** `hidden`, а не атрибутом: размонтирование стёрло бы набранные, но не сохранённые цифры, а `display:flex` из класса перебивает правило браузера для `[hidden]`. Внутри — таблица с колонками юрлиц и строками **«в работе» / «закрытые» / «Заявок»** (сумма, только для чтения) / **«% распределения»** / **«Сумма ₽»** — как шапка в файле. Заголовки колонок — **названиями юрлиц**, не кодами (`utils/companies.ts` снимает правовую форму и кавычки: «ООО "Комфорт"» → «Комфорт», полное имя остаётся в подсказке); оттуда же заголовки колонок распределения в табеле. Процент пересчитывается **на фронте тем же алгоритмом** (`utils/distribution.ts` — зеркало `services/distribution.py`), поэтому цифра совпадает с той, по которой реально разнесётся зарплата, ещё до сохранения. Суммы, в отличие от процентов, приходят с бэка.
  - **Колонки «Распределение» в классическом табеле** (юрлица + ИТОГО, хвостом после денежного блока) — сумма на каждое рабочее место и строка итогов в подвале. Появляются **только** в отделе с флагом и только у ролей, видящих деньги; видимость завязана на сами заявки (`applications`), а не на присланные суммы, иначе колонки прыгали бы после каждой правки часа. В виде «по компаниям» блока нет (как премий и ночных).
  - Суммы для табеля считает бэк — `build_applications_distribution` в `payroll_statement.py`, поверх уже посчитанного `build_payroll_summary` теми же `accrued_total` и `distribute`, что и ведомость. Фронт «Итого начислено» из кусков расчёта **не пересобирает**: разъехалось бы с `/statement`. Приходят в `GET /timesheet/{y}/{m}` полем `applications_distribution` (пусто без `include_payroll` — при частичном обновлении фронт сохраняет прежние, как и `payroll`).
  - **`accrued_total(p)`** в `payroll_statement.py` — единственное место формулы «Итого начислено» (база распределения). Раньше она была инлайном в ведомости; теперь ею считают и ведомость, и табель.
- В ведомости строки такого отдела **только показываются**: проценты не префиллятся, инпуты заблокированы, кнопок «Сохр./↺» нет — правка здесь создала бы месячный override, который заявки всё равно перекрывают. Править — в табеле отдела.
- Дополнительных расходов (отдельный блок) задача не делала — только заявки.
- **Флаг по умолчанию ВЫКЛЮЧЕН** (`server_default false`): после деплоя ни один существующий отдел «по заявкам» не распределяется, галочка в «Оргструктуре» снята, пока её не поставят руками.
- Тесты — `backend/tests/test_hr_applications.py` (32 шт.): проценты из заявок и сумма ровно 100, 320000 × 16/43, единые проценты у всех сотрудников отдела, замена каскада, помесячность (май ≠ июнь), fallback без заявок, API (замена набора, нули не хранятся, отдел без флага 422, табельщик и чужой менеджер), флаг отдела и его сохранность при правке соседних полей, «Заявок» = сумма частей, независимость сумм от раскладки на «в работе/закрытые», блок распределения в табеле (и что он совпадает с ведомостью, пуст без расчёта и отсутствует у других отделов).

## Порядок юрлиц, их названия и формат Excel-ведомости (task_vedomost_format)

### Порядок компаний настраивается и применяется ВЕЗДЕ (ч.1)

- **`Company.sort_order`** (Integer, `server_default 0`, миграция `f2a3b4c5d6e7`) —
  порядок перечисления юрлиц. Правит admin в «Оргструктуре»: стрелки **▲▼** на узле
  компании (`PUT /api/companies/order` — присылается ПОЛНЫЙ порядок id) и числовое
  поле «Порядок в списке юрлиц» в форме компании.
- **Единственный источник правды — `app/services/company_order.py`.** `company_order_by()`
  (ORDER BY для запросов), `company_sort_key` / `sort_companies` (объекты),
  `sort_company_ids` (голые id + справочник), `order_index` (id → место, когда под
  рукой только id). Сортировок `order_by(Company.id)` и `sorted(company_ids)` по месту
  в коде больше нет — они молча разошлись бы с настройкой, а вместе с ними уехал бы и
  **цвет компании**: он берётся по индексу в списке (`companyColorByIndex`).
- Второй ключ сортировки — **id**: он разводит компании с одинаковым `sort_order`
  (после ручного ввода числа такое штатно). Поэтому «поставить 1», когда единица уже
  занята, ставит компанию ПОСЛЕ неё, а не перед.
- **После любой правки порядка значения нормализуются в плотный 1..N** (`_renumber`
  в `routers/companies.py`): и перестановка стрелками, и ручной ввод. Иначе дубли и
  дыры копились бы, и следующая правка попадала бы не туда, куда целился админ.
  **Новая компания встаёт в конец** — вклиниваться в настроенный порядок она не должна.
- Порядок применён: справочник, табель (колонки, чипы, доп. юрлица сотрудника, блок
  «по компаниям»), ведомость и её Excel, Т-13 (строки юрлиц внутри блока позиции),
  дашборд (итоги по юрлицам), заявки на подбор, дерево оргструктуры.
- **Дефолт миграции — `sort_order = id`**: порядок выдачи (он был по id) сохраняется
  один в один, после деплоя ни один экран не меняется. Нужный порядок
  (ЗМО → СД → Комфорт-Эксплуатация → Комфорт-Сервис → Комфорт-Секьюрити → ГХС)
  выставляется в справочнике руками.
- `calculate_position_payroll` осталась **чистой функцией**: порядок она берёт из
  порядка ключей переданного `companies_by_id` (он приходит из запроса с
  `company_order_by()`), в БД за ним не ходит.

- Юрлицо без доли пишется **нулём, а не пустой ячейкой** (так в образце: по строке

  `**bold**` / `*italic*` / `` `code` ``.
- **Оглавление** вставляется полем TOC на месте ПЕРВОЙ `---` (она считается концом
  титульного блока) и обновляется при открытии файла — в документе без `---`
  оглавления не будет.
- Поля страницы 1,6 см и шрифт таблиц 8,5 пт подобраны так, чтобы 7-колоночные
  таблицы ТЗ влезали в портретную A4. Уменьшать поля дальше — рассыпается печать.
- Markdown разбирается **своим** парсером (pandoc в окружении нет): подмножество

- Проверка результата после генерации — числом таблиц и заголовков против

## Dashboard

- Один комбинированный эндпойнт: `GET /api/dashboard/{year}/{month}` — часы, ФОТ (по отделам и юрлицам), статусы периодов, динамика за 6 месяцев. Видимость шьётся в сервисе по роли actor-а: admin/accountant — вся компания, manager — свой отдел (принудительно), employee — только свои часы (`payroll=None`, `periods=None`).
- **Диапазон месяцев** (task_ux_improvements ч.2): `?to_year=&to_month=` — конец периода включительно, `(year, month)` при этом начало. Параметры задаются только парой (иначе 422), конец раньше начала — 422, длиннее `MAX_RANGE_MONTHS` = **12 месяцев** — 422. Без них ответ прежний: `to_*` совпадают с началом, `months_count=1`.
  - Все показатели — **сумма по месяцам** диапазона (часы, норма, ФОТ, эффект округления). Каждый месяц считается ОТДЕЛЬНО и потом складывается: норма, лимит больничного и статусы периодов — месячные, «растянуть» расчёт на диапазон нельзя.
  - `non_calculable_employees` считает **разные рабочие места**, а не строки расчёта: иначе сотрудник без графика удваивался бы с каждым месяцем.
  - Статусы периодов — строка на **(отдел, месяц)**; свернув диапазон в строку на отдел, потеряли бы, какой именно месяц не закрыт. Просрочка считается от НАЧАЛА диапазона.
  - Динамика диапазона — по его же месяцам (одиночный месяц по-прежнему тянет хвост `TREND_MONTHS` = 6 назад). Уже посчитанные месяцы переиспользуются, второй раз не считаются.
  - **Цена запроса линейна по месяцам**: на демо-базе (200 сотрудников) месяц ≈ 1,7 с, квартал ≈ 4,6 с, год ≈ 18 с. Отсюда потолок в 12 месяцев; фронт длиннее и не даёт выбрать. Если понадобится год «мгновенно» — кэш/матвью помесячных итогов, а не расширение потолка.
- Фронт: переключатель периода в шапке — два `<input type="month">` (начало/конец), стрелки двигают окно ЦЕЛИКОМ сохраняя длину, пресеты «Месяц/Квартал/Год». Выбранный период сохраняется (`tabel.dashboard.period`).
- Сервис `app/services/dashboard.py` агрегирует **поверх** `calculate_employee_payroll` и `visible_employees_for_actor` — формулы ЗП и правила видимости НЕ дублировать. Тест сверяет ФОТ дашборда с `/api/timesheet/{y}/{m}/payroll` — цифры обязаны совпадать.
- «Просрочено» = существующий период прошлых месяцев в статусе ≠ closed. Ограничение: lazy-создание периодов — месяц, который никто не открывал, в просрочку не попадёт.
- KPI `non_calculable_employees` — сколько сотрудников не вошло в расчёт ФОТ (нет оклада/графика, сменный график); фронт показывает предупреждение.
- KPI **«Эффект округления»** (`PayrollTotalsRead.rounding_effect`, task_payout_rounding) — Σ хвостов округления «К выплате» вниз до 100 ₽ за месяц (осело в пользу компании). Считается `_rounding_effect` через `build_payroll_summary` (премий/удержаний в ФОТ дашборда нет, из `calculate_employee_payroll` «к выплате» не получить) — цифра обязана совпадать с `total_rounding_tail` в `/payroll`, тест это сверяет. Живёт в блоке ФОТ, поэтому видимость та же: admin/accountant — все, manager — свой отдел, employee — `payroll=None`.
- Фронт: `DashboardPage` (recharts: BarChart/PieChart/LineChart, всё в ResponsiveContainer), данные одним запросом через `api/dashboard.ts`. Клик по отделу (строка статусов / столбец часов) → `/timesheet?year=&month=&department_id=`. Динамика при <2 точках — заглушка «Недостаточно данных».

## Сохранение состояния интерфейса (task_ux_improvements ч.3)

Выбранный месяц, фильтры, отдел и вид **не сбрасываются** при переходе между разделами и переживают перезагрузку страницы.

- Хранилище — **localStorage**, ключи с префиксом `tabel.`. В БД это не едет: состояние экрана — свойство браузера, а не данных. Ничего чувствительного (токен и профиль живут отдельно).
- Единственная точка доступа — `frontend/src/utils/persist.ts`: `UI_KEYS` (все ключи перечислены там), `loadUiState` / `saveUiState` / `loadValidated`. Любое обращение обёрнуто: недоступное хранилище (приватный режим, квота) или битый JSON = «значения нет» → **graceful дефолт**, экран работает как раньше. Прежняя пометка «localStorage в этом окружении ненадёжен» снята именно этим — падать теперь нечему.
- `loadValidated(key, fallback, isValid)` — проверка формы: в хранилище может лежать значение от прежней версии экрана. Меняете формат — либо новый ключ, либо валидатор, иначе старое значение приедет в компонент.
- Хуки/сторы: `hooks/usePersistentState.ts` (useState + запись **эффектом**, чтобы сеттер остался чистым при двойном вызове в StrictMode), `store/period.ts` (месяц, **общий** для табеля и «Расчёт ЗП»), `store/timesheetView.ts` (вид + выбранный отдел).
- Что сохраняется: период табеля/ведомости (общий), период дашборда (диапазон, свой ключ — семантика другая), вид табеля, выбранный отдел, фильтры табеля (поиск, компания) и ведомости (отдел, поиск, компания), развёрнутость блоков «ПО КОМПАНИЯМ» и «ЗАЯВКИ НА ПОДБОР», «показывать закрытые» в «Задачах».
- **Ссылка сильнее сохранённого выбора**: `?year=&month=&department_id=` из «Задач»/дашборда применяется СИНХРОННО на первом рендере `TimesheetPage` (`useState`-инициализатор ДО чтения сторов, не `useEffect`) — из эффекта первый запрос ушёл бы за прежний месяц/отдел, и его ответ мог прийти позже правильного и затереть его.
- Сохранённый отдел не опасен после смены пользователя: `TimesheetPage` сбрасывает выбор, которого нет в загруженном списке отделов (пустой список сбросом не считается — это могла быть неудавшаяся загрузка справочника).
