# ТЗ — Интеграция системы учёта рабочего времени «Земля МО» с 1С:ЗУП 3.1

Версия: 1.0 · Статус: на согласование · Дата: 2026-06-26

> Документ описывает интеграцию веб-системы учёта рабочего времени и расчёта
> зарплаты (далее — **Система**) с **1С:Зарплата и управление персоналом 3.1**
> (далее — **ЗУП**). Обмен — по REST API. ЗУП — мастер справочников; Система
> ведёт табель и считает брутто-начисление, отдаёт готовую ведомость в ЗУП.

---

## 1. Назначение и контекст

Группа «Земля МО» — несколько юридических лиц; зарплата сотрудника распределяется
между ними. Система уже реализует:

- табель рабочего времени (часы по дням и по юрлицам);
- расчёт **брутто к начислению** (оклад по норме, переработка помесячно,
  праздничные/выходные, премии, KPI, удержания: аванс и заём);
- управленческое распределение начисленного по юрлицам в процентах;
- ведомость «Расчёт ЗП» и выгрузку в Excel.

Система **НЕ считает** НДФЛ, страховые взносы, не ведёт кадровый ЭДО, не формирует
платёжные документы и регламентированную отчётность — это остаётся за ЗУП.

Цель интеграции: убрать двойной ручной ввод. ЗУП ведёт справочники (организации,
подразделения, сотрудники, оклады, графики) и отдаёт их в Систему; Система считает
табель и начисления и возвращает в ЗУП готовую ведомость, на основании которой ЗУП
рассчитывает налоги/взносы и проводит выплату.

### 1.1. Разделение ответственности

| Функция | Где ведётся | Источник истины |
|---|---|---|
| Организации (юрлица) | ЗУП → Система | **ЗУП** |
| Подразделения | ЗУП → Система | **ЗУП** |
| Сотрудники (ФИО, таб.№, должность, оклад, график, дата приёма/увольнения) | ЗУП → Система | **ЗУП** |
| Графики работы | ЗУП → Система | **ЗУП** |
| Табель рабочего времени (часы по дням × юрлицо) | Система | **Система** |
| Расчёт брутто-начисления (оклад, переработка, праздничные) | Система | **Система** |
| Премии, KPI, аванс, удержание займа | Система | **Система** (см. §9, открытый вопрос по займам) |
| Распределение начисленного по юрлицам, % | Система | **Система** |
| НДФЛ, страховые взносы | ЗУП | **ЗУП** |
| Выплата, ведомости на выплату, отражение в бухучёте | ЗУП | **ЗУП** |
| Регламентированная отчётность | ЗУП | **ЗУП** |

> Принцип: формулы расчёта брутто **не дублируются** в ЗУП. ЗУП принимает суммы
> как готовые «разовые начисления» и далее работает только с налогами/выплатами.

## 3. Архитектура интеграции

```
        ┌──────────────────────────┐         REST (JWT)        ┌─────────────────────────┐
        │        1С:ЗУП 3.1        │  ───── справочники ─────▶ │        Система          │
        │  (мастер справочников,   │   организации, подразд.,  │  (табель + расчёт ЗП)   │
        │   НДФЛ/взносы/выплаты)    │   сотрудники, графики      │                         │
        │                          │ ◀──── ведомость ───────── │                         │
        └──────────────────────────┘   начисления + распред.   └─────────────────────────┘
```

- Транспорт: **HTTPS REST**, аутентификация **JWT Bearer**.
- Инициатор обоих обменов — **ЗУП** (вызывает HTTP-сервис на стороне 1С по расписанию
  или по кнопке, обращается к REST Системы). Допустимо реализовать на стороне 1С
  регламентное задание.
- Формат — **JSON**, кодировка UTF-8.
- Денежные суммы и часы передаются в JSON как **строки** (Decimal), во избежание
  потери точности float. Пример: `"73182.00"`. На стороне 1С парсить в число с
  округлением до копеек (для сумм) и до целых часов (для часов).

## 4. Состав обмена

### 4.1. Справочники: ЗУП → Система

ЗУП передаёт (upsert по идентификатору 1С, см. §5.4) актуальные справочники.
Минимальный состав полей:

**Организации (юрлица):**
| Поле | Тип | Обяз. | Комментарий |
|---|---|---|---|
| `external_id_1c` | string (GUID) | да | ссылка элемента справочника «Организации» |
| `code` | string(5) | да | короткий код (zmo/kft/sec) |
| `name` | string | да | наименование |
| `inn` | string(12) | нет | ИНН |
| `is_active` | bool | да | пометка удаления / архив |

**Подразделения:**
| Поле | Тип | Обяз. | Комментарий |
|---|---|---|---|
| `external_id_1c` | string (GUID) | да | |
| `code` | string | да | |
| `name` | string | да | |
| `is_active` | bool | да | |

**Графики работы:**
| Поле | Тип | Обяз. | Комментарий |
|---|---|---|---|
| `external_id_1c` | string (GUID) | да | |
| `name` | string | да | напр. «5/2» |
| `hours_per_shift` | int | да | часов в смене (8) |
| `schedule_type` | enum `standard`/`shift` | да | `standard` = 5/2 по производственному календарю; `shift` (2/2, 3/3) Система пока не рассчитывает |

**Сотрудники:**
| Поле | Тип | Обяз. | Комментарий |
|---|---|---|---|
| `external_id_1c` | string (GUID) | да | ссылка элемента «Сотрудники» |
| `tab_number` | string(50) | да | табельный номер (уникален) |
| `full_name` | string | да | ФИО |
| `position` | string | нет | должность |
| `department_external_id` | string (GUID) | нет | ссылка на подразделение (может быть пусто) |
| `schedule_external_id` | string (GUID) | нет | ссылка на график |
| `default_company_external_id` | string (GUID) | да | основное юрлицо |
| `rate` | string(Decimal) | нет | оклад (плановое начисление) |
| `hire_date` | date | нет | дата приёма |
| `dismissal_date` | date | нет | дата увольнения (null если работает) |
| `is_active` | bool | да | false при увольнении |

> **Не передаются из ЗУП** (ведутся в Системе): `weekend_pay_type`,
> `weekend_coefficient`, `weekend_fixed_rate`, `overtime_coefficient`,
> проценты распределения по юрлицам, премии/KPI, параметры займа. См. §9 открытые
> вопросы.

### 4.2. Результат расчёта: Система → ЗУП

Система отдаёт **ведомость за период (год, месяц)** только по **закрытым**
периодам (`status = closed`, см. §7). Структура соответствует
`GET /api/timesheet/{year}/{month}/statement` (§5.2). По каждому сотруднику:

| Поле | Назначение для ЗУП |
|---|---|
| `tab_number`, `employee_id`, `external_id_1c` | сопоставление с сотрудником ЗУП |
| `base_salary` | начислено по окладу (вкл. оплату праздничных/выходных часов) |
| `overtime_amount` | переработка (помесячная) |
| `premium_amount` | премия |
| `kpi_amount` | KPI |
| `accrued_total` | **итого начислено** = оклад + переработка + премия + KPI |
| `deductions` | удержания (аванс + доля займа) |
| `net_payout` | к выплате (= accrued_total − deductions) |
| `distribution[]` | распределение начисленного по юрлицам: `company_external_id`, `percent`, `amount` |

В ЗУП эти суммы загружаются как **разовые/плановые начисления** документа начисления
зарплаты соответствующего сотрудника; `distribution[]` используется для отражения
затрат по юрлицам (аналитика проводок). Далее ЗУП самостоятельно рассчитывает НДФЛ
и страховые взносы от `accrued_total` и формирует выплату на `net_payout` (за вычетом
НДФЛ, который считает ЗУП).

> Важно: `net_payout` Системы — это «к выплате до НДФЛ» (брутто минус
> управленческие удержания аванса/займа). НДФЛ в Системе **не вычитается**.
> Итоговую сумму на руки определяет ЗУП.

## 5. Технический контракт REST API (сторона Системы)

Базовый URL: `https://<host>/api`. Все ответы — `application/json; charset=utf-8`.

### 5.1. Аутентификация

`POST /api/auth/login`
```json
{ "email": "integration@example.com", "password": "<пароль сервис-аккаунта>" }
```
Ответ:
```json
{ "access_token": "<JWT>", "token_type": "bearer", "must_change_password": false }
```
Далее во всех запросах заголовок: `Authorization: Bearer <JWT>`.

- Токен живёт `ACCESS_TOKEN_EXPIRE_MINUTES` (по умолчанию 480 мин). При 401 —
  повторный `login`.
- Для интеграции завести **отдельный сервис-аккаунт** с ролью `accountant`
  (видит все отделы; финансовые данные доступны). `must_change_password=false`.

### 5.2. Получение ведомости (Система → ЗУП)

`GET /api/timesheet/{year}/{month}/statement`

Ответ (сокращённо, по факту схемы `PayrollStatementRead`):
```json
{
  "year": 2026, "month": 5,
  "companies": [ { "id": 12, "code": "zmo", "name": "ЗемляМО" } ],
  "rows": [
    {

      "main_company_id": 12, "department_name": "Бухгалтерия", "position": "Бухгалтер",
      "rate": "80000.00", "norm_hours": "168.00", "fact_hours": "168.00",
      "overtime_coefficient": "1.50", "overtime_hours": "0.00", "overtime_amount": "0.00",
      "base_salary": "80000.00",
      "premium_amount": "0.00", "kpi_amount": "0.00",
      "accrued_total": "80000.00",
      "deductions": "0.00", "net_payout": "80000.00",
      "is_overridden": false, "percent_sum": "100.000",
      "distribution": [ { "company_id": 12, "percent": "100.000", "amount": "80000.00" } ],
      "is_calculable": true, "note": null
    }
  ],
  "total_base_salary": "...", "total_overtime_amount": "...", "total_premium": "...",
  "total_kpi": "...", "total_accrued": "...", "total_deductions": "...",
  "total_net_payout": "...", "distribution_totals": { "12": "..." }

```

> Для сопоставления юрлиц в `distribution[]` понадобится их `external_id_1c`. Это

Доп. эндпоинт с детализацией по дням и по компаниям (если ЗУП нужен табель):
`GET /api/timesheet/{year}/{month}/payroll` → `PayrollSummaryRead`
(per-company `breakdown_by_company`: `hours`, `overtime_hours`, `holiday_hours`,
`base_amount`, `overtime_amount`, `holiday_amount`, `total`).

### 5.3. Справочники из Системы (для сверки)

`GET /api/employees` → список сотрудников (схема `EmployeeRead`).
Используется ЗУП для сверки/диагностики; мастером остаётся ЗУП.

### 5.4. Приём справочников (ЗУП → Система) — ДОРАБОТКА

На текущий момент в Системе есть CRUD `POST/PUT /api/employees`,
`/api/departments`, `/api/companies`, `/api/schedules`, но **нет идемпотентного
upsert по идентификатору 1С**. Требуется реализовать (§10):

- `POST /api/integration/1c/sync/organizations`
- `POST /api/integration/1c/sync/departments`
- `POST /api/integration/1c/sync/schedules`
- `POST /api/integration/1c/sync/employees`

Каждый принимает массив элементов из §4.1, выполняет **upsert по `external_id_1c`**,
возвращает сводку `{ created, updated, skipped, errors[] }`. Обмен идемпотентен:
повторная отправка тех же данных не создаёт дублей.

### 5.5. Форматы, ошибки, общие правила

- Даты — `YYYY-MM-DD`. Денежные/часовые величины — строки (Decimal).
- Округление сумм Системы — до целых рублей, `ROUND_HALF_EVEN`. Суммы частей по
  юрлицам сходятся с итогом точно (метод наибольших остатков).
- Коды ошибок: `200/201` — успех, `401` — нет/протух токен, `403` — нет прав,
  `404` — нет данных за период, `422` — ошибка валидации (тело с описанием).
- Все мутации в Системе пишутся в audit log.

## 6. Расчётные правила Системы (что приходит в ЗУП уже посчитанным)

ЗУП **не пересчитывает** эти величины — принимает как есть.

1. **Норма часов** (для `schedule_type=standard`): по производственному календарю
   (источник xmlcalendar.ru) = `рабочие_дни × часы_в_смене − предпраздничные_сокращения`.
2. **Переработка — помесячно**: `overtime_hours = max(0, факт_будних − норма)`.
   Праздничные/выходные часы в факт будних и в переработку не входят.
3. **База оклада**: `base = rate × min(1, зачётные_будние / норма)`,
   `зачётные_будние = min(факт_будних, норма)`.
4. **Переработка ₽**: `overtime_hours × (rate/норма) × overtime_coefficient`
   (коэффициент per-employee: 0 / 1 / 1.5, дефолт 1.5).
5. **Праздничные/выходные ₽** (per-employee): `coefficient` →
   `holiday_hours × (rate/норма) × weekend_coefficient`; `fixed_rate` →
   `holiday_hours × weekend_fixed_rate`. Включаются в `base_salary`.
6. **Итого начислено**: оклад + праздничные + переработка + премия + KPI.
7. **Удержания**: аванс + доля займа. **К выплате** = Итого начислено − удержания.
8. **Распределение по юрлицам** (управленческое, не по часам): база =
   Итого начислено; `сумма_юрлица = Итого × %`; набор «юрлицо→%» из карточки
   сотрудника или помесячное переопределение.
9. Только `schedule_type=standard` рассчитывается. `shift`-графики →
   `is_calculable=false`, такие строки ЗУП обрабатывает вручную/по своим правилам.

## 7. Регламент обмена

1. **Справочники (ЗУП → Система)** — по изменению или регламентно (напр. ежедневно
   ночью, плюс по кнопке перед началом ввода табеля на месяц).
2. **Табель** ведётся в Системе в течение месяца. Период проходит workflow
   `draft → pending_review → closed`.
3. **Ведомость (Система → ЗУП)** забирается **только по закрытым периодам**
   (`status=closed`). Незакрытый период ЗУП не загружает (данные ещё могут меняться).
4. **Повторная загрузка** закрытого периода в ЗУП должна быть идемпотентной:
   ЗУП обновляет ранее загруженные начисления по ключу `(сотрудник, год, месяц)`,
   не плодя дубли.
5. **Переоткрытие периода** (Система, только admin, с обоснованием) после выгрузки
   в ЗУП — исключительная ситуация: ЗУП должен повторно перечитать ведомость и
   перезаписать начисления за месяц. Рекомендуется согласовывать оргрегламентом.

## 8. Что реализует 1С-разработчик (сторона ЗУП)

1. **Подсистема обмена** (HTTP-клиент к REST Системы): хранение базового URL,
   логина/пароля сервис-аккаунта, получение и кэш JWT, обработка 401.
2. **Выгрузка справочников** в Систему (§4.1, §5.4): организации, подразделения,
   графики, сотрудники — upsert по `external_id_1c` (Ссылка элемента 1С как GUID).
3. **Загрузка ведомости** из Системы (§5.2) за закрытый период и создание/обновление
   документа начисления (разовые/плановые начисления) по каждому сотруднику:
   - суммы `base_salary`, `overtime_amount`, `premium_amount`, `kpi_amount` —
     как виды начислений (маппинг на виды расчёта ЗУП согласовать отдельно);
   - `deductions` — как удержания (аванс/заём), либо игнорировать, если займы/авансы
     ведутся в ЗУП (см. §9);
   - `distribution[]` — отражение по юрлицам/способам отражения в учёте.
4. **Расчёт НДФЛ и взносов** штатными средствами ЗУП от загруженных начислений.
5. **Регламентное задание** на оба обмена + журнал обмена с диагностикой ошибок.
6. **Сопоставление видов начислений** Системы ↔ ЗУП (таблица соответствия) —
   согласовать на этапе проектирования.

## 9. Открытые вопросы (требуют решения до реализации)

1. **Оклад (rate)** — мастер ЗУП (плановое начисление). Подтвердить, что Система
   получает оклад из ЗУП и **не редактирует** его (поле становится read-only в
   карточке Системы). Сейчас в Системе оклад редактируется вручную.
2. **Займы и авансы** — сейчас ведутся в Системе (поля займа в карточке + удержания).
   В ЗУП есть штатный механизм займов сотрудникам. Решить, кто мастер:
   - вариант А (рекомендую долгосрочно): займы/авансы → ЗУП, Система их не считает,
     в `deductions` идут только согласованные удержания;
   - вариант Б (как сейчас): займы/авансы в Системе, ЗУП принимает `deductions`
     как готовую сумму удержаний.
3. **Праздничные/выходные и коэффициенты** (`weekend_*`, `overtime_coefficient`) —
   подтвердить, что это настройки Системы, а не ЗУП.
4. **Shift-графики** (2/2, 3/3): Система их пока не рассчитывает (`is_calculable=false`).
   Определить порядок: считать в ЗУП или дорабатывать Систему.
5. **Маппинг видов начислений** Система → ЗУП — отдельная согласованная таблица.
6. **НДФЛ-вычеты, исполнительные листы, больничные/отпуска** — целиком на стороне
   ЗУП; уточнить, не должны ли отпуск/больничный исключаться из табеля Системы
   (сейчас столбцы отпуск/больничный в выгрузке не заполняются).

---

## 10. Доработки на стороне Системы (объём для нашей команды)

1. Добавить поле `external_id_1c` (string/UUID, индекс, уникальность) в модели:
   `companies`, `departments`, `schedules`, `employees`. Миграция Alembic.
2. Эндпоинты идемпотентного приёма справочников из §5.4
   (`/api/integration/1c/sync/*`) с upsert по `external_id_1c`.
3. В выгрузку ведомости (`/statement`) добавить `external_id_1c` сотрудника и
   `company_external_id` в `distribution[]`.
4. Сервис-аккаунт интеграции (роль accountant) + (опционально) отдельный
   scope/ключ для интеграционных эндпоинтов.
5. Сделать поля, мастер которых ЗУП (оклад, ФИО, таб.№, график, подразделение),
   **только для чтения** в админ-панели Системы в режиме интеграции, чтобы не
   перетереть данные при следующей синхронизации.

## 11. Безопасность

- Транспорт только HTTPS. JWT Bearer, срок жизни ограничен.
- Отдельный сервис-аккаунт ЗУП с минимально необходимой ролью (accountant).
- Пароль/секреты хранить в защищённом хранилище 1С, не в коде обработки.
- Все интеграционные операции Системы фиксируются в audit log.
- Прямой доступ к БД PostgreSQL из 1С — **запрещён** (обходит права и аудит).

## 12. Этапы и приёмка

| Этап | Содержание | Критерий приёмки |
|---|---|---|
| 1. Проектирование | Согласовать §9 (открытые вопросы), таблицу маппинга видов начислений | Подписанные решения |
| 2. Доработка Системы | Поля `external_id_1c`, sync-эндпоинты, поля в ведомости (§10) | Эндпоинты проходят тесты, миграция применена |
| 3. Обмен справочниками | ЗУП выгружает организации/подразделения/графики/сотрудников | В Системе появляются записи с корректными `external_id_1c`, без дублей при повторе |
| 4. Обмен ведомостью | ЗУП загружает закрытый период, создаёт начисления | Суммы в ЗУП совпадают с `/statement`; распределение по юрлицам корректно |
| 5. Расчёт в ЗУП | НДФЛ/взносы/выплата от загруженных начислений | Контрольный расчёт за тестовый месяц сходится |
| 6. Регламент | Регламентные задания, журнал обмена, обработка ошибок | Автоматический обмен работает, ошибки видны в журнале |

**Тестовый сценарий**: один месяц по 2–3 сотрудникам разных юрлиц (включая
сотрудника с распределением 50/30/20 и переработкой) проходит весь путь
ЗУП → Система (справочники) → табель/расчёт → Система → ЗУП (ведомость) → расчёт
НДФЛ в ЗУП, и итоговые суммы сверяются вручную.
