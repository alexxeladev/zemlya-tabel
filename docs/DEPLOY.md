# Развёртывание (preprod / prod)

Контейнерный стек: **Postgres + backend (FastAPI/uvicorn) + web (nginx: статика фронта + прокси `/api` на backend)**. Всё поднимается одной командой. Фронт и API — на одном origin, CORS не нужен.

## Требования на сервере

- Linux + git + `sudo` (или root)
- Доступ в интернет (для установки Docker, сборки образов и загрузки производственного календаря)

**Docker ставить заранее не обязательно** — если его нет, `install.sh` установит
Docker Engine + compose-плагин сам (официальный скрипт get.docker.com, нужен sudo)
и добавит тебя в группу `docker`. До первого релогина docker-команды в текущей
сессии выполняются через `sudo` автоматически. Отключить авто-установку:
`AUTO_INSTALL_DOCKER=0 ./install.sh` (тогда Docker нужен заранее).

## Первая установка

```bash
git clone <repo> zemlya-tabel && cd zemlya-tabel
./install.sh
```

`install.sh` сам:
1. проверит Docker;
2. создаст `.env.preprod` и **сгенерирует секреты** (`SECRET_KEY`, пароль БД, пароль админа), если файла ещё нет;
3. соберёт образы;
4. поднимет Postgres → накатит миграции (`alembic upgrade head`);
5. создаст первичного админа;
6. поднимет backend + web;
7. напечатает URL и логин/пароль админа.

Открывать: `http://<IP-или-домен-сервера>:8080` (порт меняется через `PREPROD_HTTP_PORT` в `.env.preprod`). При первом входе система попросит сменить пароль.

`.env.preprod` в git **не коммитится** (там секреты). Хочешь задать значения заранее — скопируй `.env.preprod.example` в `.env.preprod` и заполни до запуска `install.sh` (тогда он ничего не перегенерирует).

## Обновление (цикл dev → preprod)

На dev: коммит и `git push`. На сервере:

```bash
git pull && ./deploy.sh
# или одной командой:
./deploy.sh --pull
```

`deploy.sh` по шагам: **бэкап БД** → пересборка образов из текущего кода → миграции (`alembic upgrade head`) → перезапуск backend+web. Данные БД (том `tabel-preprod-data`) и `.env.preprod` сохраняются.

### Авто-бэкап перед миграциями

Перед накатом миграций `deploy.sh` делает `pg_dump | gzip` в `$BACKUP_DIR`
(по умолчанию `~/backups/zemlya-tabel`) и хранит последние `$BACKUP_KEEP`
(по умолчанию 10). Оба параметра можно задать в `.env.preprod`:

```
BACKUP_DIR=/var/backups/zemlya-tabel
BACKUP_KEEP=10
```

Если бэкап не удался (pg_dump упал или дамп пустой) — **деплой прерывается**,
миграции не выполняются. Пропустить бэкап осознанно: `./deploy.sh --no-backup`.

Это бэкап «на всякий случай перед миграцией». Регулярные бэкапы, расписание и
проверку восстановления делают отдельные скрипты — см. следующий раздел.

## Бэкапы: снять, увезти, проверить, восстановить

Все команды запускаются из каталога проекта на сервере. Ничего править в файлах
не нужно: настройки скрипты записывают сами.

```bash
./scripts/backup.sh --status      # что настроено, когда снимали последний раз
./scripts/backup.sh               # снять бэкап сейчас
./scripts/backup.sh --schedule    # включить ежедневный бэкап в 03:30
                                  # + еженедельную проверку восстановления (вс 04:30)
```

Скрипт проверяет каждый дамп: пустой, битый или без таблиц — не бэкап, такой
файл удаляется и команда завершается ошибкой. Хранятся последние 10 (изменить:
`./scripts/backup.sh --keep 30`).

### Куда увозить копию

По умолчанию бэкапы лежат на том же сервере: сгорит он — сгорят и они. Когда
появится внешнее хранилище, включается одной командой:

```bash
./scripts/backup.sh --where dir:/mnt/backup/tabel       # внешний диск или сетевая папка
./scripts/backup.sh --where ssh:user@host:/srv/backup   # другой сервер (нужен SSH-ключ без пароля)
./scripts/backup.sh --where s3:bucket/tabel             # S3-совместимое хранилище (нужен aws cli)
./scripts/backup.sh --where local                       # вернуть «только этот сервер»
```

Если копия не уехала, команда завершается ошибкой и прямо говорит, чего не
хватает (не примонтирован диск, не подошёл SSH-ключ, нет ключей доступа к S3).

### Проверка восстановления

```bash
./scripts/restore-check.sh                       # последний бэкап
./scripts/restore-check.sh ~/backups/zemlya-tabel/tabel_20260923_033000.sql.gz
```

Дамп разворачивается во **временную** базу рядом с рабочей, из неё читаются
данные (сотрудники, рабочие места, ячейки табеля, суммы, версия схемы,
уникальные индексы), после чего временная база удаляется. Рабочая база не
затрагивается. Проверка «файл создан и непустой» бэкапом не считается: так не
видно ни оборванной выгрузки, ни дампа от другой версии схемы.

### Восстановление рабочей базы

```bash
./scripts/restore.sh                              # из последнего бэкапа
./scripts/restore.sh путь/к/файлу.sql.gz          # из конкретного
```

Операция замещающая — всё, что внесли после снятия бэкапа, пропадёт, поэтому
скрипт переспрашивает. По шагам: страховочный дамп текущей базы → проверка
выбранного бэкапа → остановка приложения → замена базы → гашение кэша дашборда
→ подъём и ожидание готовности. Если восстановили не то — вернуться можно тем же
скриптом, указав страховочный дамп (его путь печатается в конце).

Бэкап старше текущего кода — после восстановления нужны миграции:

```bash
docker compose --env-file .env.preprod -f docker-compose.preprod.yml run --rm backend alembic upgrade head
```

Готовность после этого: `curl -s http://<адрес>:8080/ready`.

## Проверки живости и готовности

| Адрес | Что отвечает | Для чего |
|---|---|---|
| `/health` | всегда 200, пока процесс жив; в базу не ходит | перезапуск зависшего контейнера |
| `/ready` | 200, если база отвечает и схема на последней миграции; иначе **503** с причиной | пускать ли трафик |

Контейнер `backend` считается здоровым по `/ready`, поэтому `web` (а с ним и
пользователи) поднимается только после применённых миграций. Если `/ready`
отвечает 503 — в теле написано, что именно не так: база недоступна, миграции не
применены или схема отстала от кода.

## HTTPS

Стек публикует HTTP: пароли и токены идут по сети открытым текстом. Включается
одной командой — выберите подходящий способ:

```bash
# 1. Бесплатный сертификат Let's Encrypt с автопродлением.
#    Нужно: домен указывает на этот сервер, порты 80 и 443 открыты снаружи.
./scripts/enable-https.sh --letsencrypt --domain tabel.example.ru --email it@example.ru

# 2. Сертификат выдал ваш IT-отдел.
./scripts/enable-https.sh --cert /путь/fullchain.pem --key /путь/privkey.pem --domain tabel.example.ru

# 3. TLS снимает внешний прокси (Cloudflare, корпоративный балансировщик).
./scripts/enable-https.sh --behind-proxy

./scripts/enable-https.sh --status   # что включено, до какого числа годен сертификат
./scripts/enable-https.sh --off      # вернуться к обычному HTTP
```

Выбранный режим запоминается, и `./deploy.sh` его сохраняет: обновление кода
HTTPS не выключает.

### Что требуется от внешнего прокси (вариант 3)

1. Терминировать TLS и перенаправлять HTTP → HTTPS.
2. Передавать заголовки `X-Forwarded-Proto: https`, `X-Real-IP` с адресом
   клиента и `X-Forwarded-For`. По `X-Real-IP` в журнал пишется адрес неудачных
   попыток входа — без него все попытки выглядят пришедшими с одного адреса.
3. Не подменять `Host`.
4. Не резать длинные ответы: табель отдела — сотни килобайт JSON.
5. Проверять живость по `/health`, готовность по `/ready`.
6. **Закрыть прямой доступ к порту 8080 снаружи** — иначе HTTPS на прокси
   обходится обычным запросом. Вариант 3 привязывает вход к `127.0.0.1`; если
   прокси на другой машине, закройте порт межсетевым экраном.

## Prod

Тот же репозиторий и те же скрипты, отдельный хост и свой `.env.preprod` (можно переименовать/держать `.env.prod` и указывать `--env-file` — но по умолчанию скрипты ждут `.env.preprod`). Повышение с preprod до prod = смена env-файла, код и образы те же.

> Дальнейший шаг для prod (когда понадобится): собирать образы в CI и пушить в GitHub Container Registry (GHCR), а на хостах делать `docker compose pull` — тогда preprod и prod крутят байт-в-байт один образ и откат делается сменой тега. Пока не настроено; текущая схема (build из git на сервере) этого не требует.

## Полезные команды

```bash
DC="docker compose --env-file .env.preprod -f docker-compose.preprod.yml"

$DC ps                 # статус сервисов
$DC logs -f            # логи (Ctrl+C — выйти)
$DC logs -f backend    # логи только backend
$DC down               # остановить (данные БД в томе сохраняются)
$DC down -v            # ОСТОРОЖНО: снести вместе с данными БД

# Ручные операции в контейнере backend:
$DC run --rm backend alembic current
$DC run --rm backend python -m app.cli reset-password --email admin@zemlya-mo.ru --new-password NEWPASS
```
