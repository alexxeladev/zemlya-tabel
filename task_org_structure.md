# Задача — Единая оргструктура (дерево Компания→Отдел→Сотрудники) + мульти-отдел менеджеров

## Контекст

Сейчас управление оргструктурой разрознено: Компании, Отделы, права, сотрудники — на разных вкладках, настраивается по отдельности. Нужно свести в **единый экран-дерево**: Компания → Отделы → Сотрудники, где сразу видно структуру, задаётся головная компания отдела, назначаются менеджеры отдела (мульти-отдел).

**КРИТИЧЕСКИ ВАЖНО:** это реорганизация UI/навигации оргструктуры. Логика РАСЧЁТОВ (мультикомпания: часы по компаниям, распределение по %) НЕ меняется. Головная компания отдела — это навигация/группировка, НЕ ограничение на кого работают сотрудники. Сотрудник по-прежнему может работать на несколько компаний.

Задача намеренно НЕ указывает имена конкретных функций, переменных, файлов. Разберись в коде сам. Действуй по правилу 3 попыток.

Перед началом — бэкап БД:
```bash
mkdir -p ~/backups
docker exec -t $(docker ps -q -f ancestor=postgres:16) pg_dump -U tabel tabel > ~/backups/before_orgstructure_$(date +%s).sql
```

## ЧАСТЬ 1 — Головная компания отдела

- У отдела появляется поле «Головная компания» (в какой компании числится отдел)
- Это для группировки в дереве и навигации — НЕ ограничивает мультикомпанию сотрудников
- Существующие отделы: при миграции проставить головную компанию (если очевидно из данных — проставить; иначе оставить пустой/дать задать вручную потом)
- Миграция, применить, alembic current = head

**НЕ путать:** головная компания отдела (навигация) ≠ компании на которые работают сотрудники (расчёт, остаётся мультикомпанийным).

---

## ЧАСТЬ 2 — Мульти-отдел для менеджеров (many-to-many)

Менеджер может управлять несколькими отделами. Связь «многие-ко-многим», управляется со стороны отдела.

- `department_id` сотрудника (где работает) — НЕ трогаем
- Добавляем связь «менеджер ↔ управляемые отделы» (managed departments): один менеджер — много отделов, один отдел — много менеджеров
- Миграция: существующим менеджерам перенести их текущий отдел в новую связь (не потерять доступ)

### Логика доступа (везде где manager по одному department_id)

Найти ВСЕ места «manager видит свой один отдел» и заменить на «видит свои отделы (managed_departments)»:
- Табель, Расчёт ЗП, Сотрудники, Дашборд, Workflow периодов, Финансы
- Селектор отделов для manager — список его отделов + «все мои отделы» с группировкой
- Принудительная проверка на бэке: manager не получает данные отдела которым не управляет (403)

## ЧАСТЬ 3 — Единый экран «Оргструктура» (дерево)

Новый раздел/экран (заменяет или объединяет разрозненные вкладки Компании/Отделы). Древовидная структура:

```
▼ Компания А (ЗемляМО)
    ▼ Отдел ИТО
        • Сотрудник 1
        • Сотрудник 2
        Менеджеры отдела: [Иванов, Петров]
    ▼ Отдел Бухгалтерия
        • Сотрудник 3
        Менеджеры отдела: [Сидоров]
▼ Компания Б (Комфорт)
    ▼ Отдел Охрана
        ...
```

### Возможности экрана

- **Раскрывающееся дерево**: Компания → её отделы (по головной компании) → сотрудники отдела
- **Создать компанию** — тут же, в дереве
- **Создать отдел внутри компании** — кнопка на компании «+ отдел», сразу с головной компанией = эта компания
- **Назначить менеджеров отдела** — на узле отдела, секция «Менеджеры отдела» (мультивыбор сотрудников с ролью manager)
- **Сотрудники в дереве** — под отделом видны его сотрудники (по department_id). Клик — переход в карточку или инлайн-инфо.
- Компактно, сворачивание узлов (при 100+ сотрудниках дерево не должно взрываться — сотрудники сворачиваются)

### Что можно делать из дерева

- Создание компании, отдела
- Задание головной компании отдела
- Назначение менеджеров отдела
- Просмотр сотрудников отдела (редактирование сотрудника — в его карточке, как сейчас)
- Переход к сотруднику

Доступ к экрану оргструктуры — admin (структуру и права меняет только admin).

### Старые вкладки

- Разрозненные вкладки «Компании», «Отделы» — либо заменить этим деревом, либо оставить как есть а дерево добавить отдельным экраном. Предпочтительно: единый экран «Оргструктура» вместо отдельных Компании+Отделы. Если проще оставить старые и добавить дерево — согласуй со мной, но цель — единое место.

## Что НЕ делать / НЕ ломать

- **Расчёты не трогать** — мультикомпания (часы, распределение %) работает как есть. Головная компания отдела на это НЕ влияет.
- **department_id сотрудника** — остаётся (принадлежность к отделу)
- НЕ делать раздел ВАХТА (следующая задача)
- НЕ делать разные уровни доступа менеджера (редактор/просмотр) — единый доступ
- Не рефакторить расчётную часть

## Acceptance criteria

1. У отдела есть головная компания. В дереве отделы сгруппированы под компаниями.
2. Единый экран «Оргструктура»: дерево Компания→Отдел→Сотрудники, раскрывается/сворачивается.
3. Создание компании и отдела (внутри компании) из дерева.
4. Назначение менеджеров отдела на узле отдела.
5. Менеджер с 2+ отделами видит все свои отделы (табель, расчёт ЗП, дашборд).
6. Менеджер не видит отделы которыми не управляет (403 на бэке).
7. Существующие менеджеры сохранили доступ после миграции.
8. **Расчёты не изменились**: сотрудник работает на несколько компаний, распределение % работает как раньше.
9. Дерево не взрывается при 100+ сотрудниках (сотрудники сворачиваемы).
10. `pytest -v` зелёный, тесты: головная компания отдела, мульти-отдел менеджера, изоляция чужих отделов, миграция, расчёты не затронуты.

## Подводные камни

- **Головная компания отдела ≠ мультикомпания расчёта** — САМОЕ важное не перепутать. Головная компания это ярлык для дерева. Расчёт остаётся по фактическим часам/процентам на разные компании. Не завязывай расчёт на головную компанию.
- **department_id vs managed_departments** — где работает vs чем руководит. Разные вещи.
- **Много мест проверки manager** — найди ВСЕ, не пропусти.
- **Миграция менеджеров** — перенести доступы, иначе потеряют.
- **Дерево + производительность** — 100+ сотрудников: ленивая подгрузка или сворачивание, не рендерить всё сразу.
- Миграции — alembic upgrade head + проверка.
