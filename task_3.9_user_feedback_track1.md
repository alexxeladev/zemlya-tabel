## ПРАВКА 1 — Manager только просматривает сотрудников (откат предыдущей правки)

**Контекст:** В прошлой задаче (3.8) мы разрешили manager редактировать своих сотрудников. По обратной связи это решение отменяется — manager должен только **просматривать**.

**Должно быть:**
- Manager **видит** список сотрудников своего отдела (read-only)
- Manager **видит** карточку сотрудника (все поля только для чтения)
- Manager **НЕ может**: создавать, редактировать, увольнять, выдавать доступ, менять что-либо у сотрудников
- Кнопки «Добавить», «Уволить», «Сбросить пароль», «Сохранить» в карточке — отсутствуют или disabled для manager
- Справочники (отделы, компании, графики, производственный календарь) — создавать/менять может **только admin**. Manager их не видит в sidebar (как и было).

**ВАЖНО — что НЕ откатывать:** Финансовые колонки в табеле и страница «Расчёт ЗП» для manager — **остаются доступны** (это правка из 3.8 которую мы НЕ отменяем). Manager видит финансы своего отдела, просто не может редактировать карточки сотрудников.

**На бэке:** убедись что PATCH/POST/DELETE эндпойнты сотрудников и справочников возвращают 403 для manager. Только admin их меняет. GET — manager может (свой отдел).

## ПРАВКА 2 — Переработка считается строго по дням

**Контекст:** Переработка должна считаться **по каждому дню отдельно**, а не от суммарной месячной нормы.

**Правильная логика:**

Для каждого дня в табеле:
- Определи дневную норму сотрудника: для обычного рабочего дня = `hours_per_shift` его графика (обычно 8), для сокращённого дня = `hours_per_shift - 1` (обычно 7)
- Если фактические часы в этот день БОЛЬШЕ дневной нормы → разница идёт в **переработку** этого дня
- Переработка за месяц = сумма переработок по всем дням

Часы в выходные/праздничные дни (тип holiday/weekend в производственном календаре) — это **отдельная категория** (праздничные часы), НЕ переработка. Они считаются по своей логике (см. правку 3).

**База оклада:**
- Обычные (не-переработка, не-праздничные) часы идут в зачёт оклада
- Оклад = `rate × (обычные_зачётные_часы / месячная_норма)`, но не больше полного оклада (cap at rate)
- Если обычных часов больше месячной нормы — оклад полный, излишек уже учтён как переработка по дням

**Проверь текущую реализацию расчёта ЗП:**
- Если переработка сейчас считается как `max(0, всего_за_месяц − месячная_норма)` — это НЕПРАВИЛЬНО, переделай на по-дневную
- Если уже по дням — убедись что логика именно такая как описано

## ПРАВКА 3 — Оплата выходных/праздничных на уровне сотрудника

**Контекст:** Сейчас оплата выходных/праздничных зашита коэффициентом ×1.5 для всех. Реально у разных сотрудников по-разному. Нужно сделать настраиваемым per-employee.

**Новая модель — добавить в карточку сотрудника:**

Два способа оплаты выходных/праздничных часов (выбор в карточке):

**Способ A — Коэффициент:**
- Поле «коэффициент оплаты выходных» — число (например 1.5, 2.0, или 0)
- 0 означает «не оплачивается дополнительно» (часы фиксируются, но доплаты нет)
- Расчёт: `часы_в_выходной × часовая_ставка_от_оклада × коэффициент`
- где `часовая_ставка_от_оклада = rate / месячная_норма`

**Способ B — Фиксированная ставка за час:**
- Поле «фиксированная ставка за час в выходной» — рубли (например 740)
- Расчёт: `часы_в_выходной × фикс_ставка`
- Не зависит от оклада

В обоих случаях **будние часы считаются от оклада как обычно** — фикс/коэффициент применяется ТОЛЬКО к часам в дни типа holiday/weekend.

**Что нужно сделать:**

1. В модели сотрудника добавить поля:
   - Тип оплаты выходных: enum «coefficient» / «fixed_rate»
   - Значение коэффициента (Decimal, nullable) — используется если тип=coefficient
   - Значение фикс-ставки (Decimal, nullable) — используется если тип=fixed_rate
   - По умолчанию: тип=coefficient, коэффициент=1.5 (текущее поведение, чтобы не сломать существующих)

2. **Создать миграцию**, применить через `alembic upgrade head`, проверить `alembic current`.

3. В карточке сотрудника (UI) — секция «Оплата выходных и праздничных»:
   - Радио-выбор: «По коэффициенту» / «Фиксированная ставка за час»
   - Если коэффициент — поле ввода числа (с подсказкой «1.5 = полуторный, 2 = двойной, 0 = не оплачивается»)
   - Если фикс — поле ввода рублей за час
   - Доступно для редактирования только admin (manager только просмотр — см. правку 1)

4. В расчёте ЗП — использовать настройки конкретного сотрудника:
   - Если тип=coefficient → праздничные часы × часовая_ставка × коэффициент
   - Если тип=fixed_rate → праздничные часы × фикс_ставка
   - Учесть в общем итоге выплаты

5. Обновить тесты расчёта — добавить кейсы:
   - Сотрудник с коэффициентом 1.5
   - Сотрудник с коэффициентом 0 (выходные не оплачиваются)
   - Сотрудник с фикс-ставкой 740 — работал 8ч в выходной → 5920 ₽ за этот день

**Что нужно сделать:**

## Acceptance criteria

1. **Manager (qa.manager@example.com)**:
   - Видит список сотрудников своего отдела, но БЕЗ кнопок редактирования/добавления/увольнения
   - Карточка сотрудника открывается в режиме просмотра
   - Финансовые колонки в табеле и страница «Расчёт ЗП» — доступны (НЕ откатывать)

2. **Переработка по дням**: сотрудник отработал в один день 10ч при норме 8 → переработка 2ч. Если в другой день 6ч — недоработка не уходит в минус переработки (переработка только положительная, по каждому дню отдельно).

3. **Оплата выходных**:
   - Создать сотрудника с коэффициентом 1.5 → работа в выходной оплачивается ×1.5 от часовой ставки
   - Создать сотрудника с фикс-ставкой 740 → работа 8ч в выходной = 5920 ₽
   - Создать с коэффициентом 0 → выходные не оплачиваются (но часы видны)

4. **Норма/Факт дней**: в табеле или расчёте ЗП видны колонки с днями. Норма дней мая 2026 ≈ 19, факт = сколько дней реально отработано.

5. **Процент по компаниям**: в разбивке видно «компания: часы (процент)».

6. Все тесты проходят: `pytest -v`.
